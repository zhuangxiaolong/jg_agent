# 精工智能开发平台——第一阶段执行效率优化技术方案 V1.0

> 文档类型：技术设计与研发实施方案  
> 产品：精工智能开发平台（Windows 桌面客户端）  
> 版本：V1.0  
> 状态：供 Codex 研发实施  
> 日期：2026-11-11  
> 配套需求：`精工智能开发平台_第一阶段提效优化_需求方案_V1.0.md`  
> 原则：基于现有代码增量改造；不改变 Codex Runtime 默认值；不新增 Grok Runtime；所有性能优化必须可测量、可关闭、可回退。

## 1. 技术目标

本方案将第一阶段性能优化拆为六个可独立验收的技术模块：

1. Performance Telemetry：统一任务追踪和耗时指标。
2. Workspace Index：本地工作区增量索引。
3. Context Optimizer：上下文检索、去重、预算和缓存。
4. Safe Parallel Scheduler：只读任务安全并行。
5. Test Orchestrator：分级测试与测试证据管理。
6. Performance Console：任务时间线、性能统计和配置管理。

Codex 必须先盘点现有实现并复用已有模块。以下接口和表结构为目标设计，不代表当前项目已经存在同名文件或技术栈。

关键原则：

- 性能追踪和上下文策略属于平台公共层，不在三个 Runtime 内分别实现一套。
- Runtime Adapter 负责将各 Runtime 原生事件映射为平台事件。
- Provider/模型配置与 Runtime 分离，但启动前必须校验兼容关系。
- 任何缓存不得绕过权限校验；缓存命中不代表用户自动获得文件访问权。

## 3. 现状盘点和基线（Sprint 0）

### 3.1 必须检查的代码位置

Codex 应搜索而不是假设：

- Runtime Registry、Runtime Adapter、Runtime Orchestrator。
- Session/Task 生命周期和事件流。
- 工作区和多仓库模型、Git Worktree。
- 文件搜索、仓库扫描、上下文构建、Token 估算。
- 命令执行、构建和测试服务。
- 本地数据库迁移和日志系统。
- 模型 Provider、Base URL、模型 ID 的配置与校验。

### 3.2 基线任务集

建议建立 10–15 个脱敏任务：

- 3 个单仓库代码定位/小改动。
- 3 个前后端多仓库开发。
- 2 个历史 Bug 修复。
- 2 个 SQL/数据库相关分析。
- 2 个测试或重构任务。

同一个对比组必须固定：Runtime、Provider、模型 ID、模型参数、代码 Commit、工作区、测试环境和网络条件。每个任务至少重复 3 次；受随机性影响的指标报告中位数、P90 和样本数。

### 3.3 基线输出

Codex 需生成 `docs/performance/baseline-report.md`，包括：

- 环境规格、Windows 版本、CPU/内存、磁盘。
- Runtime/Provider/模型版本。
- 每个任务端到端耗时和阶段耗时。
- 模型首 token/响应间隔（可测量时）。
- 工具调用数、搜索/读取量、测试时间、重试次数。
- 不可测量项和原因。
- 优先优化的前三个瓶颈，附事件证据。

## 4. 统一性能事件模型

### 4.1 事件类型

```ts
export type PerformanceStage =
  | "runtime.initialize"
  | "workspace.index_check"
  | "workspace.index_update"

  | "file.read"

  | "context.build"
  | "model.queue"

  | "tool.execute"

export interface PerformanceEvent {
  id: string;
  traceId: string;
  spanId: string;
  parentSpanId?: string;
  platformSessionId: string;
  taskId: string;
  workspaceId?: string;
  repositoryId?: string;
  runtimeKind: "codex" | "jinggong" | "claude_agent_sdk";
  providerId?: string;
  modelId?: string;
  stage: PerformanceStage;
  operation: string;
  status: "started" | "completed" | "failed" | "cancelled" | "unavailable";
  startedAt?: string;
  endedAt?: string;
  durationMs?: number;
  queueDurationMs?: number;
  inputTokens?: number;
  outputTokens?: number;
  cacheReadTokens?: number;
  cacheWriteTokens?: number;
  itemCount?: number;
  byteCount?: number;
  retryCount?: number;
  errorCode?: string;
  metadata?: Record<string, string | number | boolean | null>;
}
```

### 4.2 计时实现

- 进程内耗时用 monotonic clock（例如 `performance.now()`），事件持久化时另存 UTC 时间戳。
- 不使用系统墙钟差值直接计算 duration，避免系统时间调整造成负数/异常耗时。
- 所有开始事件必须能关联结束/失败/取消事件；应用崩溃留下的未结束 Span 在下次启动时标记为 `interrupted`。
- 并行任务使用父子 Span；父任务总耗时不能把子任务耗时相加展示为墙钟耗时。
- 区分 queue time、execution time 和 end-to-end time。

### 4.3 Runtime 适配

各 Runtime 只需上报原生可获得的数据；平台不得伪造统一细节。

- Codex Adapter：根据实际 App Server/SDK/CLI 事件映射，不假设一定能取得模型内部推理耗时。
- Jinggong Adapter：平台自研调度和工具层可上报更细粒度 Span。
- Claude Adapter：映射 SDK message、tool、usage、permission 等可公开事件。
- 缺失数据使用 `unavailable`，不可用 Provider usage 时 Token 字段为空。

## 5. 工作区增量索引

### 5.1 索引范围

首期采用轻量本地索引，不强制引入向量数据库。

建议索引数据：

- Workspace/Repository Manifest。
- 文件路径、扩展名、大小、mtime、内容哈希、语言类型。
- 可选全文检索文本和基础符号信息。
- 文件与仓库/Commit/Worktree 关联。
- 索引版本、最后扫描时间、错误状态。

### 5.2 索引技术选项

优先检查当前桌面项目的数据库和检索组件：

- 若本地数据库为 SQLite，可评估 FTS5 作为全文索引。
- 若已有可靠全文搜索引擎，优先复用。
- 第一阶段不要求部署独立服务或外部数据库。
- 不要为了引入向量搜索而增加服务器、容器或用户额外安装依赖。

### 5.3 增量流程

```text
用户启动/选择工作区
        │
        ▼
读取 Repository Manifest + Index Manifest
        │
        ▼
检查目录和 ignore 规则
        │
        ▼
文件变更检测（Watcher + 定期校验）
        │
        ▼
按路径/大小/mtime/hash 判断新增、修改、删除
        │
        ▼
只重建受影响索引项
        │
        ▼
更新 Index Version + 索引状态
```

注意事项：

- 文件 Watcher 事件可能丢失或合并，必须通过启动时轻量检查或用户手动刷新做校验。
- 大型仓库首次索引应后台执行，显示进度，不阻断会话创建。
- 索引期间可回退到当前直接文件搜索方式。
- 多 Git Worktree 要区分基线仓库和任务工作树，不能将一个 Worktree 的未提交内容错误复用到另一个任务。
- 目录 Junction、Symlink 和 Windows Reparse Point 必须防止越出授权仓库根目录。

### 5.4 忽略规则

至少处理：

- Git 忽略规则（`.gitignore`）。
- 平台默认规则：`.git`、`node_modules`、`vendor`、`bin`、`obj`、`dist`、`build`、`.next`、缓存目录等。
- 用户自定义 exclude。
- 二进制、大文件、证书、私钥、`.env`、凭据文件。
- 不允许索引整个磁盘或工作区父目录。

## 6. Context Optimizer

### 6.1 处理流水线

```text
用户需求/Jira/附件引用
        │
        ▼
任务类型识别与验收标准抽取
        │
        ▼
Workspace Manifest + 索引检索
        │
        ▼
关联类/方法/配置/SQL/接口片段
        │
        ▼
权限检查、去重、版本校验
        │
        ▼
Token Budget 分配
        │
        ▼
生成 Context Bundle（含来源和行号）
        │
        ▼
Runtime Adapter
```

### 6.2 上下文优先级

建议默认排序：

1. 平台安全与系统规则（不可被裁剪）。
2. 用户原始需求和验收标准。
3. 当前任务与工作区 Manifest。
4. 相关项目规范、MES/WMS 字典和知识引用。
5. 与修改点高度相关的代码片段。
6. 依赖调用链和相邻代码。
7. 历史会话摘要。

预算不足时先裁剪低相关历史内容和外围代码，不得裁掉用户需求、验收要求和安全限制。

### 6.3 去重和缓存

缓存 Key 建议包含：

`workspaceId + repositoryId + worktreeId + filePath + contentHash + retrievalPolicyVersion + runtimeContextVersion`

- 相同文件片段只注入一次。
- 缓存命中前仍要校验用户对文件的访问权限。
- 文件 Hash 或策略版本变化时失效。
- 不同 Workspace 之间禁止默认共享内容缓存。
- 对模型 Prompt Cache 的支持由 Provider/Runtime Adapter 单独声明；不假设所有模型都支持。
- 记录缓存命中率和减少的读取/解析量，不得将缓存节省 Token 作为未经 Provider 证实的账单数据。

### 6.4 Token 预算

- 读取当前 Runtime/模型上下文窗口配置。
- 预留模型输出空间和工具返回空间。
- Token 计数优先使用对应模型 tokenizer；不可用时采用估算器并标记 `estimated`。
- 不在每个会话中硬编码统一 Token 上限。
- 保存上下文包统计：来源数量、文件数量、片段数量、估计/实测 Token、去重数量、裁剪数量。

## 7. Safe Parallel Scheduler

### 7.1 任务分类

```ts
export type OperationSafety =
  | "readonly"
  | "workspace_write"
  | "repository_mutation"
  | "external_side_effect";

export interface ScheduledOperation {
  id: string;
  parentTaskId: string;
  workspaceId: string;
  repositoryIds: string[];
  operation: string;
  safety: OperationSafety;
  command?: string;
  timeoutMs?: number;
  requiresApproval: boolean;
}
```

### 7.2 并发规则

- `readonly`：允许并行，需设置全局和 Workspace 并发上限。
- `workspace_write`：同一 Worktree 默认串行；不同仓库只有在路径和产物隔离经过验证后才允许并行。
- `repository_mutation`：Git branch/worktree/commit 等通过平台 Git 服务管理，按仓库加锁。
- `external_side_effect`：网络上传、生产数据库、发布等按高风险操作审批，不因并行策略自动放行。

默认并发数先从 2 或 3 开始，通过性能基线调整。必须有背压，不能因为模型一次提出大量工具调用就无限创建进程。

### 7.3 冲突避免

- 锁粒度至少包括 `workspaceId + repositoryId + worktreeId + operationClass`。
- 读写冲突时写任务等待或拒绝。
- 子任务依赖图必须无环；失败应传播到父任务状态。
- 取消时递归取消子任务，并等待进程退出；超过宽限时间后按平台进程树管理策略终止。
- 同一任务不能同时由两个 Runtime 对同一 Worktree 执行写入。

## 8. Test Orchestrator

### 8.1 测试命令注册

从现有项目配置收集命令；缺少配置时由用户/开发负责人确认，不要让模型任意猜测命令并直接执行。

建议数据结构：

```ts
export interface TestCommandDefinition {
  id: string;
  repositoryId: string;
  name: string;
  level: "smoke" | "targeted" | "unit" | "build" | "integration" | "full";
  command: string;
  workingDirectory: string;
  timeoutMs: number;
  requiresNetwork: boolean;
  requiresDatabase: boolean;
  sideEffectLevel: "none" | "local" | "external";
  enabled: boolean;
}
```

### 8.2 测试选择策略

输入：变更文件、仓库语言/项目结构、依赖关系、测试命令注册表、用户是否要求全量测试。

输出：建议测试集、选择原因、需审批项、未选择测试及原因。

首期建议规则：

- 文档/注释修改：按项目配置可跳过代码测试，但做 Markdown/格式检查（若存在）。
- 单模块代码修改：相关 targeted/unit + 必要 build。
- API/接口 DTO 修改：相关后端测试 + 前端类型/构建检查。
- 多仓库接口联动：前后端 targeted + build，必要时 integration。
- 数据库脚本/迁移：静态检查和专门验证；连接真实数据库属于独立审批。
- 用户明确要求 full：必须执行 full 或说明无法执行的具体原因。

### 8.3 证据链

每次测试记录：

- TestRun ID、Task ID、Repository ID、Commit/Worktree 状态。
- 命令、工作目录、开始/结束时间、退出码。
- stdout/stderr 脱敏摘要及日志文件位置。
- 结果：passed/failed/timed_out/cancelled/not_run/environment_missing。
- 测试层级和选择原因。

禁止：

- 用模型口头声称“测试通过”替代真实运行记录。
- 将未执行/环境缺失标记为成功。
- 未验证缓存正确性就复用过去的测试通过结果。

## 9. Provider/Runtime 配置一致性

截图中曾出现模型 Provider/模型选择与 Runtime 名称同时显示的情况。技术上两者是不同概念，必须做明确绑定校验。

- Runtime：负责 Agent Harness、工具调度、权限和会话协议。
- Provider：负责模型服务端点、协议、鉴权和模型 ID。
- Model：具体模型标识和参数。

新增 `RuntimeProviderCompatibility` 能力表或注册表，描述：

- Runtime 支持的 Provider 类型。
- 所需 API 协议（Anthropic Messages / OpenAI Responses / 其他）。
- 是否支持工具调用、流式输出、用量返回、取消。
- 是否需要 Runtime 原生二进制或独立凭据。

会话启动前校验 Runtime + Provider + Model 的兼容性。不可兼容时阻止启动并说明原因。性能分析中必须记录真实 Runtime、Provider、Model，不能从 UI 标签推断。

记录真实测试执行、命令、退出码、耗时、结果和脱敏日志引用。

### 10.7 `performance_settings`

记录全局与 Workspace 性能开关、并行上限、测试策略和配置版本。

索引建议：

- `performance_span(trace_id, started_at)`
- `performance_trace(workspace_id, started_at)`
- `workspace_file_index(workspace_id, repository_id, worktree_id, content_hash)`
- `test_run(task_id, started_at)`

## 12. UI/API 交互要求

- IPC/API 增加性能 Trace 查询、Span 时间线、索引状态、索引重建、策略设置、测试计划和测试证据查询。
- 长任务使用现有事件总线推送，不新增本地 HTTP Server。
- UI 不能直接访问数据库、文件系统或 Runtime 子进程。
- 所有路径校验和权限判断放在主进程/后端服务层。
- 性能面板支持刷新、时间线展开和复制脱敏诊断摘要。

## 13. 安全要求

- 索引和缓存必须在工作区权限校验后读取。
- 任何缓存命中都不能绕过权限控制。
- 文件 Watcher 不能越权跟随 Symlink/Junction。
- 并行执行不能扩大命令执行权限。
- 进程管理应追踪完整子进程树，处理取消和异常退出。
- 日志不保存 API Key、Cookie、Authorization、完整环境变量和隐藏推理。
- 用户选择全量测试时，平台不能为了速度擅自降级。
- 任何优化失败可回退到原有执行流程。

## 16. 测试计划

### 16.1 单元测试

- Span duration、父子关系、异常结束和中断恢复。
- 索引文件过滤、Hash/mtime 变更、忽略规则。
- 上下文去重、优先级、预算裁剪、缓存失效。
- 并发锁、队列背压、父任务取消和失败传播。
- 测试策略规则和状态映射。

### 16.2 集成测试

- 一个 Workspace 含前端/后端两个独立 Git 仓库。
- 文件变更触发增量索引。
- 两个只读检索任务同时执行。
- 同一个 Worktree 的两个写任务被串行化。
- 任务修改后只运行相关测试，再依据策略运行 build/full。
- 三种 Runtime 的性能事件均能进入相同时间线。

### 16.3 回归测试

- 关闭性能优化开关，现有任务仍可执行。
- Codex 仍为默认 Runtime。
- Jinggong、Claude Runtime 原有会话/权限/工具流程不退化。
- 插件、企业微信通知、Jira、多仓库工作区功能不受影响。

### 16.4 性能对比方法

- 同一任务、同一 Commit、同一模型参数、同一机器。
- 每任务至少 3 次，报告中位数和 P90。
- 将模型等待和本地执行分开统计。
- 任务未完成、测试未通过的快速结果不能算作性能提升。
- 任何耗时下降都必须与任务完成质量、Diff、测试结果一起判断。

## 17. Codex 实施指令

请在现有精工智能开发平台代码库中实施本方案。

### 阶段 A：只读盘点

1. 阅读配套需求方案。
2. 检查当前目录、桌面框架、数据库、Runtime Adapter 和事件系统。
3. 找到实际仓库扫描、文件读取、上下文组装、工具调度和测试执行代码。
4. 检查 Runtime 与模型 Provider 的实际配置关系，特别确认当前 UI 显示的 Runtime/Provider/Model 是否一致。
5. 用代码证据输出瓶颈清单，不要先改代码。
6. 选取真实任务采集基线。

### 阶段 B：实现公共可观测能力

1. 增加 Trace/Span 数据结构和持久化。

3. 增加执行监控 UI。

### 阶段 C：逐项优化

依次实现 Workspace Index、Context Optimizer、Safe Parallel Scheduler、Test Orchestrator。每个模块独立开关、独立测试、独立回滚。

### 阶段 D：基准对比

运行同一任务集，对照优化前后耗时、工具次数、上下文 Token、测试结果和代码质量。

### 硬性要求

- 不大规模重写现有 Runtime。
- 不新增 Grok Runtime。
- 不改变 Codex Runtime 默认值。
- 不用模拟数据替代真实运行证据。
- 不擅自删除测试、权限审批或安全限制。
- 不把未执行测试标记为通过。
