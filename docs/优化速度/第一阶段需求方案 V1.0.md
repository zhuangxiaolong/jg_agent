# 精工智能开发平台——第一阶段执行效率优化需求方案 V1.0

> 文档类型：产品需求方案  
> 产品：精工智能开发平台（Windows 桌面客户端）  
> 版本：V1.0  
> 状态：供 Codex 研发实施  
> 日期：2026-11-11  
> 适用范围：现有 Codex Runtime、Jinggong Runtime、Claude Agent SDK Runtime  
> 核心目标：先定位现有会话慢在哪里，再通过索引、上下文、并行调度、测试分级和可观测性提升任务端到端效率。

---

## 1. 背景与问题定义

当前精工智能开发平台已经具备多个 Runtime、项目/工作区、Jira 任务上下文和代码开发能力。实际开发任务中，用户反馈部分任务耗时较长，期间可能发生项目重复扫描、上下文读取过多、工具调用串行、测试命令执行时间长等情况。

现阶段不能仅凭会话界面判断慢的原因。必须通过统一的执行耗时数据区分：

1. Runtime 启动及初始化耗时。
2. 模型首个响应耗时、模型响应间隔和模型总耗时。
3. 仓库扫描、代码搜索和文件读取耗时。
4. 工具排队、工具启动和工具执行耗时。
5. 上下文组装、Token 使用量及重复注入。
6. 编译、测试和其他本地命令耗时。
7. 重试、错误恢复、重复工具调用造成的额外耗时。

本阶段采取“先测量、再优化、可对照、可回退”的原则，不以主观感受或单个模型的 Token 生成速度判断整体性能。

## 2. 产品目标

### 2.1 核心目标

- 建立跨 Runtime 的统一任务耗时监控与性能追踪。
- 降低每轮任务重复扫描整个仓库的概率和耗时。
- 减少与任务无关或重复的文件内容进入模型上下文。
- 将相互独立、无副作用的只读分析任务安全并行化。
- 根据项目配置和变更范围选择合理测试层级，避免每轮都执行不必要的全量测试。
- 保证优化前后代码正确性、测试证据和安全约束不退化。

### 2.2 目标用户

- MES/WMS 开发人员：希望减少等待时间，快速获得可执行的代码修改。
- 技术负责人：希望知道慢在模型、工具、代码搜索还是测试，并能定位具体任务。
- 平台管理员：需要调整性能策略、查看统计并在出现异常时关闭优化功能。

### 2.3 成功标准

先建立可重复的基线，再评估优化效果。建议使用不少于 10 个具有代表性的真实或脱敏任务，每个任务在相同环境、相同模型/参数、相同仓库基线下重复运行至少 3 次，比较中位数。

建议目标（属于优化目标，不得在未测试前宣称已达到）：

- 对存在重复仓库扫描/文件读取的任务，端到端中位耗时目标降低 15%–25%。
- 对可并行的只读分析阶段，阶段耗时目标接近最慢子任务耗时，而不是各子任务耗时简单相加。
- 重复执行同一工作区任务时，索引增量更新不应重新全量扫描未变化文件。
- 不降低任务验收通过率，不增加未授权文件访问、错误写入和虚假测试通过。
- 任务耗时分解完整率达到 95% 以上；数据采集失败时明确标记缺失，不补造数据。

上述数值必须通过基线测量确认合理性。若当前项目无法采集某项数据，应在报告中标注“暂不可测量”，不得虚构。

## 3. 本阶段范围

### 3.1 P0 必须实现

1. 统一性能追踪：任务、会话、Runtime、模型/Provider、工具调用、命令执行关联起来。
2. 耗时分析：Runtime 启动、首个响应、模型响应、工具等待/执行、搜索/读取、上下文组装、测试/构建、重试。
3. 工作区增量索引：文件清单、修改时间/大小/哈希、忽略规则和基础全文/符号索引（以现有技术栈和 PoC 为准）。
4. 上下文优化：按需检索、去重、分段、Token 预算和缓存。
5. 安全并行：只读且相互独立的任务可并行；写操作和同一工作树冲突操作必须串行或隔离。
6. 分级测试：目标测试、模块测试、构建测试、集成测试、全量测试，并展示选择原因。
7. 性能配置开关：按 Runtime/工作区控制，支持一键关闭优化并回退现有行为。
8. 性能报告：会话内查看执行阶段耗时，任务完成后显示总览。

### 3.2 P1（本阶段可预留接口，不要求完整交付）

- 基于历史任务数据自动推荐模型/Runtime。
- 语义向量索引和跨项目检索。
- 自动选择并动态扩缩并行 Agent 数量。
- 测试缓存和跨任务复用构建产物。
- 任务复杂度预测和动态 Token 预算。

### 3.3 明确不做

- 本阶段不新增 Grok Runtime。
- 不替换或重写 Codex、Jinggong、Claude 的 Agent Loop。
- 不改变 Codex Runtime 为全局默认 Runtime 的既有设置。
- 不自动在 Runtime 之间切换任务。
- 不为了速度减少必要的权限审批、跳过安全检查或伪造测试结果。
- 不默认把整个仓库、全部字典或所有历史会话注入模型。
- 不将隐藏推理内容作为性能日志保存。

## 4. 核心用户场景

### 场景 A：用户提交开发任务

1. 用户在已有工作区中提交任务。
2. 平台加载工作区清单和索引状态。
3. 平台根据任务内容、已变更文件、项目规则和检索结果组装上下文。
4. Runtime 执行任务。
5. 平台实时记录各阶段耗时、工具调用、测试执行和错误恢复信息。
6. 任务结束后展示耗时分析和结果摘要。

### 场景 B：多仓库前后端联合开发

1. 工作区包括前端、后端和公共组件等多个 Git 仓库。
2. 平台对各仓库独立索引和版本追踪。
3. Agent 可并行执行各仓库的只读探索与依赖分析。
4. 修改时按仓库和工作树权限控制写操作。
5. 各仓库独立显示 Diff、测试结果和耗时。

### 场景 C：重复会话

1. 用户对同一工作区提出相近任务。
2. 平台复用未过期且校验通过的索引和文件元数据。
3. 发现文件变更时只更新受影响文件及必要关联数据。
4. 上下文只加载当前任务需要的文件，不重复塞入之前会话完整内容。

### 场景 D：测试执行

1. Agent 修改文件后，平台根据项目配置、修改范围和依赖关系推荐测试层级。
2. 先执行相关的快速测试或编译检查。
3. 是否执行全量测试由项目策略、用户要求和风险等级决定。
4. 所有测试必须记录真实命令、工作目录、退出码、开始结束时间和输出摘要。
5. 未执行的测试标记为“未执行”，不得显示为“通过”。

## 5. 功能需求

### FR-001：统一任务性能追踪

- 每个执行任务生成唯一 `traceId`，并关联 `platformSessionId`、`taskId`、`workspaceId`、`runtimeKind`。
- 所有阶段事件包含开始时间、结束时间、持续时间、状态和错误分类。
- 支持任务阶段：初始化、索引检查、检索、上下文组装、模型等待/响应、工具执行、命令执行、测试、重试、收尾。
- 不同 Runtime 上报能力可能不同。不能取得的数据标为 `unavailable`，不能使用估算值冒充实测值。
- 对模型首 token 时间、模型响应时间、Token 使用量：优先使用 Runtime/Provider 原生数据；没有时显示“不可用”或带明确标识的估算值。

### FR-002：执行耗时面板

会话页面新增“执行监控/性能”区域，至少展示：

- 本次任务总耗时。
- Runtime 和模型/Provider。
- 首个可见响应耗时（可测量时）。
- 模型调用次数及累计等待时间（可测量时）。
- 工具调用次数、排队时间、累计执行时间。
- 代码搜索和文件读取次数/耗时。
- 上下文组装耗时、输入/输出 Token（如可取得）。
- 构建和测试耗时、通过/失败/未执行数量。
- 重试次数和失败恢复耗时。

支持展开查看每个阶段时间线。默认不显示模型隐藏推理或敏感工具完整参数。

### FR-003：工作区增量索引

- 工作区可单独启用/关闭索引。
- 首次扫描建立索引；之后优先增量更新。
- 监听文件变更，采用防抖和批量更新，防止构建过程中的大量临时文件导致索引风暴。
- 忽略 `.git`、依赖目录、构建输出、缓存、二进制、大文件、用户配置排除项及仓库 `.gitignore` 规则。
- 默认排除密钥文件、证书、凭据、`.env` 等敏感文件；不得将敏感文件内容写入索引。
- 支持仓库级别查看索引状态、文件数、最后更新时间、失败项。
- 索引失效时可以手动重建；重建期间允许按现有搜索方式工作，不得阻断基本开发。

### FR-004：上下文按需检索和预算

- 根据任务摘要、Jira 描述、验收标准、修改文件、仓库 Manifest 和检索结果组装上下文。
- 文件采用相关片段/行范围注入，默认不整文件注入；对小型配置文件可按策略完整注入。
- 对同一文件/片段去重，避免多个上下文来源重复注入。
- 按 Runtime/模型能力设置上下文预算；平台核心指令、用户需求、安全约束和验收标准优先级最高。
- 上下文裁剪必须保留来源、路径、行范围和仓库信息，便于 Agent 追溯。
- 缓存必须按文件哈希、索引版本和上下文策略版本校验，发现变化即失效。
- 不允许缓存用户私密内容后跨工作区或跨用户复用。

### FR-005：安全并行执行

- 允许并行的操作类型：只读文件搜索、独立仓库结构分析、独立依赖分析、只读 Git 状态查询等。
- 写文件、同一工作树 Git 操作、会修改相同构建产物的命令必须串行或使用隔离 Worktree。
- 对每个工作区设置最大并行度，默认值由 PoC 测试后确定，建议初始不超过 3。
- 每个并行任务需要任务 ID、父任务 ID、仓库 ID、只读/写入声明和超时。
- 单个子任务失败时，主任务需要显示失败原因；不得静默忽略并把整体任务标记成功。
- 用户取消主任务时，应取消可取消的子任务并清理临时资源。

### FR-006：分级测试策略

测试层级：

1. `smoke`：基本启动/关键路径快速检查。
2. `targeted`：与变更文件/模块直接相关的测试。
3. `unit`：模块单元测试。
4. `build`：相关项目编译/构建。
5. `integration`：跨模块/跨仓库集成测试。
6. `full`：全量测试。

要求：
- 优先读取仓库中已配置的测试命令，不自行猜测并直接执行高风险命令。
- 通过项目 Manifest 登记命令、目录、耗时等级、是否需要网络/数据库、是否有副作用。
- Agent 可提出测试建议，平台策略引擎决定允许自动执行、需要审批或禁止。
- 对前后端多仓库任务，分别记录各仓库测试结果，并记录跨仓库测试。
- 若测试未执行、超时或环境缺失，必须如实展示。
- 由用户明确要求全量测试时，不得仅因耗时而自动跳过。

### FR-007：性能策略配置

- 全局性能功能总开关。
- 工作区索引开关。
- 上下文裁剪/缓存开关。
- 安全并行开关和最大并行数。
- 测试分级策略：自动建议/执行快速测试/执行全量测试需审批。
- 日志保留周期和诊断数据导出。
- 配置修改必须记录时间和配置版本。
- 一键恢复默认设置。

### FR-008：性能基线与对比

- 支持选择任务记录作为基线样本。
- 对同类任务按 Runtime、模型、工作区和任务类型分组。
- 对比任务耗时中位数、模型等待、工具时间、搜索时间、测试时间和完成情况。
- 样本不足时显示“样本不足”，不得给出确定性排名。
- 不把不同模型、不同代码版本、不同任务复杂度的数据直接作公平对比。

### FR-009：Runtime 和模型配置一致性检查

- Runtime 是 Agent 执行框架；模型 Provider/模型 ID 是模型服务配置，二者必须分别管理。
- 启动会话前检查所选 Runtime 是否支持当前 Provider、模型 ID、工具调用和流式协议。
- 例如 Claude Runtime 不得仅因为模型下拉框可选就默认兼容任意 OpenAI-compatible 模型。
- 不兼容时阻断启动并给出明确原因，不能静默回退或错误标注。
- 性能面板必须同时显示 Runtime、Provider、模型 ID、Base URL 标识（脱敏）。

## 6. 交互与界面要求

### 6.1 会话内性能入口

在现有 Jira/子 Agent/代码变更/Git/上下文等侧栏区域新增“执行监控”入口，避免挤占主对话空间。

### 6.2 任务完成摘要

任务结束时展示：

- 执行结果：成功/部分成功/失败/已取消。
- 总耗时和各阶段占比。
- 修改仓库及文件数量。
- 测试通过、失败、未执行数量。
- 性能诊断结论（仅根据实测证据）。
- 如存在性能异常，给出明确阶段，不擅自断言模型能力不足。

### 6.3 执行状态

区分：排队中、索引中、检索中、等待模型、模型响应中、工具执行中、测试中、等待审批、已完成、失败、已取消。

不得仅用“Agent 正在处理”覆盖全部阶段。

## 7. 数据与隐私要求

- 性能事件存本地数据库。
- 不记录隐藏推理、API Key、Authorization Header、完整环境变量或敏感文件正文。
- 工具参数只保存脱敏摘要和必要元数据。
- 索引数据按工作区隔离。
- 日志支持清理和导出；导出前执行脱敏。
- 默认保留周期建议 30 天，可配置；索引数据保留到用户移除工作区或清理索引。

## 8. 验收标准

### AT-001 可观测性

- 能查看一条任务从启动到结束的阶段时间线。
- 时间线阶段能对应真实执行事件。
- 不支持采集的指标明确显示不可用。

### AT-002 增量索引

- 首次扫描后修改单个文件，再次执行任务只更新相关索引项。
- 未变化文件不重复做全文内容解析。
- `.git`、`node_modules`、`bin`、`obj`、`dist` 等目录按规则被排除（以项目实际配置为准）。
- 敏感文件内容不会进入索引。

### AT-003 上下文优化

- 相同片段不重复注入。
- 可查看本次上下文来源和大小统计。
- 超预算时按优先级裁剪并显示被裁剪类别，不得删除用户验收标准和系统安全要求。

### AT-004 并行执行

- 两个独立只读仓库分析任务可并行。
- 同一工作树的冲突写操作不并行。
- 取消主任务后子任务得到终止或明确标记无法取消。

### AT-005 测试策略

- 相关测试先于全量测试执行。
- 测试命令、退出码、日志摘要、耗时可追溯。
- 未执行的全量测试不显示为通过。

### AT-006 回归与回退

- 关闭所有性能优化开关后，核心开发流程仍可按旧路径执行。
- 不破坏 Codex Runtime 默认选择及现有 Jinggong/Claude Runtime。
- 性能优化不降低安全审批要求。

## 9. 实施顺序

1. 现状盘点与性能基线采集。
2. 统一事件模型及性能面板。
3. 工作区增量索引。
4. 上下文检索、裁剪和缓存。
5. 安全并行调度。
6. 分级测试策略。
7. 对照测试、回归和开关回退。

## 10. 待 Codex 盘点确认

以下内容不得根据本文档猜测：

- 当前桌面框架和本地数据库类型。
- 三个 Runtime 实际调用链及可采集事件。
- 多仓库 Workspace/Repository 数据模型。
- 当前文件搜索和上下文组装实现。
- 当前测试命令配置及测试执行服务。
- 当前是否已有文件监听、索引或缓存机制。
- 当前 Modelflare/其他 Provider 与不同 Runtime 的实际协议兼容矩阵。

Codex 必须先提供代码证据和差距清单，再进行实现。
