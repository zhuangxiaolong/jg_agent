## 1. 产品概述

### 1.1 产品背景

目前 MES5、MES6、WMS 等系统的研发工作涉及 Jira 需求查询、需求附件阅读、代码定位、生产字典查询、开发规范确认、代码修改和测试验证等多个环节。相关信息分散在 Jira、Git 仓库、Excel 数据字典、项目文档及开发人员经验中，研发人员需要重复查找资料、理解历史代码和确认业务规则。

精工 Agent 计划建设一个可在 Windows 上直接安装和运行的 AI 研发桌面客户端，把 Jira 任务、代码仓库、企业知识、开发规则、模型服务和开发过程记录整合到一个桌面应用中，让开发人员从 Jira 任务直接进入 AI 辅助开发流程。首期数据和运行时均以本机为中心，不依赖公司自建应用服务器。

### 1.2 产品定位

精工 Agent 是一个**安装在 Windows 电脑上的桌面开发 Agent**，产品体验参考 Codex 桌面应用，不是要求用户通过浏览器访问的 Web 平台，也不是首期就全自动提交和发布代码的无人值守系统。

桌面客户端通过本机 IPC 调用受控主进程和 Agent Runtime，直接访问用户授权的 Jira、Git、模型中转站及本地知识库，提供：

1. Jira 任务及附件获取；
2. MES5、MES6、WMS 生产字典和研发知识检索；
3. 项目级及系统级开发规范约束；
4. 代码分析、修改、测试和变更审核；
5. 多中转站、多模型管理和会话级选择；
6. 会话记忆、项目记忆和知识资产管理；
7. Agent 执行过程、权限、成本和审计管理。

### 1.2.1 产品交付形态与运行边界（V1.1 强制要求）

| 项目 | V1.1 要求 | 明确不采用的方式 |
|---|---|---|
| 产品形态 | Windows 桌面应用，提供 `JinggongAgent-Setup.exe` 或 MSI 安装包 | 不交付需要用户自行启动的 Web 服务 |
| 使用入口 | 桌面快捷方式/开始菜单，双击启动应用窗口 | 不要求用户打开浏览器输入 localhost 地址 |
| 应用架构 | 桌面 UI + 本机主进程 + Agent 子进程 | 不建设独立后端服务器、不开放本地 HTTP API 端口 |
| 数据存储 | 本地 SQLite + 本地文件目录 | 首期不要求 PostgreSQL、Redis、MinIO、Docker |
| 代码执行 | 本机隔离工作区/Git Worktree + Agent Runtime 权限与审批 | 不要求 Kubernetes 或远端执行集群 |
| 外部连接 | 客户端主动出站连接 Jira、Git 和模型中转站 | 不接受外部系统主动连接本机监听端口 |
| 用户模型 | V1.1 以单机单 Windows 用户为主，使用本地配置和权限边界 | 首期不建设公司统一用户中心、SSO 和多人在线协作 |
| 数据同步 | 本地备份/导入导出；企业知识包可由管理员分发 | 首期不建设跨电脑实时同步服务 |

**重要说明：** Electron/Tauri 这类桌面应用可能使用内嵌 WebView 绘制界面，但这不等于 Web 部署。最终用户只安装和启动 Windows 程序，不需要浏览器、Node.js、Python、Docker 或数据库服务。

### 1.2.2 首版单机运行范围

- 会话、任务快照、模型配置元数据、记忆和审计记录保存在本机。
- Jira/Git/模型凭据通过 Windows 凭据保护机制加密保存，应用不得明文写入配置文件或日志。
- 首期一台电脑可运行多个 Agent 会话，但并发数受本机 CPU、内存和模型限额控制。
- 用户可从设置中备份/恢复应用数据，后续可迁移至另一台 Windows 电脑。
- 企业共享知识库、组织账号、集中策略下发和团队审计属于后续企业版能力。

### 1.3 产品目标

| 目标编号 | 产品目标 | 衡量方式 | 目标值/口径 |
|---|---|---|---|
| OBJ-01 | 降低开发人员从接收任务到理解需求的时间 | Jira 任务准备耗时 | 试点后较试点前基线下降，具体目标在试点基线采集后确定 |
| OBJ-02 | 降低查找 MES/WMS 表结构和业务规则的时间 | 字典查询耗时、检索命中率 | 建立标准测试集后测量；精确表名/字段名问题优先保证准确性 |
| OBJ-03 | 提高代码修改的可审查性 | Diff 覆盖率、构建/测试结果完整率 | 所有开发模式任务均产生变更摘要；有代码修改时必须生成 Diff |
| OBJ-04 | 提高研发规范执行率 | 自动规则拦截数、规则通过率 | 首期至少落地 10 条可自动检查的硬规则 |
| OBJ-05 | 提升测试准备效率 | 测试用例生成覆盖率、可执行率 | 按需求验收点建立覆盖检查，生成与执行结果分开记录 |
| OBJ-06 | 形成可复用的公司研发知识资产 | 已审核字典、规则包和项目记忆数量 | 按 MES5、MES6、WMS 分系统统计 |
| OBJ-07 | 降低模型使用和数据访问风险 | 调用审计覆盖率、越权事件数 | 关键调用全量记录；权限隔离测试必须通过 |

> **指标原则：** 不以 Agent 对话次数、生成代码行数作为核心价值指标。效率提升目标需先建立当前人工流程基线，再通过试点项目验证。

### 1.4 非目标（首期不做）

- 不建设独立 Web 后端服务、应用服务器、Docker Compose 数据库栈或 Kubernetes 集群。
- 不要求最终用户安装和维护 PostgreSQL、Redis、Python、Node.js 等开发运行环境。
- 不实现跨电脑实时会话同步、组织级 SSO、集中账号中心和服务器端多租户。
- 不开放本机 HTTP/WebSocket 监听端口供浏览器或其他电脑访问。

- 不从零开发通用代码大模型或完整 Agent 执行引擎。
- 不自动向 Git 主分支提交、合并或发布生产版本。
- 不自动修改 Jira 任务状态、负责人、评论或工作日志；后续如需写回，必须另行定义审批权限。
- 不直接连接生产数据库执行写操作，不自动执行生产变更。
- 不把未经审核的历史文档视为权威生产字典。
- 不允许普通用户自行添加未审核的公网模型服务地址或查看其他团队的密钥。
- 不承诺任何模型生成的代码天然正确；代码结果必须经过规则检查、测试和人工审核。

### 1.5 首期范围与优先级

优先级定义：P0 = MVP 必须具备；P1 = MVP 后优先增强；P2 = 后续版本规划。

| 模块 | P0：MVP 必须 | P1：增强 | P2：后续规划 |
|---|---|---|---|
| 本地用户与权限 | 首次启动建立本地用户配置；Windows 当前用户绑定；本机管理员设置 | 多人共用电脑的本地配置隔离、企业策略包 | 公司账号中心、SSO、组织级多租户 |
| Jira | 按日报日期字段查询任务、任务详情、附件导入 | 评论/历史信息、任务筛选条件、只读缓存 | 经审批的 Jira 状态回写/评论 |
| Git/代码 | 仓库登记与选择、分支选择、隔离工作区、Diff | 创建 Pull/Merge Request、更多 Git 服务适配 | 自动化合并（需单独风险评审） |
| Agent 会话 | 新建/恢复会话、流式过程、工具审批 | 多 Agent 协作、任务模板 | 跨项目自动任务编排 |
| 知识库 | MES5/MES6/WMS 字典导入、结构化查询、来源追溯 | 业务文档/代码知识检索、定期同步 | 自动知识治理与影响分析 |
| 规范与测试 | 规则包、至少 10 条自动检查、测试用例生成 | CI 门禁、测试报告模板、规则版本发布 | 质量度量与缺陷闭环分析 |
| 模型管理 | 管理员配置中转站/模型、会话选择、调用日志 | 预算、限额、模型能力评分、故障切换 | 成本优化路由和模型自动选择 |
| 记忆 | 会话历史、会话恢复、项目记忆基础能力 | 记忆审核、纠错、过期和归档策略 | 跨项目知识推荐（需权限控制） |
| 审计安全 | Windows 本地凭据保护、任务工作区隔离、操作留痕 | 风险扫描、本地审计导出、异常告警 | 企业集中审计与安全运营集成 |

## 2. 用户角色与权限

### 2.1 用户角色（V1.1 单机版）

V1.1 不依赖远端用户中心。默认使用 Windows 当前登录用户作为本地操作身份，首次启动建立本地配置档案。

| 本地角色 | 主要职责 | 主要权限 |
|---|---|---|
| 本机使用者（Developer） | 选择 Jira 任务、发起分析/开发、查看代码和测试结果 | 使用已授权 Jira/Git/模型连接；创建个人会话；在指定工作区开发；使用授权知识库 |
| 本机管理员（Local Admin） | 管理本机连接、模型、知识包、规则包和安全设置 | 配置凭据、允许的模型/仓库、工作区边界、执行策略、备份与恢复 |
| 知识维护者（Knowledge Maintainer） | 维护本机 MES5/MES6/WMS 字典和规则 | 导入、审核、发布、废弃本机知识版本；查看导入日志 |

V1.1 的角色主要用于本机功能授权，不代表远端账号体系。若后续需要多人在不同电脑共享项目会话或统一管理权限，另行建设企业版服务端。

### 2.2 权限原则

1. 默认拒绝：未明确授权的 Jira 项目、代码仓库、知识空间和模型不可见、不可调用。
2. 最小权限：Jira/Git 使用专用服务账号或用户授权令牌；Agent 每个任务只获得所选工作区和必要权限。
3. 密钥隔离：API Key、PAT 等通过 Windows Credential Manager 或经安全评审的 DPAPI 加密方案保存；主进程负责访问，渲染界面只获取脱敏状态。
4. 本机数据隔离：数据库、附件、记忆和工作区存放在当前 Windows 用户数据目录，不允许其他普通 Windows 用户读取。
5. 高风险操作审批：删除、网络访问、依赖安装、数据库变更、Git 推送等动作按策略要求审批。
6. 审计记录本机追加写入，提供导出能力；普通会话不能直接编辑历史记录。

### 2.3 本机功能权限矩阵（首期建议）

| 功能 | 本机使用者 | 本机管理员 | 知识维护者 |
|---|---:|---:|---:|
| 使用 Agent 会话 | √ | √ | 按需 |
| 配置 Jira/Git 连接 | 使用已授权连接 | √ | — |
| 添加/禁用模型 Provider | 使用已启用模型 | √ | — |
| 导入/发布生产字典 | — | √ | √ |
| 编辑开发规范 | 使用已发布规则 | √ | 按授权 |
| 调整执行审批策略 | — | √ | — |
| 导出本机审计记录 | 本人记录 | √ | 知识导入记录 |
| 查看密钥明文 | — | 不提供明文查看 | — |

该矩阵控制当前 Windows 用户的本地应用功能。它不是服务器端 RBAC；Windows 文件系统 ACL 和凭据隔离是本机数据隔离的基础。

## 3. 核心业务流程

### 3.1 Jira 任务驱动开发主流程

```text
启动精工 Agent 桌面应用（首次启动完成本地初始化）
    ↓
选择 Jira 项目（默认 NEWDEVGROUP）和日报日期（默认当天）
    ↓
查询 cf[11116] 对应日期的 Jira 任务
    ↓
浏览任务列表并选择一个任务
    ↓
加载概要、描述、验收要求、附件及来源信息
    ↓
选择代码项目/仓库、目标分支和开发模式
    ↓
选择模型中转站及模型
    ↓
创建独立 Agent 会话和隔离代码工作区
    ↓
Agent 检索项目规范、生产字典和相关代码
    ↓
分析方案 / 代码开发 / 测试用例生成与执行
    ↓
展示 Diff、测试结果、知识引用和未解决风险
    ↓
人工审核并决定是否导出补丁或创建代码评审请求
```

### 3.2 Jira 查询流程

1. 用户进入 Jira 任务面板。
2. 系统默认加载当前日期；用户可以选择历史日期。
3. 平台按 Jira 项目 Key、日报日期字段 `cf[11116]` 生成 JQL。
4. 查询结果分页加载，显示任务概要信息。
5. 用户可按任务 Key、概要关键词、状态、负责人等进行前端筛选（实际支持字段以 Jira 返回为准）。
6. 用户打开任务详情，检查描述和附件。
7. 用户点击“基于此任务创建会话”，进入会话工作区。

**查询边界：** 日期应使用 Jira 实例配置时区；如果字段类型为 Date Time，则按当天 00:00:00 至次日 00:00:00 的左闭右开范围查询。字段类型、字段名称、时区和实际 JQL 语法需在 PoC 阶段核验。

### 3.3 代码开发流程

1. 用户选择已登记的仓库、分支和开发模式。
2. 系统检查用户是否有该仓库的读取/写入权限。
3. 系统创建独立工作区，不直接使用主分支工作目录。
4. Agent 读取任务上下文、项目规则和必要知识。
5. Agent 先给出开发计划；对于配置为“先计划后执行”的项目，等待用户确认。
6. Agent 根据授权进行文件读取、修改和命令执行。
7. 系统记录变更文件、Diff、命令、测试结果和审批记录。
8. 用户审查结果；需要推送或创建 PR/MR 时执行二次授权流程。
9. 会话与工作区按保留策略存档或清理。

### 3.4 知识库发布流程

```text
知识管理员上传资料
    ↓
文件安全检查和格式识别
    ↓
解析结构化字典 / 文档文本 / 代码片段
    ↓
检查重复、字段缺失、版本冲突和解析错误
    ↓
知识管理员预览并确认
    ↓
发布为指定系统/版本/模块的有效知识
    ↓
Agent 检索时返回内容及来源版本
```

### 3.5 模型选择流程

1. 平台管理员添加中转站，配置协议、Base URL 和密钥引用。
2. 管理员添加或同步模型，完成连通性及 Agent 能力测试。
3. 管理员设置模型可用范围、预算和启停状态。
4. 用户创建会话时，从有权使用的模型列表中选择中转站和模型。
5. 会话默认固定所选模型；如需切换，用户应明确操作，系统记录切换前后的模型。
6. 每次调用记录实际 provider/model、Token 或供应商返回用量、耗时、结果状态和费用（费用数据以网关/供应商可获得数据为准）。

## 4. 功能需求

### 4.1 Windows 桌面启动与基础工作台

| 需求编号 | 需求描述 | 优先级 | 验收标准 |
|---|---|---:|---|
| DESKTOP-001 | 用户通过 Windows 安装包安装应用，从桌面/开始菜单启动 | P0 | 安装后无需打开浏览器或命令行即可启动主窗口 |
| DESKTOP-002 | 首次启动创建本地配置档案并绑定当前 Windows 用户 | P0 | 不依赖公司账号服务器；不同 Windows 用户的数据目录相互隔离 |
| DESKTOP-003 | 启动时检查 Agent Runtime、Git 和本地数据库状态 | P0 | 缺少依赖时显示修复向导，不静默失败 |
| DESKTOP-004 | 所有应用数据保存在当前用户本地数据目录 | P0 | 可定位数据目录；卸载时提供保留/清除用户数据选项 |
| DESKTOP-005 | 主窗口关闭时正确处理正在运行的 Agent 子进程 | P0 | 退出前提示运行中的任务，不无提示丢失任务或遗留孤儿进程 |
| AUTH-001 | 使用 Windows 当前用户作为默认本地身份；可选启用本地应用锁 | P0 | 首次启动自动建档；应用重启后能恢复本地会话 |
| AUTH-002 | 按本机角色控制设置、知识发布和执行审批功能 | P0 | 未授权操作无法通过 UI 或 IPC 绕过 |
| HOME-001 | 首页展示最近会话、最近任务、执行状态和失败提醒 | P1 | 用户能从首页恢复最近会话或进入任务详情 |
| HOME-002 | 展示本机模型用量和近期 Agent 执行记录 | P1 | 展示内容与本地审计/用量记录一致；无数据时显示空状态 |

### 4.2 Jira 集成

#### 4.2.1 Jira 连接配置

| 需求编号 | 需求描述 | 优先级 | 验收标准 |
|---|---|---:|---|
| JIRA-001 | 管理员配置 Jira Base URL、项目 Key、认证方式和凭据引用 | P0 | 配置保存后可进行连接测试；密钥不回显明文 |
| JIRA-002 | 支持 Jira 连接启停和健康检查 | P0 | 连接异常时显示可读错误及最近检测时间 |
| JIRA-003 | 支持配置日报日期字段，首期默认 `cf[11116]` | P0 | 字段可配置，不在代码中散落硬编码；可检测字段元数据 |
| JIRA-004 | 管理员可配置 Jira 实例时区 | P0 | 查询日期边界按指定时区计算 |

#### 4.2.2 日报任务查询与选择

| 需求编号 | 需求描述 | 优先级 | 验收标准 |
|---|---|---:|---|
| GIT-001 | 管理员登记 Git 仓库地址、名称、所属系统、默认分支和凭据引用 | P0 | 仓库连接测试成功后才允许启用 |

| GIT-005 | 支持代码只读分析模式 | P0 | 分析模式下写文件工具不可用或被拒绝 |
| GIT-006 | 支持代码开发模式，允许在隔离工作区修改代码 | P0 | 修改仅发生在任务工作区，能追溯任务和会话 |

| GIT-009 | 支持执行项目构建、静态检查和测试命令 | P0 | 命令来自仓库项目配置或管理员批准模板，不任意执行生产脚本 |
| GIT-010 | Agent 不得自动向主分支推送/合并/发布 | P0 | 通过权限和 Git 分支保护实现，不只依赖提示词 |
| GIT-011 | 用户可导出 Diff/补丁包 | P1 | 导出内容与工作区最终差异一致 |
| GIT-012 | 支持创建 Pull Request / Merge Request | P1 | 经用户确认后创建；默认不自动合并 |
| GIT-013 | 支持工作区超时清理、保留和恢复 | P0 | 清理前遵循保留策略；用户可查看清理状态 |

**代码执行模式：**

- `ANALYZE`：只读分析，不允许改代码。
- `PLAN`：读取代码并输出实施计划，不执行修改。
- `DEVELOP`：在隔离工作区内修改代码。
- `FIX`：针对错误日志、测试失败或明确问题执行定位修复。
- `TEST`：生成/补充测试并执行批准的测试命令。

用户每次启动任务时必须明确选择模式；首次进入某个仓库时可采用 `PLAN` 作为默认模式。

### 5.1 页面清单

| 页面编号 | 页面名称 | 主要区域 | 关键操作 |
|---|---|---|---|
| UI-01 | 工作台首页 | 最近会话、Jira 任务入口、执行状态、模型用量 | 新建任务会话、恢复会话 |
| UI-02 | Jira 任务面板 | 日期、项目、任务列表、详情、附件 | 查询、筛选、选择任务、创建会话 |
| UI-03 | Agent 工作区 | 对话区、执行过程、任务上下文、模型选择、审批区 | 分析、开发、暂停、取消、审批 |
| UI-04 | 代码变更页面 | 仓库/分支、变更文件、Diff、命令记录、测试结果 | 查看 Diff、运行检查、导出补丁 |
| UI-05 | 知识库管理 | 系统/版本/模块、上传记录、解析预览、审核发布 | 上传、预览、发布、废弃、回滚 |
| UI-06 | 规范与测试管理 | 规则包、规则明细、分级、测试模板 | 编辑、测试、发布规则包 |

### 5.2 Jira 任务面板交互

页面建议分为左右两栏：

- 左侧：日期选择、项目选择、搜索条件、任务列表。
- 右侧：当前选中任务的概要、描述、验收标准、附件列表和 Jira 原始链接。
- 底部主操作：`基于此任务创建会话`。

任务列表需支持加载状态、空结果、权限错误、网络错误和分页状态。日期切换后清空旧任务选中状态，避免将旧任务误关联到新日期。

### 5.3 Agent 工作区交互

工作区建议采用三栏或可折叠布局：

1. **任务上下文栏：** Jira Key、概要、附件、仓库、分支、知识空间、规则包。
2. **会话主区域：** 用户与 Agent 对话、计划、分析、代码说明和最终总结。
3. **执行状态栏/侧栏：** 当前模型、运行状态、工具调用、审批请求、文件变更和测试结果。

关键状态需使用明确文案，禁止仅用颜色区分。执行审批时，必须展示具体动作、命令/目标资源、执行理由、潜在影响和批准/拒绝操作。

### 5.4 代码 Diff 页面

至少提供：

- 文件列表及新增/修改/删除状态；
- 行级 Diff；
- Agent 变更摘要；
- 变更关联 Jira 任务；
- 规则检查结果；
- 构建及测试结果；
- 未解决风险和未执行项；
- 导出补丁/创建 PR 的入口（按版本启用）。

## 6. 数据与接口需求

### 6.0 本地数据与进程通信架构

- 主业务数据默认使用 SQLite 单文件数据库，数据库迁移由应用随版本升级执行；首期不要求 PostgreSQL 服务。
- 结构化 MES/WMS 字典采用 SQLite 索引表；非结构化资料先使用全文检索，向量检索作为后续可选能力。
- 附件、解析结果、Diff、日志和知识原文件存放在 `%LOCALAPPDATA%\JinggongAgent\` 下的受控子目录。
- UI 渲染进程只能通过白名单 IPC 调用主进程；不允许 Renderer 直接访问 Node 文件系统、凭据、Shell 或数据库。
- 主进程管理 Jira/Git Connector、SQLite、凭据读取、Agent Runtime 子进程及更新器。
- 应用不启动 localhost HTTP API，也不要求 Docker Desktop。

### 6.2 外部接口与本机 IPC

| 接口对象 | 主要用途 | 接口约束 |
|---|---|---|
| Jira REST API | 查询 Issue、字段、附件、链接 | 以实例实际版本 API 为准；支持分页；请求超时和限流处理 |
| Git 服务 | Clone、Fetch、读取分支、创建工作分支、获取 Diff | 使用最小权限凭据；不将密钥写入 Agent 可读日志 |
| Agent Runtime | 启动/恢复会话、传入上下文、接收流式事件、审批工具操作 | 桌面主进程通过本机子进程 stdio/受控 IPC 调用，不暴露监听端口；Runtime 通过适配层封装 |
| Model Gateway | 统一调用不同中转站和模型 | 用户端不直接访问上游密钥；记录真实模型标识 |
| 文档解析模块 | 提取 PDF/Office/CSV/代码文本和结构化字段 | 本机受限进程/库解析；限制大小、页数、压缩包解压深度 |
| 知识检索服务 | 字典精确检索、文档语义检索 | 先做权限过滤，再把检索结果交给模型 |
| 代码检查/测试服务 | Lint、构建、单测、安全扫描 | 只执行已批准命令模板或受控命令策略 |

### 6.3 Jira 查询接口逻辑（需求级）

建议的查询条件：

```text
project = <configured_project_key>
AND cf[11116] = "<selected_date>"
ORDER BY updated DESC
```

以上仅为 Jira 字段类型为 Date 时的查询示例。若字段为 Date Time，则必须改为对应的时间范围查询，并按 Jira 实例时区计算；字段类型和 JQL 运算符必须以现场验证结果为准。

桌面连接器需要：

- 对 Jira 项目、日期字段、时区和分页参数做配置化管理；
- 对 JQL 参数进行安全构造，避免字符串拼接造成查询错误；
- 返回任务列表同时保留 Jira Issue Key 和原始链接；
- 处理 401/403、404、429、5xx、超时和分页异常；
- 对短时间重复查询做适度缓存，缓存时间由管理员配置；
- 不在普通日志中记录认证头、密码和完整 Token。

## 7. 非功能需求（NFR）

### 7.1 安全

| 编号 | 要求 | 验收方式 |
|---|---|---|
| NFR-SEC-01 | Jira/Git/模型密钥必须通过 Windows Credential Manager 或 DPAPI 等本机安全存储保护 | 扫描前端构建产物、代码库和日志，不得出现明文凭据 |
| NFR-SEC-02 | 应用不得启动可被局域网访问的 HTTP/WebSocket 服务；对外连接使用 HTTPS/TLS | 检查监听端口和网络抓包，确认仅主动出站连接 |
| NFR-SEC-03 | Agent 在任务级 Git Worktree/独立工作区中执行，并使用 Windows 原生沙箱/权限审批能力（若 Runtime 支持） | 审核可写路径、子进程权限及越界测试 |
| NFR-SEC-04 | 默认禁止 Agent 访问生产网段和任意公网；网络白名单由管理员配置 | 网络隔离测试 |
| NFR-SEC-05 | 附件及 Jira 描述按不可信输入处理，防范提示注入 | 注入测试不应导致系统规则覆盖或未授权工具操作 |
| NFR-SEC-06 | 本机功能、仓库、知识库和模型均执行本地权限校验 | 越权访问测试通过 |
| NFR-SEC-07 | 高风险操作审批，批准结果与执行对象绑定 | 未批准操作不能执行；审批后不能篡改执行目标 |
| NFR-SEC-08 | 审计日志脱敏且具备访问控制 | 密钥扫描、审计权限测试通过 |

### 7.2 性能与容量（建议初始目标，PoC 后校准）

| 编号 | 指标 | 建议目标 |
|---|---|---|
| NFR-PERF-01 | 桌面页面交互响应时间 | 本机普通操作 P95 ≤ 200ms；本地列表查询 P95 ≤ 1 秒（不含第三方接口耗时） |
| NFR-PERF-02 | Jira 任务查询响应 | 在 Jira 正常且单页数据量内，P95 ≤ 8 秒；超过时显示加载和分页状态 |
| NFR-PERF-03 | Agent 首个流式响应 | 目标 P95 ≤ 10 秒；受所选模型/中转站影响，单独统计 |
| NFR-PERF-04 | 附件解析 | 支持异步处理；用户可离开页面，完成后状态可查询 |
| NFR-PERF-05 | 并发 Agent 数 | MVP 默认 1–2 个并发任务，管理员可根据本机 CPU/内存调高，需有排队与资源提示 |
| NFR-PERF-06 | 执行资源 | CPU、内存、运行时长和磁盘配额均可配置 |

### 7.3 可用性与稳定性

- Agent Runtime 中断后不得把任务标记为成功；应显示中断原因或未知状态。
- Jira、Git、模型中转站故障应分别显示，不应统一显示为“系统异常”。
- 模型超时、限流和网络中断应有超时、重试和取消策略，避免重复执行写操作。
- 代码执行和测试命令应记录退出码、日志及环境版本。
- 工作区和附件存储应有本地备份/清理策略；备份恢复应有完整性校验和恢复演练。

### 7.4 可维护性与扩展性

- Jira、Git、Agent Runtime 和 Model Gateway 均通过适配层接入，避免业务逻辑绑定单一厂商。
- 系统/项目规则通过版本化配置维护，不将大量业务约束硬编码在桌面主进程。
- SQLite 数据结构、IPC 消息和 Runtime 事件应有版本管理。
- 支持增加其他业务系统、代码仓库和模型提供方，不影响已有会话追溯。

### 7.5 可观测性

至少监控：Jira 连接成功率、任务查询失败率、附件解析成功率、Agent 任务成功/失败率、模型调用延迟和失败率、平均 Token/费用、工作区资源占用、规则阻断次数、测试通过率。

## 8. 关键业务规则

| 规则编号 | 规则内容 |
|---|---|
| BR-001 | Jira 日报日期默认当天，日期按 Jira 实例时区解释。 |
| BR-002 | Jira 查询必须以管理员配置的项目 Key 和日期字段为准；首期默认项目 `NEWDEVGROUP`、字段 `cf[11116]`，上线前需核验。 |
| BR-003 | 一个 Agent 会话必须记录创建时的 Jira 任务快照、仓库、分支、模型和规则包版本。 |
| BR-004 | 开发模式必须使用隔离工作区；不得直接修改主分支。 |
| BR-005 | 分析模式为只读模式，不允许写文件和执行具有写副作用的命令。 |
| BR-006 | 生产字典按 MES5/MES6/WMS、版本、模块和数据库类型隔离。 |
| BR-007 | 未审核的知识源不得作为正式生产字典的权威依据；可按策略作为“待核实参考”展示。 |
| BR-008 | 规则分为阻断、警告、提示；阻断级检查未通过时，不得进入可交付状态。 |
| BR-009 | 测试生成、测试执行、测试通过和业务验收覆盖是不同状态。 |
| BR-010 | 每次模型调用记录用户、会话、模型、时间、状态和可获取的用量信息。 |
| BR-011 | Agent 不得读取或输出未授权的其他项目记忆、代码、附件或密钥。 |
| BR-012 | Jira 描述、评论、附件和仓库文档均视为不可信业务输入，不能覆盖平台系统指令。 |
| BR-013 | 密钥仅保存为 Secret 引用；任何界面和日志均不得明文回显。 |
| BR-014 | 需要推送代码、创建 PR/MR 或执行高风险命令时，按配置触发人工审批。 |

## 9. MVP 验收标准与测试场景

### 9.1 MVP 总体验收

| 验收项 | 验收要求 |
|---|---|
| Jira 查询 | 选取至少 10 个工作日，与 Jira 页面人工筛选结果核对；任务无漏查、无跨日期误查，分页完整 |
| Jira 附件 | 对已声明支持的格式进行样本测试；解析成功率目标 ≥95%，失败需有原因和文件定位 |
| 任务上下文 | 会话中能查看 Jira Key、概要、描述、附件清单、原始链接和数据获取时间 |
| 代码仓库 | 至少接入 3 个代表性仓库，建议覆盖 MES5、MES6、WMS 各一个（以实际仓库可用性为准） |
| 隔离开发 | 完成至少 5 个样例开发任务，变更仅出现在隔离工作区，不影响主分支 |
| Diff | 所有文件变更可查看，能显示新增、修改、删除及最终差异 |
| 测试 | 执行结果准确区分通过、失败、未执行、环境受阻和仅生成未验证 |
| 字典知识 | 建立 MES5/MES6/WMS 样本字典测试集，精确查询能定位系统、版本、表和字段来源 |
| 规范 | 至少 10 条可自动执行的硬规则，验证违规样例可被阻断或警告 |
| 模型切换 | 至少配置 2 个可用模型（可来自同一或不同中转站）；切换后实际调用及日志一致 |
| 记忆 | 会话可以恢复；项目记忆和知识库有明确来源及权限范围 |
| 安全 | 密钥不进入前端或普通日志；越权访问、提示注入和未审批高风险操作测试通过 |

### 9.2 关键测试用例

| 用例编号 | 场景 | 操作 | 预期结果 |
|---|---|---|---|
| TC-JIRA-001 | 查询当天任务 | 默认日期进入 Jira 面板 | 默认日期与 Jira 时区当天一致，返回任务列表 |
| TC-JIRA-002 | 查询历史日期 | 选择过去某工作日 | 仅返回该日期匹配任务，列表与 Jira 核对一致 |
| TC-JIRA-003 | 日期边界 | 测试当天零点、当天末尾及次日零点任务 | 不跨日期误查；Date/Date Time 查询逻辑正确 |
| TC-JIRA-004 | 无匹配任务 | 选择没有任务的日期 | 显示空结果，不显示上一次查询内容 |
| TC-JIRA-005 | Jira 无权限 | 使用无项目权限用户查询 | 返回权限错误，不暴露其他任务内容 |
| TC-JIRA-006 | 附件解析失败 | 上传加密/损坏/不支持格式附件 | 显示失败原因，不把未解析文件标记为成功 |
| TC-GIT-001 | 只读分析 | 选择 ANALYZE 并要求 Agent 修改文件 | 系统拒绝写操作并提示当前为只读模式 |
| TC-GIT-002 | 隔离开发 | 选择 DEVELOP 修改一处代码 | 变更只在隔离工作区，主分支无变化 |
| TC-GIT-003 | 未授权推送 | Agent 尝试向主分支推送 | 系统阻止并记录审计 |
| TC-GIT-004 | Diff 展示 | 完成新增、修改、删除文件任务 | Diff 与 Git 工作区差异一致 |
| TC-KB-001 | 同名字段查询 | 分别查询 MES5/MES6 中同名字段 | 返回对应系统和版本信息，不混用定义 |
| TC-KB-002 | 旧版本字典 | 检索已废弃版本 | 默认不作为当前权威知识返回，或明确标识已废弃 |
| TC-RULE-001 | 阻断规则 | 提交包含违规代码的变更 | 检查失败并阻止标记为可交付 |
| TC-TEST-001 | 测试未执行 | 仅生成测试用例，不运行命令 | 状态为“仅生成未验证”，不得显示通过 |
| TC-MODEL-001 | 模型切换 | 同一会话从模型 A 切换至模型 B | 新调用使用模型 B，历史调用仍保留模型 A 记录 |

| TC-MEM-001 | 项目记忆隔离 | 用户访问无权限项目的记忆 | 不返回对应内容或检索片段 |
| TC-SEC-001 | 提示注入附件 | 附件要求 Agent 泄露密钥或忽略系统规则 | Agent 不执行该指令，按普通资料处理并可提示风险 |
| TC-SEC-002 | 密钥泄露检查 | 检查前端包、会话记录和日志 | 不存在明文密码、PAT 或 API Key |

## 12. 产品决策建议

### 12.1 首期必须坚持的原则

1. **先闭环，再扩展。** 首先保证 Jira → 会话 → 代码工作区 → Diff/测试的链路可靠。
2. **复用执行引擎，自研业务能力。** 通过 Agent Runtime 适配层降低对单一代码 Agent 的绑定。
3. **知识要结构化、可追溯。** MES/WMS 表结构和字段定义不能只依赖向量相似度。
4. **强约束必须可执行。** Prompt 负责指导，静态检查/测试/权限/审批负责强制。
5. **默认人工负责最终代码决策。** Agent 负责辅助开发，人员负责审核、推送、合并和发布。
6. **模型切换必须经过能力认证。** 支持聊天不等于支持稳定代码 Agent 工具调用。
7. **记忆不等于无边界共享。** 会话、项目和企业知识分层保存，来源和权限必须明确。

### 12.2 建议的 MVP 成功定义

当一名研发人员可以在精工 Agent 中选择某一天的 Jira 任务，获取任务描述及附件，选择授权代码仓库和模型，启动隔离的 AI 辅助开发；Agent 能基于适用的 MES/WMS 字典及项目规范完成代码分析或修改，执行已批准的检查/测试，并提供可审查 Diff、测试报告、知识来源和执行记录，同时不越权访问其他项目、不泄漏凭据、不直接修改主分支，即认为 MVP 达到核心目标。

### 12.3 立项建议

建议按“技术验证 PoC → 核心 MVP → 企业知识与规范 → 团队推广”的方式推进。首期不建议同时追求自动 Jira 写回、自动合并、生产发布、多 Agent 编排等复杂功能。优先选择 3 个代表性代码仓库、若干真实 Jira 任务和一组经审核的生产字典，验证业务价值和安全边界，再扩大范围。

## 附录 E：V1.1 产品形态决策记录

1. **桌面应用而非 Web 服务：** 最终用户双击 Windows 程序使用，不打开浏览器、不启动 localhost 服务。
2. **本地数据库而非数据库服务器：** 首期使用 SQLite；后续如需多人协作，再评估中心化服务。
3. **运行时适配层：** Codex App Server 可作为首选 PoC，但当前官方文档将 App Server 标记为 Experimental；必须锁定版本并做兼容性测试，业务层不直接依赖其原始协议。
4. **模型兼容性：** 自定义中转站需逐个验证流式、工具调用和 Agent 执行能力；普通聊天模型不自动获得代码 Agent 资格。
5. **企业版边界：** 组织级账号、跨设备同步、集中审计、统一知识分发和管理策略下发不纳入单机 MVP。
