# 精工 Agent Windows 桌面客户端可行性分析

> **文档版本：** V1.1（Windows 桌面版）  
> **分析日期：** 2026-11-04  
> **项目定位：** 面向公司 MES5、MES6、WMS 研发人员的 Windows 安装式开发 Agent 客户端  
> **结论：** 技术上可行。首期明确采用 Windows 桌面客户端形态，用户安装后直接启动；不建设用户需要部署或维护的应用服务器、Web 服务或数据库服务器。建议采用“桌面客户端 + 本机 Agent Runtime + SQLite + Windows 安全凭据 + Jira/Git/模型 HTTPS 连接器”的路线。

---

## 产品形态重大决策（V1.1，优先级高于 V1.0 的服务器方案）

用户已明确要求：产品体验类似 Codex，直接安装在 Windows 电脑上使用。因此本项目首期产品是一个 **Windows 桌面安装包**，不是部署在电脑上的 Web 服务，也不是服务器平台。

| 项目 | V1.1 决策 |
|---|---|
| 交付形式 | `JinggongAgent-Setup.exe` 或 MSI 安装包 |
| 启动方式 | 桌面/开始菜单快捷方式，双击打开桌面窗口 |
| 应用结构 | 桌面 UI + 本机主进程 + Agent Runtime 子进程 |
| 进程通信 | 本机 IPC；Runtime 首选 stdio；不开放 localhost HTTP/WebSocket 服务 |
| 本地数据 | SQLite + `%LOCALAPPDATA%\JinggongAgent` 文件目录 |
| 凭据 | Windows Credential Manager 或 DPAPI 安全存储 |
| 代码隔离 | Git Worktree + Windows 原生沙箱/权限审批（PoC 实测） |
| 外部依赖 | 客户端主动 HTTPS 访问 Jira、Git 和模型中转站 |
| 不需要 | Docker、PostgreSQL、Redis、MinIO、Kubernetes、独立 Python/Node 服务 |
| 暂不建设 | 公司统一账号中心、跨设备实时同步、多人共享服务端和集中式后台 |

**V1.0 文档中出现的 FastAPI/Java 后端、PostgreSQL/pgvector、Docker/Kubernetes、内网服务器部署建议不再作为首期产品方案。** 它们只有在未来确定建设企业集中协同版时才重新评估。

桌面 UI 内部可以采用 Electron/Tauri 等 Web 技术，但最终用户安装并运行的是独立 Windows 程序，不需要打开浏览器或访问 localhost。

## 一、项目目标与范围

计划建设一个公司内部的开发 Agent 平台，操作体验接近 Codex，但重点不是重新开发一个通用编程模型，而是把公司现有研发流程、Jira 任务、代码仓库、MES/WMS 生产字典、开发规范和测试流程整合进一个统一入口。

### 1.1 核心目标

1. **以 Jira 任务驱动开发：** 按日报日期字段 `cf[11116]` 查询当天任务，用户选中任务后，自动带入任务概要、描述、验收要求和附件。
2. **理解公司 MES/WMS 业务：** 将 MES5、MES6、WMS 的生产字典、字段说明、业务规则等沉淀为可检索知识库，辅助 Agent 理解既有系统。
3. **规范化代码生成：** 把项目开发约束、数据库规范、接口规范、异常处理要求和测试要求落实为可检查的工程规则，而不是只靠提示词提醒。
4. **统一管理模型：** 管理员可配置模型中转站和模型；用户在每个会话中选择模型，平台记录本次会话实际使用的模型和费用。
5. **企业级记忆：** 保留会话历史、项目上下文、公司开发知识和用户偏好，并能按权限检索、更新和追溯。
6. **可控地修改代码：** Agent 在隔离工作区中读取和修改代码，执行测试，提交变更供开发人员审核；默认不直接修改主分支、不自动发布。

## 四、核心功能可行性分析

### 4.1 Jira 登录、日报任务查询和任务上下文导入

#### 推荐实现流程

1. 管理员配置 Jira Base URL、项目 Key（当前提供的项目 Key 为 `NEWDEVGROUP`）和认证方式。
2. 用户启动精工 Agent 桌面应用后，按日期选择日报日期，默认当天。
3. 桌面主进程中的 Jira Connector 调用 Jira REST API，通过 JQL 查询 `cf[11116]` 对应日期的任务。
4. 前端展示任务 Key、概要、状态、负责人、优先级、更新时间等信息，用户选中一个任务。
5. 桌面主进程读取该 Issue 的概要、描述、验收标准、评论（首期可选）、附件元数据和附件文件。
6. 对附件进行格式识别、解析、切块和索引；在 Agent 会话中提供任务上下文和附件引用。
7. 用户选择代码项目/仓库、目标分支和开发模式，开始分析或直接开发。

#### 查询方式示例

Jira Data Center REST API 支持通过 JQL 查询 Issue，并可通过 `fields` 参数限定返回字段；自定义字段可以使用 `cf[字段ID]` 形式检索。示意请求：

```http
GET {JIRA_BASE_URL}/rest/api/2/search
    ?jql=project%20%3D%20NEWDEVGROUP%20AND%20cf%5B11116%5D%20%3D%20%222026-11-04%22
    &fields=summary,description,status,assignee,priority,attachment,created,updated
    &startAt=0&maxResults=100
```

JQL 的最终表达式必须根据 `cf[11116]` 的实际字段类型确定：

- 如果是 Date 类型，先验证 `cf[11116] = "YYYY-MM-DD"` 是否能准确返回当天日报任务。
- 如果是 Date Time 类型，使用当天起止时间范围查询，并按 Jira 实例配置的时区处理边界。
- 若字段并非日期类型，需先查清字段实际含义和索引能力，不能只按字段编号猜测。

建议首期固定 `project = NEWDEVGROUP`，再按需要增加负责人、任务状态或任务类型过滤条件。Jira 搜索结果需要分页读取，不能假设一次请求返回全部任务。

#### 附件处理

- Jira 返回附件的文件名、MIME 类型、大小及下载地址；桌面主进程使用同一 Jira 身份凭据下载附件。
- 支持首期：TXT、MD、CSV、XLSX、DOCX、PDF、JSON、SQL、常见图片；对代码压缩包可设置大小和文件数量上限。
- 不建议把所有附件全文直接塞进模型上下文。应先保存原文件，再抽取文本/表格/代码，按任务建立索引，Agent 按需检索相关片段。
- 附件下载失败、格式不支持、文件过大、加密文件或解析失败，应在会话中明确标记，不能静默忽略。
- Jira 描述、评论和附件内容都属于外部输入。需要防范附件中夹带“忽略系统规则、泄露密钥、执行命令”等提示注入内容；它们只能作为业务资料，不能覆盖平台系统规则。

#### 登录与授权建议

优先使用 Jira Data Center 支持的 Personal Access Token（PAT）或 OAuth 2.0（取决于实例版本和管理员配置），为集成建立专用服务账号，仅授予目标项目的浏览和附件读取权限。Basic Auth 只适合作为短期 PoC 或受控脚本接入，不建议长期以个人用户名/密码运行服务。Jira 官方文档将 PAT/OAuth 2.0 列为推荐方式，并将 Basic HTTP 标为安全性较低的其他方式，详见 [2]。

> **针对当前提供的账号信息：** 用户密码已在聊天中以明文形式出现。建议立即修改该密码，并检查是否在其他系统复用。后续不要把密码写入 Markdown、源码、数据库明文或前端；应改用 PAT/服务账号凭据，并存储在 Windows Credential Manager 或 DPAPI 保护的凭据区。当前 Jira URL 使用 HTTP，正式部署前应通过 HTTPS 反向代理或可信内网 TLS 保护认证流量。

### 4.2 选择代码地址/项目并直接开发

#### 推荐操作模式

- **分析模式：** Agent 只读代码，给出影响范围、方案、风险和测试建议，不修改文件。
- **开发模式：** Agent 在独立分支/Git Worktree/本机隔离工作区修改代码，执行构建和测试，产出代码差异（Diff）。
- **修复模式：** 用户提供错误日志、测试失败或现场问题，Agent 定位并修复。
- **测试模式：** Agent 读取需求和代码，补充测试用例并运行现有测试。

#### 典型流程

```text
选择 Jira 任务
    ↓
选择 Git 仓库 + 分支 + 开发模式
    ↓
创建任务隔离工作区 / 独立分支
    ↓
Agent 读取任务、附件、项目规则和相关代码
    ↓
输出实施计划并等待用户确认（可配置）
    ↓
修改代码 + 运行静态检查/构建/测试
    ↓
生成变更摘要、Diff、测试报告和未解决风险
    ↓
用户审核 → 手动推送/创建 PR → 人工合并
```

首期至少要支持 Git URL/已登记仓库选择、分支选择、仓库权限校验、工作区清理和结果下载。若代码仓库是 GitLab、GitHub Enterprise 或自建 Git 服务，可以通过相应 API 或 Git 协议接入。

**安全要求：** 不建议 Agent 直接在开发人员的日常工作目录中运行，也不允许首期直接向主分支写入。每个任务使用独立 Git Worktree 和受限执行工作区。PoC 需验证 Windows 原生沙箱/权限审批是否可用；限制文件读写范围、网络访问和运行时长；生产凭据不进入 Agent 环境。对依赖安装、数据库变更、删除操作、外部网络访问、推送代码等动作执行审批。

### 4.3 MES5、MES6、WMS 生产字典记忆

这是平台形成公司差异化价值的关键模块。仅仅把 Excel 上传到向量数据库，不能保证代码开发时准确理解表结构和业务含义。

#### 建议把知识拆为三层

| 知识层 | 内容 | 推荐存储与检索 |
|---|---|---|
| 结构化字典 | 表名、字段名、字段类型、长度、是否为空、主外键、注释、枚举值 | 关系型表 + 精确查询/全文检索 |
| 业务知识 | 模块说明、业务流程、状态流转、字段含义、业务约束、历史设计决策 | 文档分块 + SQLite FTS5/关键词检索；向量检索作为本地可选扩展 |
| 代码示例 | 典型接口、Service/DAO 写法、SQL 样例、常见实现模式 | 代码索引 + 关键词检索；向量能力按需增加 |

#### 导入和更新流程

1. 管理员上传 MES5、MES6、WMS 的数据字典、表结构文件和业务说明。
2. 导入程序识别文件格式，抽取工作表、表名、字段名、数据类型、注释和枚举信息。
3. 形成统一元数据模型，并记录系统版本、来源文件、上传人、上传时间和版本号。
4. 对每个模块、表、字段建立 SQLite 精确/关键词索引；业务描述和设计文档首期使用全文检索，后续根据检索评测决定是否引入本地向量索引。
5. Agent 开发时先根据任务识别涉及系统和模块，再检索相关表、字段、状态值、既有代码和规范。
6. 输出涉及的表和字段时，能够提供来源文件及版本，便于开发人员核对。

#### 特别注意

- MES5、MES6、WMS 可能存在相同字段名但含义不同，检索结果必须带系统、版本、模块和数据库标识。
- “数据字典”是结构化知识源，精确表名/字段名查询应优先于语义相似度。
- 知识需要有版本、负责人、审核状态和废弃标记；未经确认的旧字典不能被当作当前生产事实。
- 不建议把生产库账号、密码、真实客户数据和敏感业务数据放进模型记忆。需要样例数据时应使用脱敏数据。

### 4.4 强约束开发规范和测试用例

**核心原则：提示词只能指导 Agent，不能构成可靠的强约束。** 要实现“强约束”，必须让规则进入工具权限、代码检查和 CI 流程。

#### 建议分为四道约束

| 层级 | 实现 | 作用 |
|---|---|---|
| L1：Agent 规则 | 全局 `AGENTS.md`、MES 规则、WMS 规则、项目规则 | 让 Agent 理解编码风格、架构边界、业务规则 |
| L2：自动检查 | Formatter、Linter、静态扫描、SQL 检查、依赖/安全扫描 | 发现格式、危险 API、重复代码和部分架构违规 |
| L3：自动测试 | 单元测试、接口测试、集成测试、回归测试、数据库测试 | 验证代码行为和业务逻辑 |
| L4：审核门禁 | Diff 审核、风险动作审批、CI 必须通过、人工合并 | 防止未验证代码进入主干和生产 |

#### MES/WMS 规则模板建议

- 数据库：表/字段命名、主键生成、数据类型、长度、索引、事务边界、SQL 方言和分页规则。
- 桌面主进程：模块分层、IPC DTO/实体转换、异常处理、脱敏日志、幂等性。
- MES 业务：工单、工序、工艺路线、报工、过站、物料齐套、质量检验、设备数据等领域约束。
- WMS 业务：库位、容器、批次、库存状态、收发存、盘点、冻结、库存事务和条码规则。
- 接口：入参校验、返回结构、错误码、权限、超时、重试和接口兼容性。
- 测试：正常场景、边界场景、异常场景、重复提交、并发/库存一致性、权限和历史数据兼容。

最终规则必须根据公司实际技术栈、既有代码和生产约定逐条确认，不能直接套用通用模板。

#### 测试用例生成建议

Agent 根据 Jira 需求和验收标准，输出测试用例表，至少包含：用例编号、需求点、前置条件、测试数据、操作步骤、预期结果、优先级、自动化建议。对于代码变更，Agent 应尝试补充自动化测试并运行现有测试命令。

测试结果需要区分：**已执行通过、已执行失败、未执行、环境受阻、仅生成未验证**。不能把“模型生成了测试用例”表述为“测试已通过”。

### 4.5 多中转站、多模型配置

首期不部署 LiteLLM Proxy 或其他模型网关服务器。由桌面应用提供 Provider 管理界面，直接连接用户已具备的模型中转站/兼容 API。若公司已经运行统一网关，客户端可把它作为一个 Provider 接入；未来确有统一预算、限流和团队级路由需求时，再评估集中网关。LiteLLM 的文档可作为兼容性参考，参见 [3][4]。

#### 平台配置方式

管理员配置：

- 中转站名称、API Base URL、协议类型。
- 凭据引用（Windows Credential Manager/DPAPI Secret ID），不保存明文 API Key。
- 模型 ID/别名、上下文窗口、最大输出、推理强度等可用参数。
- 可用用户/团队、每日预算、请求速率和停用状态。
- 健康检查、连接测试、模型清单同步。

用户会话选择：

```text
中转站：公司主中转 / 研发备用中转 / 内网模型服务
模型：模型 A / 模型 B / 模型 C
本次会话锁定：是（默认）
```

桌面客户端在本地 SQLite 为每个会话保存 `provider_id` 和 `model_id`，调用时由 Runtime/模型网关路由。用户端只看到允许其使用的模型，不直接接触上游 API Key。

#### 兼容性风险

Codex 的模型请求使用 OpenAI Responses API。通过网关把 Responses 请求转换成其他厂商协议时，工具调用、结构化输出、推理摘要、上下文长度和流式事件可能有差异。不能仅凭“模型能聊天”就认定它适合代码 Agent。上线前需要对每个中转站/模型做统一验收：工具调用成功率、长任务稳定性、代码修改质量、上下文长度、流式中断恢复和成本。

### 4.6 平台记忆功能

建议采用“会话记录 + 项目记忆 + 企业知识库”三种机制，不把所有内容混成一个长期记忆。

| 记忆类型 | 存储内容 | 生命周期与控制 |
|---|---|---|
| 会话记忆 | 本次 Jira 任务、对话、计划、工具调用、代码差异和测试结果 | 按会话保存，可恢复、归档、删除 |
| 项目记忆 | 项目架构、模块关系、构建命令、常见问题、已确认设计决策 | 由项目维护人审核，按仓库/项目权限隔离 |
| 企业知识库 | MES5/MES6/WMS 生产字典、开发规范、通用技术文档 | 管理员发布版本，记录来源和适用范围 |

记忆不应只依赖模型的上下文窗口。建议存储结构化元数据、原文件和文本片段；首期通过 SQLite 全文索引检索，向量索引作为后续可选增强；每次新会话只检索与当前 Jira 任务、代码仓库和系统版本相关的内容。新增“长期项目记忆”时应记录来源和置信状态，对自动提炼的结论允许人工确认、纠错和废弃。首期记忆元数据保存在本机 SQLite，原文和索引保存在应用数据目录；全文检索优先，向量检索不是 MVP 的前置依赖。

## 五、关键风险与控制措施

| 风险 | 等级 | 影响 | 控制措施 |
|---|---|---|---|
| Jira 版本、字段类型或权限与预期不一致 | 中 | 无法准确查询日报任务或下载附件 | 先做 API 探测；核实版本、字段元数据、JQL 和权限；建立接口回归测试 |
| Jira 当前使用 HTTP | 高 | 凭据和会话流量可能被窃听 | 正式环境启用 HTTPS/TLS；只允许内网访问；避免明文密码长期接入 |
| 个人密码/长期密钥泄露 | 高 | Jira、模型或代码系统被未授权访问 | 立即轮换已暴露密码；改用专用服务账号/PAT；Windows Credential Manager/DPAPI 管理；定期轮换 |
| Agent 执行危险命令或误改代码 | 高 | 代码损坏、敏感数据泄露或生产风险 | 任务级 Worktree；Windows 沙箱/权限控制；文件与网络范围限制；资源限制；高风险操作审批 |
| 需求附件含提示注入或恶意文件 | 高 | Agent 违反规则、外传数据或执行不安全命令 | 附件视作不可信数据；病毒/文件类型检查；提示注入防护；禁止凭附件文本授权工具操作 |
| 代码/生产字典发送到外部模型 | 高 | 公司源代码和客户数据泄露 | 模型数据分级；审批模型白名单；敏感内容脱敏；私有模型/私有中转优先处理敏感项目 |
| MES5/MES6/WMS 字典过期或版本冲突 | 中高 | Agent 生成错误 SQL、字段或业务逻辑 | 版本化、审核、适用范围标签、失效机制；回答展示来源版本 |
| 只靠 Prompt 约束规范 | 高 | 生成代码不一致，无法稳定执行 | 规则文件 + Linter/静态检查 + 测试门禁 + 人工审核 |
| 各中转站对 Agent 工具协议支持不一致 | 中高 | 某些模型无法稳定调用工具或完成长任务 | 做模型认证清单和能力矩阵；上线前跑标准代码任务基准 |
| 长任务成本不可控 | 中 | Token 和计算费用超预算 | 按用户/团队/模型预算；会话限额；成本可视化；超额暂停或审批 |
| 记忆污染、越权检索 | 中高 | 错误知识反复影响开发或跨项目泄密 | 项目/团队权限过滤；来源溯源；记忆审核；访问日志和删除策略 |

## 六、MVP 建设计划与投入估算

以下为在 Jira、Git、测试环境和字典资料可访问的前提下的初步估算，不是正式工期承诺。

### 6.1 推荐分阶段推进

| 阶段 | 周期估算 | 交付内容 | 验收重点 |
|---|---:|---|---|
| 阶段 0：技术验证 | 3–5 个工作日 | Jira API 探测；字段 `cf[11116]` 查询验证；Codex 执行环境；模型网关连通；一个 Git 仓库试跑 | Jira 查询准确；能读附件；能在隔离工作区完成一个简单修复并跑测试 |
| 阶段 1：最小可用版 | 2–3 周 | Windows 桌面壳、本地配置档案、Jira 日期任务列表、任务上下文导入、代码仓库选择、Agent 会话、模型选择、Diff 展示 | 用户能从 Jira 任务启动开发并查看变更和测试结果 |
| 阶段 2：企业知识与规范 | 1–2 周 | MES5/MES6/WMS 字典导入、RAG 检索、项目规则、测试用例生成、规范检查 | Agent 能引用字典来源；关键规则由检查工具拦截 |
| 阶段 3：试点与加固 | 1–2 周 | 权限、审计、成本统计、异常恢复、记忆管理、用户试点 | 选 3–5 个典型仓库/任务完成闭环，修复高风险问题 |

**整体建议：** 先用约 1 周完成可行性 PoC，再按 4–6 周建设内部 MVP。若要求正式企业级上线，增加 SSO、细粒度权限、合规审计、多执行引擎、复杂知识库治理和高可用，建议另行评估 8–12 周或更长。

### 6.2 最小团队配置

| 角色 | 建议投入 | 主要职责 |
|---|---:|---|
| 技术负责人/架构师 | 0.5–1 人 | 技术路线、MES/WMS 规则、代码评审、验收 |
| Windows 桌面/Agent 集成开发 | 1–2 人 | 桌面主进程、Jira/Git/模型连接器、Agent 生命周期、会话与记忆 |
| 前端开发 | 1 人 | 工作台、任务选择、会话、模型配置和结果视图 |
| Windows 打包/发布 | 0.5 人 | 安装包、代码签名、运行时分发、升级、日志和本机诊断 |
| 测试/业务代表 | 0.5 人 | 任务样本、字典核对、测试基线、安全与验收 |

如果当前团队人力不足，建议先做阶段 0 和阶段 1，不要一开始就同时建设全套企业知识治理和复杂多租户功能。

## 七、MVP 验收标准

建议使用可验证的指标验收，避免只以“Agent 能对话”作为成功标准。

| 维度 | 建议验收标准 |
|---|---|
| Jira 任务查询 | 选取不少于 10 个工作日，与 Jira 人工筛选结果对比；目标任务无漏查、无跨日期误查；分页完整 |
| Jira 附件 | 对已声明支持的文件类型，附件下载和解析成功率达到 95% 以上；失败原因可见；大文件有上限和提示 |
| 任务上下文 | 会话中能查看 Jira Key、概要、描述、验收标准、附件列表及来源链接 |
| 代码开发 | 至少接入 3 个代表性仓库；Agent 能在隔离分支修改代码并输出 Diff；不直接写主分支 |
| 构建与测试 | 对选定仓库，Agent 能执行项目约定的构建/测试命令并报告真实结果；未执行与通过明确区分 |
| 字典检索 | 建立 MES5、MES6、WMS 代表性问答集；抽测表名、字段名、状态值等精确问题，答案提供可追溯来源 |
| 开发规范 | 至少选 10 条可自动检查的硬规则；违规代码能被检查工具或 CI 拦截，而不只是提醒 |
| 模型切换 | 每个会话可选择授权的中转站和模型；切换结果准确；日志能追踪实际 provider/model |
| 记忆 | 会话可恢复；项目记忆有来源、版本和权限；不同项目用户之间不能越权检索 |
| 安全审计 | Agent 工具执行、模型调用、审批、代码差异和测试结果有审计记录；密钥不出现在前端和普通日志中 |

## 十、最终建议

### 10.1 建议立项，但采用小步快跑

这个项目值得做。它能把公司日常开发流程中的 Jira 需求、代码仓库、生产字典、开发规则和测试验证串成闭环，逐步沉淀公司的 MES/WMS 研发知识，减少开发人员重复查表、找代码和理解业务规则的时间。

但项目成败不取决于界面做得像不像 Codex，而取决于三件事：

1. **任务上下文准确：** Jira 任务和附件能否正确获取，生产字典是否可信且版本正确。
2. **代码执行可控：** Agent 是否在隔离环境里开发，能否按规范构建、测试并交付可审查的 Diff。
3. **知识规范可执行：** 开发约束是否由规则、检查和测试落地，是否能积累成可复用的企业资产。

### 10.2 推荐决策

- **批准阶段 0 PoC：** 先验证 Jira `cf[11116]`、附件读取、Codex 本地/内网执行、一个 MES/WMS 仓库、一个模型中转站。
- **PoC 通过后建设 MVP：** 优先完成 Jira → Agent 会话 → Git 隔离开发 → Diff/测试报告的完整闭环。
- **第二批完善企业知识：** 导入 MES5/MES6/WMS 字典，建立规范、测试用例模板和项目记忆。
- **正式推广前补齐安全治理：** HTTPS、服务账号、密钥管理、执行隔离、模型白名单、权限审计和成本管理。

**建议项目名称：精工 Agent（公司级 MES/WMS 智能研发平台）**  
**首期目标：让开发人员从 Jira 任务一键进入可控的 AI 辅助开发流程，而不是追求一开始就全自动开发、测试和发布。**

## 十三、Windows 桌面版最终结论与专项风险

### 13.1 可行性结论

Windows 安装式桌面客户端可行，且比首期部署本地 Web 服务更符合用户期望。技术关键从“服务端部署”转为“桌面进程安全、Agent Runtime 分发、Windows 沙箱、数据本地化、升级和卸载”。

### 13.2 必须 PoC 验证的事项

1. Electron/Tauri/.NET 中哪一种能够最稳妥地管理 Codex Runtime 子进程、流式事件、取消、审批和恢复。
2. Codex App Server 当前属于 Experimental，选定版本的协议兼容和 Windows 运行能力是否足够；如不满足，提供备用 Runtime。
3. 不安装全局 Node/Python/Docker/PostgreSQL 的 Windows 干净环境中，应用是否可启动。
4. `codex.exe` 和 Git Runtime 是随安装包携带还是首启安全下载，需验证许可证、签名、哈希、更新策略。
5. Windows Credential Manager/DPAPI 是否满足 API Key、Jira PAT 和 Git Token 的安全保存要求。
6. 任务级 Worktree 和 Windows 原生沙箱对文件范围、网络访问和命令执行是否能真正生效。
7. 应用关闭、崩溃、升级和系统重启后，Agent 子进程与本地会话是否能正确收尾或恢复。

### 13.3 版本边界

- **桌面 MVP：** 单机用户、本地 SQLite、Jira/Git/模型连接、Agent 会话、Worktree、Diff、基本知识库和本机审计。
- **后续企业版：** 统一账号/策略、团队知识包发布、跨电脑记忆同步、集中审计、管理后台和共享执行资源。只有确认多人协作需求后再引入服务端，不得把它作为首期前置条件。
