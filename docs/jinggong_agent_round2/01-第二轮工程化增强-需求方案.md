# 精工 Agent 第二轮工程化增强需求方案

版本：V1.0  
适用产品：精工Agent（Windows 桌面端）  
适用 Runtime：Codex Runtime、精工 Runtime  
文档性质：产品需求基线 / Codex 开发输入  
优先级：P0 工程可靠性优先，P1 管理与运营能力增强

---

## 1. 项目背景与目标

精工 Agent 已具备或正在建设以下基础能力：项目与会话管理、Jira 任务接入、模型中转配置、项目知识库、Codex Runtime 与精工 Runtime 双运行模式、需求准入检查、代码变更查看、构建/测试证据链，以及多 Agent 协作能力。

第二轮建设不以增加聊天功能为目标，而是将现有能力工程化，重点解决：

1. Agent 任务边界不清，执行过程缺少明确的输入、权限和验收契约。
2. Agent 自报完成与真实验证通过容易混淆。
3. 多个开发 Agent 同时修改代码时存在文件覆盖、分支冲突和工作区污染风险。
4. 任务执行缺少预算、并发、超时、递归层级和失败熔断控制。
5. 应用异常退出后，任务、日志、上下文和工作区恢复能力不足。
6. 工具权限、敏感操作审批与审计链不够完整。
7. 缺少 Agent 模板、质量统计、知识库版本追溯和故障诊断能力。
8. 当前工作台对任务、代码、运行、成本和质量信息的呈现仍可进一步统一。

### 1.1 总体目标

建设可控、可恢复、可审计、可度量的 Agent 执行体系，使一个真实 MES/WMS 开发任务能够在明确权限和预算约束下完成任务拆解、协作开发、代码集成、真实构建与测试，并保留可检查的执行证据。

### 1.2 核心原则

- **先盘点、后改造**：Codex 必须先分析现有代码和功能，不得直接推倒重做。
- **复用优先**：已有会话、Runtime、模型配置、知识库、日志、Git、测试证据模块优先扩展，不重复建设。
- **真实优先**：状态、日志、费用、构建和测试结果必须来自真实运行事件或可核验数据。
- **安全默认**：默认最小权限、默认隔离、默认不自动执行高风险操作。
- **双 Runtime 一致体验**：Codex Runtime 和精工 Runtime 统一前端概念、状态和管理体验，但允许底层能力存在差异。
- **渐进增强**：P0 先实现工程可靠性；P1 再完善管理、模板和效率分析。

## 2. 本轮范围与非目标

### 2.1 本轮范围

| 优先级 | 能力 | 本轮目标 |
|---|---|---|
| P0 | Agent 任务契约 | 每个 Agent 任务有结构化输入、权限、预算、依赖和验收标准 |
| P0 | 状态与证据分离 | 执行完成、验证通过、人工验收是不同状态 |
| P0 | 代码工作区隔离 | 写入型 Agent 独立 Worktree/分支，安全集成 |
| P0 | 资源与成本控制 | 并发、超时、Token/费用预算、递归深度、失败熔断 |
| P0 | 持久化与恢复 | 异常退出后可检查、恢复或安全终止任务 |
| P0 | 权限与审计 | 工具权限、审批、审计事件、敏感信息保护 |
| P1 | Agent 模板 | 可复用专业 Agent 配置与团队模板 |
| P1 | Agent 质量评分 | 任务成功、返工、测试、人工介入等质量指标 |
| P1 | 知识库版本管理 | 记录任务执行时使用的知识库版本和内容快照 |
| P1 | 人工接管 | 暂停、追加指令、批准、恢复、终止和交接 |
| P1 | 故障诊断包 | 导出脱敏后的日志、事件、错误和证据索引 |
| P1 | AI 开发质量驾驶舱 | 任务量、质量、效率、成本等指标统计 |
| P1 | UI 工作台增强 | 对话、任务、代码、运行监控四视图及可调整面板 |
| P1 | 通知集成 | 任务完成、失败、阻塞时接入现有企业微信通知能力（若已实现则复用） |

### 2.2 非目标

- 不重写 Codex Runtime，不复制其内部 Agent 实现。
- 不要求 Codex Runtime 和精工 Runtime 的底层能力完全相同；不支持的能力必须显式标注。
- 不在本轮建设通用云端多租户 SaaS 平台。
- 不自动批准数据库生产变更、远程推送、主分支合并、文件批量删除等高风险操作。
- 不把模型自报 Token、费用、测试通过率作为权威数据。
- 不把 AI 生成的质量评分直接用于员工绩效结论。

## 3. 用户角色与核心场景

### 3.1 用户角色

- 普通开发人员：创建任务、查看执行过程、提交人工确认、检查代码和测试证据。
- 项目负责人/技术负责人：配置项目规范、审批关键操作、检查风险和交付质量。
- 平台管理员：配置 Runtime、模型、工具权限、预算策略、模板和审计策略。
- 只读审计人员：查看任务状态、运行证据和操作记录，不得修改执行内容。

### 3.2 核心场景

**场景 A：单 Agent 执行普通开发任务**  
用户创建任务，系统生成任务契约，按权限执行，留存代码变更和测试证据，最终区分执行完成、验证通过及人工验收。

**场景 B：多 Agent 协作开发**  
主 Agent 创建多个子任务；只读分析任务可并行；写入型任务使用独立工作区；通过依赖关系串并行调度；最终由主 Agent 汇总并通过质量门禁。

**场景 C：任务超预算/超时**  
系统预警并暂停继续派发；根据策略等待用户、缩减任务、切换允许的模型或终止。不得静默超预算继续执行。

**场景 D：应用异常退出**  
重启后加载未完成任务，展示上次状态、最后事件、工作区和恢复选项；不盲目重放不确定是否已产生副作用的工具调用。

**场景 E：高风险操作**  
Agent 请求执行高风险工具时，系统展示操作内容、影响范围和风险，等待具备权限的用户批准；审批需绑定具体任务、操作和有效期。

## 4. P0 需求

### P0-1 Agent 任务契约

每个主任务和子任务必须有结构化任务契约（Task Contract）。

必填信息：

- task_id、session_id、project_id、runtime_type。
- parent_task_id（主任务为空）。
- task_title、task_goal、task_description。
- task_type：analysis / design / implementation / review / test / documentation / integration / other。
- input_refs：Jira、文件、知识库、代码文件、父任务结果等引用。
- output_expectations：期望交付内容及格式。
- acceptance_criteria：可检查的验收条件。
- allowed_tools：可使用工具白名单。
- permission_profile：只读、代码写入、命令执行等权限配置。
- allowed_paths / denied_paths：允许和禁止访问的工作区路径规则。
- dependencies：前置任务 ID 和依赖条件。
- workspace_policy：shared_readonly / isolated_worktree / no_workspace。
- model_policy：继承或指定模型策略；不将密钥写入契约。
- budget_policy：Token、费用、时间、工具调用和重试上限。
- created_by、created_at、contract_version。

规则：

1. 契约创建后保存版本，不允许静默覆盖；修改需生成新版本和变更事件。
2. 子任务只能获得完成该任务所需的最小上下文，不得默认复制全部主会话历史。
3. 工具调用必须校验任务契约中的权限和路径约束。
4. 任务缺少验收标准时，主 Agent 应先补齐或向用户确认，不得将模糊任务直接派发给写入型 Agent。
5. 对 Codex Runtime 不支持的平台字段，保存为平台侧策略，并明确标记哪些策略由平台执行、哪些由 Runtime 执行。

### P0-2 执行状态、验证状态、验收状态分离

禁止使用单一 `status=SUCCESS` 表示所有阶段均通过。建议分别维护三组状态。

**执行状态 execution_status**

- PENDING：等待调度
- READY：依赖已满足，待启动
- RUNNING：执行中
- PAUSED：人工暂停
- BLOCKED：受阻/等待审批
- COMPLETED：Agent 执行结束
- FAILED：执行失败
- CANCELLED：已取消
- INTERRUPTED：应用或 Runtime 中断，结果待核实

**验证状态 verification_status**

- NOT_REQUIRED：无需验证（必须记录原因）
- NOT_STARTED：未开始
- RUNNING：验证执行中
- PASSED：真实验证通过
- FAILED：真实验证失败
- PARTIAL：部分通过
- INCONCLUSIVE：证据不足或环境不可用

**验收状态 acceptance_status**

- NOT_SUBMITTED：尚未提交验收
- PENDING_REVIEW：等待人工验收
- ACCEPTED：授权人员已验收
- REJECTED：验收被拒绝

状态约束：

1. Agent 执行结束只能将 execution_status 置为 COMPLETED，不能自动将 verification_status 置为 PASSED。
2. verification_status=PASSED 必须关联真实构建/测试/静态检查等证据；证据不足只能是 INCONCLUSIVE。
3. ACCEPTED 必须记录验收人、时间、验收意见和对应代码版本/证据版本。
4. 没有要求人工验收的任务，可按项目策略标记 NOT_REQUIRED，但需留存原因和策略来源。
5. 任一状态变化均产生不可随意篡改的事件记录。

### P0-3 真实证据链

每条证据至少包含：

- evidence_id、task_id、project_id、evidence_type。
- source：runtime / process / test_runner / git / user / platform。
- command 或 action（适用时）。
- working_directory、environment_info、runtime_version。
- started_at、finished_at、duration_ms。
- exit_code、result_status。
- log_ref、artifact_ref、commit_sha、diff_ref（适用时）。
- content_hash、created_at。

要求：

1. 保存原始执行结果或可追溯日志引用，不能只保存模型摘要。
2. 测试证据必须关联当前代码版本（commit SHA 或工作区 diff hash）。
3. 构建/测试命令、退出码和日志来自实际执行器。
4. 无可用测试环境时标记 INCONCLUSIVE，并说明原因，不能伪造通过。
5. 证据摘要由模型生成时，必须保留其对应的原始证据引用。
6. 对证据记录采用追加式存储；如需纠错，新增更正事件，不覆盖原始证据。

### P0-4 多 Agent 工作区隔离与集成

工作区策略：

- `no_workspace`：仅分析、规划或问答任务。
- `shared_readonly`：只读 Agent 可共享项目代码快照。
- `isolated_worktree`：写入型 Agent 默认独立 Git Worktree 和分支。

要求：

1. 创建 Worktree 前校验仓库状态、分支和目标路径。
2. Worktree 与 task_id 绑定，并记录基准 commit。
3. 只读 Agent 的文件系统权限必须由工具层强制执行，而不只是提示词约束。
4. 不同写入型 Agent 默认不可共享可写目录。
5. 子 Agent 完成后生成变更摘要、文件清单、diff 和工作区状态。
6. 主 Agent 集成前检查基准版本、文件冲突、未提交变更、删除/重命名和越界修改。
7. 自动合并仅允许在明确配置、无冲突且通过质量门禁时执行；默认由用户确认。
8. Push、合并受保护分支、覆盖他人修改和删除工作区必须经过审批。
9. 任务取消或失败时保留工作区，除非用户选择清理；不得自动删除唯一代码成果。
10. 在 Windows 本地环境下验证 Git Worktree 路径、文件锁、进程退出和清理行为。

### P0-5 资源预算与熔断

支持以下限制，配置可按全局、项目、会话、Agent 角色分层继承：

- max_concurrent_agents。
- max_agent_depth。
- max_total_agents_per_task。
- max_runtime_minutes。
- max_model_requests。
- max_tool_calls。
- max_input_tokens / max_output_tokens（Runtime 可提供时）。
- max_cost_amount / currency（有可信计价数据时）。
- max_retries_per_task。

规则：

1. 预算配置必须显示来源、继承结果和最终生效值。
2. 接近预算阈值时预警；达到硬上限时暂停新调用或阻断任务。
3. 无法获得真实 Token/费用时，显示“不可用/估算”，不得伪装成精确计费。
4. 模型价格表需带生效时间和币种；费用计算必须可追溯到模型、用量和价格版本。
5. 失败重试需区分可重试错误与不可重试错误，并采用退避策略。
6. 对可能有副作用的工具调用必须使用幂等键或执行前后状态核验，避免重复执行。
7. 出现循环派发、连续失败、超时或预算耗尽时触发熔断，记录原因。

### P0-6 持久化与任务恢复

需持久化：任务契约及版本、父子关系、依赖、状态、事件、消息引用、模型/工具调用摘要、证据引用、审批记录、预算消耗、工作区映射和恢复点。

恢复要求：

1. 应用启动时扫描非终态任务及上次运行实例。
2. 将无法确认执行结果的 RUNNING 任务标记为 INTERRUPTED，而不是直接视为失败或成功。
3. 展示最后事件、最后一次工具调用、工作区状态和潜在副作用。
4. 用户可选择：安全恢复、重新尝试指定步骤、只查看/导出、终止并保留工作区。
5. 只在明确安全的检查点恢复，不默认重放所有模型请求和工具调用。
6. 任务恢复必须使用幂等标识和执行前状态检查。
7. 对 Codex Runtime：先确认官方/当前 SDK 的会话恢复能力；不支持时采用平台级恢复记录，不能宣称恢复了 Runtime 内部上下文。
8. 记录恢复次数、恢复人、恢复策略和恢复结果。

### P0-7 权限与审计

权限采用最小权限模型，至少区分：

- read_project：读取项目代码/文件。
- write_workspace：修改被分配的工作区。
- execute_command：执行命令。
- access_network：访问网络。
- install_dependency：安装依赖。
- read_secrets：读取密钥（默认禁止 Agent 直接读取）。
- database_read / database_write。
- git_commit / git_push / git_merge。
- delete_files。

要求：

1. 权限需绑定用户、项目、Runtime、Agent 角色或任务范围。
2. 工具调用入口统一进行权限校验，不能仅依赖前端按钮隐藏或 System Prompt。
3. 高风险操作需二次确认或审批，审批绑定具体参数摘要、任务和有效期。
4. 审批后若命令/参数发生变化，原审批自动失效。
5. 审计记录至少包含操作者、Agent、任务、工具、参数摘要、结果、时间和审批引用。
6. 日志、诊断包和模型上下文不得明文暴露 API Key、密码、访问令牌等秘密。
7. 提供权限拒绝记录和审计查询能力。

## 5. P1 需求

### P1-1 Agent 模板管理

支持模板新增、编辑、复制、启用、停用、版本管理和导入导出。

模板配置：名称、角色、说明、系统提示词、默认模型策略、工具权限、知识库引用、工作区策略、预算默认值、输出格式、适用项目类型、版本、作者和更新时间。

内置建议模板：MES 需求分析、MES 开发、WMS 开发、数据库审查、代码审查、测试设计、测试执行、技术文档。

模板不能绕过项目权限；从模板创建 Agent 时仍需按当前任务重新校验权限和预算。

### P1-2 Agent 质量评分与运营指标

建立可解释指标，不输出无法追溯的“AI 综合分”。建议指标：

- 任务执行完成率。
- 真实验证通过率。
- 任务一次通过率。
- 返工率。
- 人工介入率。
- 平均执行时长。
- 单任务模型用量和可核算成本。
- 任务失败原因分布。

所有指标必须明确统计口径、分母、时间范围、数据来源和过滤条件。允许按 Runtime、项目、Agent 模板、任务类型分组。

不允许把模型自评、未验证任务或没有真实分母的数据纳入“验证通过率”。不得把指标直接解释为员工绩效。

### P1-3 知识库版本管理

任务启动时记录本次使用的知识库集合及版本：

- 知识库 ID、版本 ID、文档 ID、文档版本/更新时间。
- 数据字典版本、开发规范版本、项目规则版本。
- 内容 hash 或可追溯快照引用。
- 检索时实际命中的文档引用（如 Runtime 能提供）。

知识库更新不得改变已执行任务的历史版本引用。新任务默认使用当前生效版本；项目可锁定指定版本。删除文档时保留历史任务引用的元数据和审计记录。

### P1-4 人工接管

在运行中任务支持：暂停、恢复、追加指令、批准/拒绝审批、指定 Agent 交接、终止、保留工作区。

人工追加指令必须生成新消息事件，保留修改前任务契约，不得悄悄覆盖原任务目标。接管后明确显示当前控制者是用户还是 Agent。

### P1-5 故障诊断包

允许用户按任务或会话导出诊断包，包含：任务契约、状态事件、脱敏日志、模型/工具调用元信息、Runtime 版本、错误堆栈、工作区状态、Git 差异摘要、证据索引和恢复记录。

默认不打包完整源码、密钥、环境变量、用户凭据和无关客户数据。导出前提供内容预览和脱敏提示。

### P1-6 AI 开发质量驾驶舱

提供按时间范围、项目、Runtime、任务类型和 Agent 模板筛选的统计视图。

核心卡片：任务总量、执行完成数、验证通过数、验收通过数、失败数、人工介入率、平均耗时、Token 用量、可核算费用。

图表：任务趋势、失败原因、验证结果、耗时分布、成本分布、Agent 模板对比。

每个统计值支持下钻到任务明细，避免只有不可核验的汇总数字。

### P1-7 UI 工作台增强

主工作区增加四个视图：

1. 对话：用户与主 Agent 的交互、关键进度和结论。
2. 任务：主任务/子任务树、依赖关系、运行状态、人工干预。
3. 代码：文件变更、diff、分支、Worktree、提交和集成状态。
4. 运行监控：模型/工具调用、耗时、预算、错误、构建和测试证据。

右侧信息栏（Jira、代码变更、Git、上下文等）支持拖动宽度、收起、展开和布局记忆。详细工具日志不应全部挤入主聊天窗口。

所有状态颜色必须同时配合文字和图标，不得只依赖颜色区分。布局在常见 Windows 桌面分辨率下可用，窄窗口时支持折叠和响应式调整。

### P1-8 通知集成

复用现有企业微信通知模块（如已建设）。事件类型：任务完成、任务失败、等待审批、预算预警、任务阻塞、需要人工接管。

通知应包含任务名称、项目、状态、关键原因和精工 Agent 内部可定位入口；不得发送密钥、完整代码或敏感日志。支持个人接收配置、去重、失败重试和通知记录。

## 6. 交互与界面要求

- 主任务详情清楚展示执行状态、验证状态、验收状态，三者不可合并。
- 预算区域显示已用、剩余、阈值和数据可信度。
- 子 Agent 任务卡展示角色、任务范围、工作区、执行状态和结果摘要。
- 高风险操作必须有明确的确认对话框，显示真实命令和影响范围。
- 应用重启后，对中断任务提供恢复入口，不自动继续执行有副作用的步骤。
- 证据区域可查看原始日志或原始报告，模型摘要仅作为辅助说明。
- 支持用户复制任务 ID、证据 ID、commit SHA 和诊断信息。

## 7. 验收标准

### P0 验收

**任务契约**
- 创建的主任务和子任务均存在结构化契约。
- 任务契约修改有版本和事件记录。
- 工具调用超出权限或路径范围时被执行层拒绝，并记录审计事件。

**状态和证据**
- Agent 返回“完成”但没有测试证据时，不会显示“验证通过”。
- 实际构建/测试失败时，验证状态为 FAILED，并关联真实退出码和日志。
- 验收通过必须可追溯到人员、时间、意见及对应代码版本。

**工作区隔离**
- 两个写入型 Agent 可在同一仓库的不同 Worktree 工作，互不覆盖。
- 同一文件的冲突能被检测并阻止默认自动覆盖。
- 取消任务后代码成果可保留并查看。

**预算控制**
- 达到并发、超时、模型请求或费用硬上限时，系统按策略阻止后续执行。
- 无可信 Token/费用数据时，界面明确显示未知或估算。
- 连续失败和循环调度能被熔断。

**恢复机制**
- 模拟应用异常退出后，重启能够识别非终态任务并标记 INTERRUPTED。
- 可查看最后事件、工作区和工具调用状态。
- 不会在无法确定副作用时自动重放命令。

**权限审计**
- 无权限工具调用被拒绝并留痕。
- 审批绑定具体操作参数，参数变化后审批失效。
- 诊断日志与导出文件完成秘密信息脱敏。

### P1 验收

- Agent 模板可创建、版本化、复制和应用。
- 质量指标均有定义和任务明细下钻。
- 历史任务能追溯当时所用知识库版本。
- 用户可暂停、追加指令、恢复和终止任务。
- 诊断包可导出且不含密钥和未授权源码。
- 驾驶舱数据与任务明细核对一致。
- 四视图工作台可切换，侧栏尺寸和布局可记忆。
- 企业微信通知有发送记录、失败记录和去重机制。

### 端到端验收用例

选取一个非生产环境的真实 MES 或 WMS 开发任务，完成：需求建立 → 契约校验 → Agent 任务拆分 → 独立工作区开发 → 代码审查 → 构建/测试 → 证据归档 → 人工验收 → 诊断包/指标可查询。

另需覆盖：权限拒绝、预算超限、测试失败、Worktree 冲突、应用异常退出和安全恢复。

## 8. 交付物

1. 现状盘点与技术差距分析报告。
2. 目标架构和模块边界说明。
3. 数据库迁移脚本及回滚方案。
4. 任务契约、状态和证据链实现。
5. 工作区隔离和安全集成实现。
6. 预算、权限、审批和审计实现。
7. 持久化及任务恢复实现。
8. P1 模板、指标、知识库版本、诊断包和 UI 实现。
9. 自动化测试及端到端测试报告。
10. 升级说明、已知限制和回滚说明。

## 9. 实施约束

- 先做代码审查和功能盘点，再提出改造计划。
- 每个需求标注“已有可复用 / 需扩展 / 需新增 / 当前 Runtime 不支持”。
- 不得为了统一抽象而削弱 Codex Runtime 原生能力。
- 对 Codex Runtime 和精工 Runtime 分别列出真实能力差异。
- 不得以 UI 模拟状态、假日志或静态示例作为验收。
- 未完成项必须如实标记，不得宣称已完成。
- 数据库迁移必须考虑旧版本数据兼容和失败回滚。
- 所有 P0 完成并通过端到端验收后，才进入 P1 全量建设。
