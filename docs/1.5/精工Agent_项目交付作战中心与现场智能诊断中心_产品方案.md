# 精工 Agent 项目交付作战中心与现场智能诊断中心

> 文档类型：产品方案、交互规格、技术架构与分阶段开发指令  
> 版本：1.5 评审稿  
> 审查日期：2026-11-26  
> 覆盖模块：项目交付作战中心、MES/WMS 现场智能诊断中心  
> 本阶段交付：产品方案与交互原型，不包含生产源码改动

## 1. 方案结论

将原“交付工作台”升级为**项目交付作战中心**，将原“现场问题排查中心”升级为**MES/WMS 现场智能诊断中心**。两者围绕同一条 `DeliveryProject` 项目主线协同，工作流和记录边界保持清晰。

交付中心负责项目阶段、里程碑、任务、交付问题、客户决策、项目资料、周报与验收准备。诊断中心负责现场异常从登记、分诊、证据收集、排查验证、开发升级、解决验证到知识复用的全过程。交付问题可发起诊断，诊断档案可定位回项目及对应交付问题。新建现场诊断必须关联一个未归档交付项目，具体交付问题为可选项。

项目归属只取自 `DeliveryProject.id`。诊断分析运行有独立的运行记录和受控 Runtime 目录，不读取或要求聊天历史。运行使用现有 Runtime 配置和专家中心定义，不复制凭据、模型供应商或专家档案。模型产出始终标记为建议，项目状态、客户承诺、根因和解决验证均由人员确认。

本方案按当前代码基线制定。现有大部分实体、存储、项目外键、诊断独立运行、项目问题导入幂等检查及项目聚合已经存在。第一阶段产品实现不需要重建项目模型或整体迁移数据库，重点是工作流、页面组织、统一项目上下文和 Runtime/专家配置的显式选择。

### 2.3 存储和数据模型事实

当前 SQLite schema 版本为 25。schema 23 建立交付项目及其子表，schema 24 建立诊断档案、运行、步骤、证据、假设、解决记录、知识案例和事件表，schema 25 补充项目与问题关联索引。领域对象完整内容以 JSON 存储，并对常用过滤字段维护索引列。

`diagnostic_cases.delivery_project_id` 外键指向 `delivery_projects.id`，删除项目时使用 `ON DELETE SET NULL` 保留诊断档案。历史档案可以没有项目归属，新建档案则由主进程校验要求项目。项目归档不等于删除，归档项目仍用于显示历史诊断关系，但不能作为新建诊断的项目选择。

关系概览：

```text
DeliveryProject 1 ── N DeliveryMilestone
DeliveryProject 1 ── N DeliveryTask
DeliveryProject 1 ── N DeliveryIssue
DeliveryProject 1 ── N DeliveryMeeting / DeliveryDocument / DeliveryReport / DeliveryActivity
DeliveryProject 1 ── N DiagnosticCase
DeliveryIssue  0 ── 1 DiagnosticCase（可选关联；导入入口按项目与问题键复用档案）
DiagnosticCase 1 ── N DiagnosticRun
DiagnosticRun  1 ── N DiagnosticStep / DiagnosticHypothesis
DiagnosticCase 1 ── N DiagnosticEvidence / DiagnosticResolution / DiagnosticEvent / DiagnosticKnowledgeCase
```

第一阶段不增加项目表、诊断项目表、聊天关联表或重复知识库。专家/Runtime 选择快照可作为 `DiagnosticRun` 的可选 JSON 字段向后兼容；只有后续确有索引、并发或审计需求时才新增 SQLite 列或迁移。

## 3. 产品目标与边界

### 3.1 目标用户和主要工作

- **交付负责人**：巡检项目组合中的延期、阻塞、客户待确认和高风险事项，安排升级处理。
- **项目经理**：维护阶段计划，协调任务与客户决策，控制项目风险，编制周报和验收准备。
- **实施工程师**：记录现场问题，按安全步骤收集证据、验证假设、回填客户或开发处理结果。
- **开发工程师**：接收结构化复现条件、证据、已排除路径和客户影响，减少重复问询。
- **技术骨干/知识审核人**：复核根因与解决质量，决定是否沉淀为同项目或跨项目知识。

当前产品是本机桌面工作区。负责人字段是姓名/显示名，角色视图是入口和筛选预设，不构成企业身份认证、数据授权或跨设备协作。

### 3.2 成功标准

- 项目经理能在一个组合总览中定位需要决策或升级的事项，并从异常直接进入对应项目记录。
- 每个现场诊断都能从项目或项目问题进入，也能从诊断档案定位回原项目，不需要搜索聊天历史。
- 诊断信息按事实、缺失信息、AI 假设、人工验证结果分开呈现。关键建议能追溯到已选来源。
- 研发升级材料包含现场症状、版本/环境、复现步骤、证据、排查记录、影响和待开发确认项。
- 解决关闭和知识共享需要人员确认。跨项目共享只使用审核通过、去敏后的案例。
- 项目归属、问题归属、运行快照在主进程校验。Runtime 不获得自动写客户 MES/WMS 的能力。

### 3.3 不在本次目标内

- 云端服务、多设备同步、组织账号、实时多人协作和真实 RBAC。
- Jira 双向同步、客户工单系统连接、财务成本/毛利核算、自动人员排程和完整甘特图。
- 自动访问客户生产数据库、设备、PLC、接口或服务器，自动运行 SQL/Shell/PowerShell，或自动修改生产数据、配置、库存和服务。
- 由 AI 自动修改项目计划、负责人、客户承诺、交付问题状态、诊断根因或解决状态。
- 重写 Runtime、Agent 编排、专家中心、知识库、项目资料导入和 Excel 映射。
- 将“推测”“静态规则摘要”包装成已验证 AI 结论。

## 4. 业务流程

### 4.1 项目启动与计划建立

1. 项目经理创建或打开交付项目，确认客户、系统类型、产品版本、阶段、经理、成员和计划周期。
2. 维护已有里程碑、任务、交付问题、会议和资料。按现有实体记录，不额外创建一套“阶段门”表。
3. 作战舱把已存在的数据整理成进度、逾期、风险、待决策和资料缺口。缺少负责人或日期时标记“信息未补齐”，不推断为正常。
4. 用户可以从项目资料、操作手册和确认过的项目知识进入现有知识能力；新增/修改结构化记录前由人员保存确认。

### 4.2 日常项目巡检与行动闭环

1. 作战总览按阻塞、逾期、客户待确认、高优先级、临近里程碑和待验证分类显示异常。
2. 用户按项目、负责人、系统、优先级或事项类型筛选，打开原始任务、交付问题或里程碑。
3. 对现场软件/流程异常，用户从交付问题选择“发起现场诊断”，或在项目内新建一个只关联项目的诊断档案。
4. 诊断状态变化在项目诊断汇总中更新。它不会自动覆盖 `DeliveryIssue.status`，两边在用户确认后分别维护。
5. 每周报告基于可追溯的结构化记录快照生成草稿。用户校对状态、客户措辞和数据周期后保存/导出。

### 4.3 现场诊断闭环

1. **登记**：从交付项目/问题导入，或在诊断中心登记。系统带出项目系统类型和问题标题，允许补版本、环境、影响范围、实际/期望结果和复现步骤。
2. **预检**：选择可用 Runtime、模型和专家档案。预览展示将发送的数据摘要、来源、脱敏警告和不支持项。用户确认后才执行。
3. **分诊**：输出已知事实、信息缺口、优先级建议、业务模块/环节候选和初步假设。用户逐项确认或修正，未确认内容保留为建议。
4. **排查**：每次优先给出少量有序、安全、可验证步骤。步骤需包含目的、前置条件、预期正常信号、异常信号、所需证据、依据和安全等级。
5. **回填**：实施人员记录结果和证据。正常、异常、不确定、不适用、阻塞均需能表达；不适用和阻塞需要原因。
6. **调整路径**：有新证据时生成新计划版本，保留旧运行和步骤快照。不得把过期计划与新结论混在一起。
7. **升级或处理**：需要开发介入时生成可编辑开发草稿，用户确认后再走现有 Jira/研发流程。现场处理建议只说明人工授权动作，不执行写操作。
8. **验证关闭**：保存根因状态、解决类型、操作摘要、验证方法和结果。失败回到排查；成功后由人员确认解决/关闭。
9. **知识沉淀**：生成去敏案例草稿。审核通过前只对原项目可见；跨项目共享需审核人明确选择并确认去敏。
10. **回到项目**：项目摘要展示诊断数量、严重级别、等待客户/开发/验证状态、未分配和重开问题；周报与验收准备引用项目和诊断的真实状态。

### 4.4 角色化入口

项目经理视图按“项目例外、待决策、逾期任务、客户会议与周报”组织。实施工程师视图按负责人显示“待排查、待补证据、待客户配合、待验证”。交付负责人视图按项目健康、Critical/High、重开及长期阻塞排序。

角色视图只改变筛选、默认排序和首页入口。当前没有可信的登录身份，不能把本地显示名过滤宣传为访问控制。

| 周报与验收 | 周报、风险摘要、项目报告草稿和验收文档清单 | 生成数据快照草稿、编辑、保存、导出；显示来源时间和缺失字段；不伪造完成率或客户签收 |

### 5.3 现场智能诊断中心

| 页面 | 首屏内容 | 关键交互 |
| --- | --- | --- |
| 诊断队列 | 待分诊、排查中、等客户、等开发、待验证、重开；每行显示案件编号、项目/客户、产品版本、优先级、负责人、更新时间 | 项目/状态/系统/模块/优先级/负责人筛选；从队列新建时必须先选项目 |
| 项目问题态势 | 所有活动交付项目，包含零诊断项目；显示总量、未关闭、严重/高、等待客户/开发/验证、未分配、重开和最近更新时间 | 进入项目诊断队列；直接在项目上下文新建档案 |
| 诊断工作区 | 固定项目上下文头、案件现状、分诊、当前排查步骤、证据、根因假设、处理/验证、升级草稿、事件时间线 | 逐阶段折叠/展开；证据和引用就近查看；运行前打开预检面板；步骤结果明确选择后提交 |
| 案例审核与知识 | 草稿、待审核、已批准、拒绝/归档；项目内和跨项目共享范围清晰 | 查看脱敏内容、来源和范围；审核人批准/拒绝并留理由；批准内容进入既有检索范围 |

### 5.4 诊断工作区的交互细节

案件详情顶部固定显示项目编号/名称、客户、产品系统/版本、项目阶段/经理，以及关联交付问题标题。项目和交付问题均使用名称导航，UUID 不进入可见表单。

主体按“现场事实—分诊—排查步骤—证据—根因与处理—开发协同—活动记录”组织。每项 AI 内容都显示状态标签“AI 建议”“人工确认”或“已验证”，并可展开来源。无法验证的字段显示“未知/待补充”，不能显示为零风险。

预检侧栏展示 Runtime、供应商/模型、专家档案及版本、将提供给模型的项目/问题/证据范围、来源列表、敏感信息提示和运行警告。关闭预检或取消运行不更改案件。预览 hash 不匹配或案件输入有变化时，要求重新预检。

## 7. 技术架构与数据边界

### 7.1 分层职责

**Renderer** 负责组合页面、筛选和交互状态。不得访问 SQLite、任意路径或模型凭据。组件只消费 Preload 类型化 API。

**Preload** 暴露最小增量的交付和诊断方法。沿用现有 `deliveryWorkbench` 与 `diagnostics` 命名空间，参数和返回值用领域 DTO，不暴露通用 IPC。

**Main/IPC** 使用 Zod 校验输入，重查项目、工单、归档状态和运行配置；跨模块汇总在主进程生成。文件路径、证据读取、脱敏、Runtime 生命周期和状态迁移继续只在 Main 执行。

**Domain** 维护 `DeliveryProject`、交付实体、诊断状态/运行/步骤/证据/知识和作战舱 DTO。AI 运行快照中新增的专家/配置字段设为可选，以兼容 schema 25 已保存数据。

**LocalStore** 继续作为本地唯一数据源。第一阶段不新增项目表、项目关联表或知识检索存储。现有 JSON payload 新增可选字段可兼容旧档案；新增物理字段前先证明需要 SQL 过滤、约束或迁移原子性。

### 7.2 项目工作上下文

增加一个只读的项目作战舱汇总 DTO，由 Main 从现有 `getProject`/`DeliveryProjectBundle`、交付总览规则和诊断项目聚合组装。它不是新实体，不缓存事实状态。每次页面进入/刷新从 LocalStore 读取权威数据。

诊断建案从项目带出产品系统，且必须复核项目状态；当关联交付问题时校验该问题的 `deliveryProjectId` 与案件项目相同。项目改变时清空不再属于新项目的问题 ID。禁止用本地代码项目 ID 作为交付项目 ID。

### 7.3 Runtime 与专家中心复用

- 诊断继续通过现有受控 Runtime adapter 执行，不创建 Agent Chat Session，不读取 session 列表或历史。
- 运行选项从现有 Runtime/Settings 获取。第一版只暴露当前诊断执行器实际支持的 Runtime 类型，并列出有效供应商、模型和可用性。配置不可用时禁用执行并说明原因。
- 绝不把 API Key、Token、密码或凭据对象发给 Renderer，也不写入运行快照。运行记录可保留 Runtime 类型、供应商/模型标识、专家档案 ID、版本/hash、prompt 版本、输入/输出 hash、来源 refs 和时间。
- 选中 `ExpertProfile` 后，Main 复用现有专家解析/兼容性校验，提取工作流、步骤、来源、技能标签、输出契约和检查要求，作为诊断提示约束。先支持一个主专家档案；不借用需要 Session 的多 Agent 协作记录。
- Runtime 选择、专家档案、案件现状和来源引用共同参与输入快照 hash。执行前后若任一输入变化，旧预检失效。
- 每次调用复用现有诊断运行目录、输出结构验证、敏感扫描、来源 ID 校验和取消逻辑。失败、取消、过期和成功均保留运行记录。

### 7.4 知识与上下文

上下文顺序为当前案件事实与用户明确选择证据、当前 DeliveryProject 的已确认数据、与案件产品/版本匹配的操作手册、当前项目确认知识、同项目已批准案例、跨项目批准且去敏案例。不得因为项目关联而默认外发整份合同、所有资料或所有历史案件。

上下文预览至少说明来源名称、定位、摘要、版本或 hash、是否用户明确选择。项目文档 hash 变化或案件数据变化后重新计算预览。无匹配来源时明确显示“没有可用依据”，不伪造引用。

### 7.5 安全和生命周期

- 生产写操作、SQL 执行、远程连接和命令执行不纳入本产品接口。
- 步骤安全级别继续采用 `read_only_ui`、`read_only_evidence`、`manual_customer_action`。危险动作描述必须指出授权/变更窗口和停止条件，但不提供执行器。
- 证据沿用受管存储、大小/路径/hash 校验、脱敏和删除机制。
- 新建诊断只允许关联未归档项目；历史归档项目继续可见。项目物理删除触发外键置空时，案件改为“待关联项目”，不得丢弃诊断历史。
- 已有关联的关闭档案允许重开并保留历史运行；新计划生成新的 `planRevision`。

interface DeliveryWorkbenchApi {

interface DiagnosticApi {

## 9. 页面验收与质量要求

### 9.1 项目交付作战中心验收

- 总览指标和异常行可下钻到确切项目与记录；归档、缺日期和缺负责人不会被显示为“正常”。
- 角色预设可切换，但页面不声称是权限控制。负责人为空时进入未分配队列。
- 项目详情显示来自同一项目 ID 的诊断聚合，包括零案件项目。
- 从交付问题发起诊断只创建一次，重复点击打开同档案；从诊断返回能定位到项目和问题。
- 周报显示生成时间、覆盖周期、来源快照及缺失数据说明。草稿可编辑，未确认的模型文本不能直接定稿。
- 项目资料和 Excel 映射继续走现有入口；交付项目 ID 与本地代码项目 ID 不混用。

### 9.2 现场智能诊断中心验收

- 新建案件项目必选，产品系统与项目系统一致；项目问题只能选择当前项目下记录。
- 新建不允许选归档项目；历史案件关联的已归档项目仍显示名称和上下文。
- 诊断队列、项目态势、案件详情均显示一致的项目/工单名称与状态。
- 每次 AI 运行前展示 Runtime、模型、专家版本、来源与警告；运行历史可回看输入 hash、输出 hash、来源和结果状态。
- AI 事实、建议、人工确认、验证结果明显区分；引用无效或来源变化时拒绝或要求重跑。
- 步骤结果可以表达正常、异常、不确定、不适用和阻塞。根因未验证不能显示“已验证”。
- 开发草稿、关闭、案例审核均有明确用户确认；运行失败/取消后不丢失案件和历史。
- 全流程没有聊天 Session 依赖，也没有生产环境写操作入口。

### 9.3 工程质量

- IPC 输入继续采用严格 schema，项目/问题/证据归属由 Main 校验。
- 对新增聚合逻辑覆盖零数据、归档项目、孤立历史诊断、重复导入和状态组合。
- Runtime 与专家选择覆盖配置缺失、模型不可用、profile 被禁用/修改、预检后案件变化、取消及失败。
- 每阶段运行对应的单元/存储测试与 `npm run build`。UI 阶段再运行 `npm run test:desktop` 并人工检查宽屏和窄窗口。
- 不因重排页面改变既有存储语义、文件安全边界、诊断状态规则或交付健康统计口径。

## 10. 分阶段开发计划

### 阶段 A：共享项目上下文与导航骨架

范围：更新两个模块名称和入口；统一项目/案件上下文头；规范从总览、台账、项目、诊断之间的导航参数；建立项目级作战舱 DTO 或确认复用现有查询足够；保持现有表结构。

完成条件：全链路不依赖聊天历史；项目、问题、案件跳转正确；项目零诊断、归档项目和孤立历史档案展示正确；现有 CRUD 和入口测试通过。

### 阶段 B：项目交付作战中心

范围：重排组合总览为例外驱动；增加我的行动筛选视图；建立项目作战舱七类工作页签；强化诊断摘要与交付问题发起诊断；周报与验收仅消费现有记录和报告机制。

完成条件：核心日常巡检无需在多个全局页面间反复搜索；没有新项目实体或无依据指标；批量任务、资料导入、项目健康、报告导出行为回归通过。

### 阶段 C：现场诊断队列与专家/Runtime 选择

范围：将诊断列表变成按处置阶段组织的队列；重组案件工作区；暴露 Main 认可的 Runtime/模型选项和适用专家档案；把专家档案版本和 Runtime 选择纳入预检及运行审计；继续复用当前安全和知识上下文。

### 阶段 D：诊断到交付闭环与交付质量

范围：交付队列展示等客户/开发/验证诊断；案件关闭和重开影响项目汇总；会议行动和诊断升级草稿可人工转交；周报/验收引用项目与诊断数据；案例审核跨项目范围可视化。

完成条件：状态映射只做只读聚合，未经用户确认不自动改写另一模块的记录；重复导入稳定；报告能区分事实与未知；知识共享有审核和脱敏记录。

每个阶段单独实现、验证和汇报，通过后再启动下一阶段。若必须新增 schema migration，先提交迁移兼容和回滚说明，再进入对应阶段，不与页面调整捆绑。

## 12. 原型说明

配套文件 `精工Agent_双模块重设计_可交互原型.html` 是可直接在浏览器打开的单文件交互原型，使用演示项目和诊断案件。它覆盖作战总览、项目台账、项目作战舱、诊断队列、项目问题态势、诊断工作区、运行预检、步骤结果、开发草稿和案例审核入口。

原型交互用于确认信息架构与流程，不代表这些 UI 已经写入生产页面，也不连接真实 Runtime、数据库、文件或 Jira。功能实现按本方案第 10 节分阶段推进。
