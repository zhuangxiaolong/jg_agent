# WMS、MES5、MES6 开发规范

**版本：** V1.0  
**编制日期：** 2026-11-05  
**适用对象：** WMS、MES5（JZ.IMS）、MES6（iMES）相关的产品、架构、开发、测试、实施和运维人员

## 1. 文档定位

本规范用于统一 WMS、MES5、MES6 项目的需求分析、设计、编码、数据库、接口、测试、发布和交付要求。

本规范是团队级基线，不替代具体仓库中的 `AGENTS.md`、README、架构文档和已有实现。进入任何代码仓库后，必须先识别系统代际，再以该仓库同类代码的最新、最常用、最完整实现为准。文档、通用经验与现有代码冲突时，以现有代码和已确认的业务规则为准。

## 2. 总体原则

1. **先确认范围，再编写代码。** 需求必须明确业务对象、触发条件、状态变化、权限、异常、接口、数据范围和验收标准。
2. **先搜索，再修改。** 新增或修改控制器、服务、仓储、实体、DTO、配置和公共组件前，先查找至少 2～3 个同类实现。
3. **保持分代一致。** MES5 与 MES6 的分层、ORM、事务、配置和 SQL 习惯不得混用。
4. **业务数据可追溯。** 库存、工单、批次、序列号、过站、领退料、盘点和接口处理都必须保留必要的业务来源和操作记录。
5. **生产路径优先保守。** 产线过站、库存扣减、发料、收料、出入库和 ERP 同步属于高风险路径，改动前后都要评估查询次数、事务范围、并发行为和重试影响。
6. **证据分级。** 静态检查、编译通过、接口调用、数据库执行、现场业务闭环分别记录，不得用其中一种证据替代另一种证据。
7. **小步提交。** 一个提交只解决一个明确问题，避免无关格式化、批量重命名和大范围重构。
8. **可回滚、可诊断。** 发布包、数据库脚本、配置变更和消息契约必须有版本、校验值、回滚方式和日志定位信息。

## 3. 系统识别与边界

### 3.1 仓库识别顺序

进入仓库后按以下指纹识别系统，不按目录名称猜测：

| 识别项 | MES6（iMES） | MES5（JZ.IMS） |
|---|---|---|
| TargetFramework | `net10.0` / `net10.0-windows` | `netcoreapp3.1`，个别项目为 `2.2` |
| 解决方案 | `IMES.sln` | `JZ.IMS.sln` |
| 项目/命名空间 | `IMES.*` | `JZ.IMS.*`，特例 `IMS.JWT` |
| 入口项目 | `IMES.Web.Entry` | `JZ.IMS.WebApi` |
| ORM | 源码项目 `IMES.SqlSugar.Core` | NuGet 包 `CorePackage/JZ.IMS.Core.*.nupkg` |
| 数据库配置键 | `SqlConnection`、`DbType` | `DbOpion`、`ErpDbOpion` |

若指纹不明确，继续检查 README、入口项目、`appsettings`、命名空间和项目引用链。仍无法判断时，只提出一个最小确认问题，不得直接套用另一代实现。

### 3.2 WMS 与宿主系统的关系

WMS 是业务域，不单独决定技术栈。WMS 运行在 MES5 时，遵循 MES5 的三层架构、Dapper、手动事务和 Oracle 约定；WMS 运行在 MES6 时，遵循 MES6 的业务域分层、SqlSugar、AOP 单元事务和多数据库约定。

WMS 与 ERP、MES、WCS、PLC、条码设备的边界必须在接口矩阵中明确：数据主责方、调用方向、触发时机、幂等键、失败重试、补偿方式和对账口径均不可留空。

### 3.3 三类系统速查

| 维度 | WMS | MES5 | MES6 |
|---|---|---|---|
| 关注对象 | 库存、库位、批次、序列号、物流单据 | 生产执行、质量、设备和工单 | 生产执行、质量、设备和工单的现代化业务域实现 |
| 技术定位 | 业务域，依赖宿主系统代际 | .NET Core 3.1 + 三层架构 + Dapper/Oracle | .NET 10 + Furion + SqlSugar + 业务域拆分 |
| 事务重点 | 库存锁定、扣减、流水和单据一致性 | 手动事务边界与 Oracle/SQL Server 语义 | `SqlSugarUnitOfWorkFilter` AOP 事务与多库边界 |
| 接口重点 | ERP/MES/WCS/设备幂等、重试、对账 | 传统服务接口、配置和 DTO 映射 | 动态 Service 路由、消息、缓存和多组织 |
| 发布重点 | 接口矩阵、库存对账和现场闭环 | `dotnet build JZ.IMS.sln` 与 14 文件发布包 | 解决方案编译、业务域注册、多数据库和缓存验证 |

## 4. 需求与设计规范

### 4.1 需求最小内容

每个需求至少包含：

- 业务目标和适用组织、仓库、库区、产线或工厂；
- 角色、权限和数据范围；
- 主数据：物料、单位、仓库、库位、批次、序列号、供应商、客户、工单、产品和工艺；
- 正常流程、异常流程、撤销/反审核流程和并发场景；
- 状态机及每个状态的可执行动作；
- 外部接口、字段映射、超时、重试和对账规则；
- 数据保留、审计、报表和导出要求；
- 可验收的输入、输出和业务结果。

需求中出现“实时、自动、同步、库存准确、先进先出、禁止出库”等词语时，必须补充判定口径和验收数据，不能只保留描述性文字。

### 4.2 设计产物

复杂功能至少形成以下设计内容：

1. 业务流程图和状态流转图；
2. 数据模型和关键字段说明；
3. API/消息接口契约；
4. 权限与数据范围矩阵；
5. 异常、重试、补偿和对账方案；
6. 测试场景和验收证据清单；
7. 发布、回滚和数据脚本执行说明。

## 5. WMS 业务开发规范

### 5.1 库存模型

库存必须区分至少以下维度，并在需求和数据库中保持一致：

- 物料、组织、仓库、库区、库位；
- 库存状态：可用、冻结、待检、不良、报废、在途等；
- 批次、供应批次、生产日期、失效日期；
- 序列号（如适用）；
- 数量、辅助数量、单位和换算关系；
- 货主、供应商或客户（如适用）。

可用库存、现存库存、预留库存、在途库存和冻结库存不得用一个模糊字段代替。库存变更必须有业务单据来源、变更前后数量、操作人、时间和关联单号。

### 5.2 出入库与库存事务

- 入库必须明确收货、质检、上架和可用化的先后关系。
- 出库必须明确分配、拣货、复核、发运和扣账时点。
- 领料、退料、补料、移库、调拨、盘盈、盘亏和报废必须分别建模，禁止通过修改库存余额“绕过”业务单据。
- 同一库存扣减必须在一致的事务边界内完成校验、锁定/预留、扣减和流水写入。
- 任何库存变更接口必须具备幂等控制；客户端重复提交、消息重复投递和网络超时重试不得造成重复扣账。
- 库存不足、批次不符、效期不符、状态不允许和单位换算失败时，应返回可定位的业务错误，并保留失败原因。

### 5.3 FIFO/FEFO 与批次规则

先进先出（FIFO）或先到期先出（FEFO）必须以明确字段排序，至少说明时间字段、同时间的次级排序和人工指定批次的权限。系统不能仅按数据库默认顺序或当前页面顺序判定出库批次。

效期校验应明确生产日期、失效日期、剩余天数、临期阈值和跨时区规则。批次冻结、解冻和替代料必须记录审批或授权来源。

### 5.4 条码、序列号和设备接口

- 条码解析必须集中处理，统一大小写、空格、分隔符和前导零规则。
- 条码解析失败时，不得静默截断或猜测关键字段。
- 序列号必须保证唯一性、生命周期和归属变更可追溯。
- 与 PDA、打印机、称重设备、WCS、PLC 或自动化设备对接时，明确编码、超时、重试、重复报文和人工补录路径。
- 设备调用成功不等于库存业务成功；设备结果与业务落账必须有明确的关联状态。

### 5.5 ERP/MES/WCS 接口

接口矩阵至少包含：接口编号、提供方、消费方、方向、触发方式、请求/响应字段、业务主键、幂等键、状态映射、失败重试、补偿、对账和联系人。

接口实现必须：

- 使用参数化查询和结构化请求模型；
- 校验外部单号、组织、物料、单位和数量；
- 保存原始报文或可重建的关键摘要；
- 对超时、重复、部分成功和未知结果分别处理；
- 提供可按业务单号、接口流水号和时间范围查询的日志；
- 明确“已发送、已接收、已处理、已对账”的状态，不把发送成功当作业务完成。

### 5.6 盘点与对账

盘点必须支持盘点单、冻结范围、实盘数量、差异、复核、审批和调整流水。对账必须明确比较双方、时间窗口、业务口径和差异处理人；报表数字需标明统计时点和数据来源。

## 6. MES5（JZ.IMS）开发规范

### 6.1 技术与分层

MES5 使用 .NET Core 3.1、ASP.NET Core、SqlSugar 5.1.4、Dapper、Autofac、AutoMapper、CSRedis、Quartz 和 MongoDB 等现有基础设施。整体采用传统三层结构：

- `JZ.IMS.IServices` / `JZ.IMS.Services`：服务接口与业务服务；
- `JZ.IMS.IRepository`：仓储接口；
- `JZ.IMS.Repository.Oracle`：Oracle 主仓储实现；
- `JZ.IMS.Repository.SqlServer`：SQL Server 仓储实现（如项目启用）；
- `JZ.IMS.Models` / `ViewModels` / `MongoModels`：实体与 DTO；
- `JZ.IMS.WebApi`：API 入口与 Autofac 容器。

新增功能应进入现有业务目录和分层，不能为了一个功能引入 MES6 的 Furion 特性、DDD 五项目结构或新的依赖注入模式。

### 6.2 C# 与依赖约束

- 以 C# 8 和 .NET Core 3.1 可编译语法为准。
- 不使用 `record`、`init`、仅在新版本可用的模式匹配增强语法或项目未引入的包。
- 复用现有静态辅助类、ServiceLocator 和注入方式，除非需求明确要求替换。
- DTO 映射遵循现有 AutoMapper Profile；实体映射遵循 DataAnnotations 和现有列名大小写。
- 基础设施 `JZ.IMS.Core` NuGet 包按黑盒使用，不修改或推断包内实现。

### 6.3 Repository、SQL 与事务

- 仓储遵循 `BaseExRepository<T, TKey>` 和项目现有 Dapper 写法。
- 所有用户输入和外部输入必须参数化，禁止字符串拼接 SQL。
- 主库通常为 Oracle，SQL 使用 Oracle 方言；涉及 SQL Server 仓储时，必须检查并同步另一份实现的语义。
- 复杂查询先核对现有表、索引、关联字段和数据量，再决定 SQL 或仓储抽象方式。
- 业务写操作的手动事务边界必须完整：校验、业务写入、库存/状态变化、流水和关联写入应在同一事务内；异常必须回滚，成功后才提交。
- 不得把事务中的外部 HTTP、设备调用或长时间等待放入数据库事务，除非已有实现明确要求并评估过锁持有时间。

### 6.4 配置、日志与发布

- 主库配置使用既有 `DbOpion`，ERP 库使用 `ErpDbOpion`，并确认 `UseErp`、`UseMongoDB` 等开关。
- 不在代码中硬编码密码、Token、连接串和客户地址。
- 日志至少包含业务单号、接口流水号、组织/仓库、关键状态和异常堆栈；敏感字段必须脱敏。
- 修改对接相关代码前，先阅读 `Doc/` 下对应文档。
- API 打包前必须执行 `dotnet build JZ.IMS.sln`。按项目约定只打包指定的 14 个 API 文件，不得把 PDB、配置文件、deps/runtimeconfig 或其它未要求文件混入发布包。

## 7. MES6（iMES）开发规范

### 7.1 技术与业务域结构

MES6 使用 .NET 10、Furion、SqlSugar、Redis Cluster、RabbitMQ、SignalR、Nacos 和 Serilog 等现有基础设施。业务域通常拆分为五个项目：

```text
IMES.<Domain>.Application   # API 控制器、动态 API、业务编排
IMES.<Domain>.Domain         # Service 和核心业务逻辑
IMES.<Domain>.Models         # SugarTable 实体
IMES.<Domain>.ViewModels      # DTO、请求和响应契约
IMES.<Domain>.Enums          # 业务枚举
```

新增业务域应按现有模式补齐五个项目，并完成 `IMES.Web.Core`、入口项目的引用与注册。不要把新代码放入遗留 `BaseDDD/` 目录。

### 7.2 Service 路由与依赖注入

- 通用抽象和共享逻辑放在 `Domain/BaseServices/`；具体业务实现放在 `Domain/BizServices/`。
- 业务服务按现有 `[ClassCategory(Module = "...", Code = "...")]` 规则标记。
- 应用层通过 `Application/Services/` 下的 `*ServiceTypeMap.cs` 按编码路由到具体实现。
- 新增类型必须检查同一模块已有的 Service、TypeMap、DTO 和枚举，保持命名、返回包装和异常处理一致。

### 7.3 SqlSugar、实体与事务

- 实体使用 `SugarTable` 及项目现有基类；继承 `BaseMes` 的实体遵循多组织自动填充规则。
- 优先使用 SqlSugar Lambda，让 ORM 生成当前数据库方言；必须使用裸 SQL 时，根据 `db.CurrentConnectionConfig.DbType` 做分支。
- 不得写死 `NVL`、`SYSDATE`、`ROWNUM`、`TOP`、`GETDATE()` 等单一数据库方言。
- 事务由 `SqlSugarUnitOfWorkFilter` AOP 自动管理，Service 通常不手动 `BeginTran/Commit`。需要特殊事务边界时，先检查同模块现有实现和影响面。
- 修改公共实体、基类、拦截器或缓存逻辑前，必须搜索所有派生类和调用点。

### 7.4 查询、缓存与性能

- 远程数据库场景优先减少网络往返次数，避免 N 次串行查询；批量取数和一次性投影应以实际生成 SQL 为依据。
- 禁止使用 `db.CopyNew()` 并行化带 `WithCache` 的查询，避免缓存上下文不一致。
- 复杂 Lambda，尤其是复杂 `Contains`，必须检查生成 SQL 和实际执行计划。
- 过站主流程 `ProductOperation` 属于高风险实时路径，修改后必须确认查询次数没有增加，事务范围没有扩大。
- 写操作遵循现有 Redis/SqlSugar 缓存失效机制，不得只更新数据库而绕过缓存清理。

### 7.5 多数据库与配置

- 数据库类型由配置 `DbType` 驱动，主库和 ERP 库可能不是同一种数据库。
- 使用 `SqlConnection` 等现有配置节点，配置结构和命名跟随当前仓库。
- 所有跨库查询、同步和事务必须明确是否为同库事务；不得假设主库与 ERP 库可共享事务。

## 8. API、错误与安全规范

### 8.1 API 契约

- 请求、响应、枚举、分页和错误码优先复用项目现有契约。
- 必须校验必填项、长度、格式、范围、组织权限和数据归属。
- 写接口应返回业务单号、状态或幂等结果，避免只返回布尔值。
- 分页、排序和筛选字段必须使用白名单，禁止直接拼接客户端字段。
- 接口变更需说明兼容策略、前端影响和版本切换方式。

### 8.2 错误处理

错误分为参数错误、权限错误、业务规则错误、外部依赖错误和系统异常。对外返回可理解的错误码和消息；日志保留堆栈、关联 ID 和原始异常。不得把数据库连接串、Token、SQL 密码、内部路径或完整堆栈返回给客户端。

### 8.3 安全

- 权限控制必须覆盖菜单、按钮、API、组织、仓库和数据范围。
- 所有 SQL 使用参数化；文件上传校验扩展名、大小、内容类型和存储路径。
- 密码、Token、身份证号、手机号和客户敏感信息按现有脱敏规则处理。
- 对外接口使用 HTTPS、签名或现有认证机制；密钥从配置或密钥管理系统读取。
- 审计日志不得允许普通业务用户修改或删除。

## 9. 测试与验收规范

### 9.1 测试层次

1. **静态检查：** 编译、格式、依赖、SQL 参数和代码审查。
2. **单元/服务测试：** 状态转换、库存规则、批次效期、幂等和异常分支。
3. **接口测试：** 正常、重复提交、超时、重试、权限、边界数据和错误码。
4. **数据库测试：** SQL 可执行性、事务回滚、并发扣减、索引/执行计划和数据一致性。
5. **集成测试：** ERP、MES、WCS、设备、消息和定时任务的端到端链路。
6. **SIT/UAT/现场验证：** 使用可追踪单据和实际角色完成业务闭环。

### 9.2 关键场景

WMS 至少验证收货、质检、上架、拣货、复核、出库、移库、调拨、盘点、冻结/解冻、批次/效期、序列号、接口重复和库存不足。

MES5 至少验证 Oracle 事务、SQL Server 分支（如启用）、服务映射、AutoMapper、定时任务、接口重试和发布包内容。

MES6 至少验证动态 Service 路由、AOP 事务、多数据库方言、组织字段自动填充、缓存失效、消息重复和过站主流程查询次数。

### 9.3 证据记录

每项验证记录环境、版本/提交号、输入单据或参数、执行时间、结果、日志/响应/数据库截图或导出文件路径。必须明确：

- “编译通过”不等于“接口可用”；
- “接口返回成功”不等于“数据库已正确落账”；
- “数据库落账”不等于“ERP/MES/WCS 已完成闭环”；
- “测试环境通过”不等于“生产已部署并验收”。

## 10. Git、评审与发布规范

### 10.1 分支与提交

- 默认分支命名使用 `codex/` 前缀，或遵循项目已存在的分支规则。
- 提交信息使用中文，一句话说明改动，例如：`修复设备过站报错"Value cannot be null.(Parameter 'source')"`。
- 提交前检查 `git status`、差异、目标文件清单和敏感信息；不得提交密码、Token、客户生产数据和临时文件。
- 保留用户已有提交信息，不随意改写历史；只暂存需求相关文件。

### 10.2 Code Review

评审至少检查：

- 是否符合当前系统代际和模块既有实现；
- 是否扩大事务、查询次数、锁范围或接口重试风险；
- 是否覆盖权限、组织、仓库、批次、状态和幂等；
- 是否存在 SQL 注入、敏感信息泄露和日志噪声；
- 是否有数据库脚本、配置、回滚和发布说明；
- 测试证据是否与声明范围一致。

### 10.3 发布与回滚

发布包、数据库脚本、配置和接口契约必须一一对应版本。发布前确认备份、停机/不停机策略、脚本顺序、灰度范围、健康检查和回滚命令。数据库脚本涉及结构或数据时，必须提供反向脚本或明确不可逆原因，并先在验证环境执行。

## 11. Definition of Done（完成定义）

一个开发项只有同时满足以下条件，才可标记为“开发完成”：

- 需求范围、业务规则和验收标准已确认；
- 代码符合当前仓库分层、命名、依赖和数据库约定；
- 权限、组织/仓库数据范围、异常、幂等和审计已处理；
- 相关 SQL、接口、消息、配置和脚本已审查；
- 已执行适用的编译和自动化测试；
- 关键业务场景完成接口或集成验证；
- 数据库、日志、缓存、消息和外部系统结果可追踪；
- 发布包、变更清单、回滚方式和测试证据已归档；
- 已知限制、未验证事项和待客户确认项已明确标注。

“代码已提交”“接口返回 200”“测试数据成功”只能证明局部完成，不能单独作为上线、验收或生产闭环依据。

## 12. 快速检查清单

### 开发前

- [ ] 已确认仓库属于 MES5、MES6，或明确为 WMS 宿主模块
- [ ] 已阅读同目录 2～3 个同类实现
- [ ] 已确认数据库类型、事务方式、配置键和接口边界
- [ ] 已明确权限、组织/仓库范围、状态机和幂等键

### 开发中

- [ ] 未混用 MES5/MES6 的架构、ORM、事务和配置写法
- [ ] SQL 已参数化，并检查了方言、索引和查询次数
- [ ] WMS 库存变更有单据来源、流水和并发控制
- [ ] 外部接口有超时、重试、重复和对账处理
- [ ] 日志可按单号、接口流水号或关联 ID 定位

### 提交与发布前

- [ ] 已完成适用的 build、单元/接口/集成测试
- [ ] 已区分静态、接口、数据库和业务闭环证据
- [ ] 已检查差异、敏感信息、脚本和发布文件清单
- [ ] 已准备回滚方案、配置说明和测试证据
- [ ] 已标记所有未验证、待确认和环境相关限制
