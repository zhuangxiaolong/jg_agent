# 04｜分阶段开发计划与交付要求

## 总体原则

- 先读代码和测试，再修改。
- 一次只推进一个阶段；阶段完成后 build/test，通过验收后再进入下个阶段。
- 任何涉及同一文件的任务必须串行；不得让多个 Agent 同时修改 `App.tsx`、`performance-service.ts`、`telemetry.ts`、`PerformancePanel.tsx` 等公共文件。
- 可以并行的任务仅限完全隔离的文件范围，例如先分别编写组件样式草案，但最终集成需由一个 Agent 负责。
- 不以“代码已写完”作为完成标准，以真实构建、测试与 UI 验收为准。

## 阶段 0｜只读架构审查（不改代码）

### 任务

1. 检查目标分支最新 HEAD、README 版本、package scripts 和 AGENTS.md。
2. 阅读本开发包全部文档。
3. 重新检查：
   - `packages/performance/src/types.ts`
   - `packages/performance/src/telemetry.ts`
   - `packages/performance/src/context-retrieval.ts`
   - `packages/performance/src/context-optimizer.ts`
   - `packages/performance/src/workspace-index.ts`
   - `apps/desktop/src/main/performance-service.ts`
   - `apps/desktop/src/main/index.ts`
   - `apps/desktop/src/renderer/App.tsx`
   - `apps/desktop/src/renderer/PerformancePanel.tsx`
   - `apps/desktop/src/renderer/performance.css`
   - `apps/desktop/src/preload/index.ts`
   - `packages/domain/src/index.ts`
   - `packages/storage` 中 PerformanceState 读写实现与迁移。
   - RunLifecycle、AgentTaskRunner、VerificationRun 的真实 ID、生命周期和关联字段。
4. 核对 Claude Agent SDK、Codex、Jinggong、Grok 各 Adapter 的 RuntimeEvent 能力。
5. 输出《1.0 源码差距审查报告》，说明：已有能力、缺失能力、改动文件、迁移风险、不可采集指标。
6. 不要修改任何代码，不新增文件，不生成 Mock 证明。

### 阶段 0 验收

- 给出当前 HEAD SHA 与版本。
- 每个需求有明确的现有代码位置或标记「仓库中未找到」。
- 不把推断写成事实。
- 没有代码变更。

## 阶段 1｜Trace 身份、项目绑定与上下文快照（P0）

### 目标

先打通数据链路，确保每轮 Trace 能绑定本轮任务和当前 Session 的 Project/Workspace，并准确记录本轮上下文快照。

### 任务

1. 在现有 `PerformanceTrace` / `PerformanceReport` 上做最小增量扩展，支持 turn/run/project/repository/workspace/worktree 关联字段。
2. 将 Trace 从“以 Session 为单位的当前记录”明确为“一轮用户提交一条 Trace”。保留按 sessionId 查询历史列表的能力。
3. 审查 RunLifecycle 的真实 Run ID/Turn ID，从实际可得点传入。不能编造 ID；字段暂时缺失就留空。
4. 修正 `DesktopPerformanceService.identity()` 对独立会话的身份语义，确保没有 projectId 时不冒充 repositoryId。
5. 保存当前 Session 项目绑定快照；Project 必须按 session.projectId 精确解析。
6. 在 Context Retrieval/Optimizer 的最终结果处保存 selected/excluded/sourceCounts/token stats，不要在 Renderer 重新扫描。
7. 为必需上下文和可选来源上下文保留可解释统计；估算口径标识为 `estimated`。
8. 检查 `performanceService.finish()` 的时点；如需将验证阶段计入 Trace，先确认运行顺序，再调整；否则验证保持独立 Run 关联。
9. 若 PerformanceState schema 从 v1 升级，新增安全迁移和旧记录兼容测试。

### 交付

- 修改后的领域类型、服务和存储兼容逻辑。
- Trace Context Snapshot 可通过现有 `performance:report` 返回。
- 单元测试：一轮一 Trace、Project 关联、独立会话、跨 Session 隔离、旧数据迁移。

### 阶段 1 禁止

- 不做大规模 UI 改版。
- 不开始采集完整 prompt、消息正文或原始工具参数。
- 不擅自新增模型 Token 推算逻辑。

## 阶段 2｜Context Inspector UI（P0）

### 目标

把右侧「上下文」从静态环境信息改造成当前 Session + 当前 Trace 的上下文分析面板。

### 任务

1. 从当前 Session 的 `session.projectId` 精确查找 Project；不得使用左侧当前选中 project 对象作为 Session 项目。
2. 将 Project Root、Workspace Path、Worktree Path 分开呈现。
3. 未关联 Project 时显示「独立会话」和当前工作目录，不显示虚假的 Git 项目目录。
4. 展示 Runtime、Provider、Model、Reasoning、Endpoint host。
5. 展示应用侧上下文预算：required/optional/total estimated tokens、budget、overflow、dedupe、trim、cache 和检索耗时。
6. 若真实 Usage 有来源，独立展示；无数据则如实显示不可用。
7. 展示本轮 selected/excluded 来源清单和理由。
8. 保留当前已启用开发规范/字典的管理入口；区分可用资料和本轮实际加载资料。
9. 完成 loading/empty/error/unavailable/standalone/project-bound 状态。
10. 保证切换 Session 后旧数据立即清理。

### 交付

- Context Inspector 组件与样式。
- UI 测试或可复现的人工验收步骤。
- 真实项目 Session、独立 Session、无 Trace 三种界面状态截图或测试记录。

## 阶段 3｜Execution Monitor 事件与工具调用（P1）

### 目标

把执行监控升级为有稳定调用关联的执行时间线和工具调用列表。

### 任务

1. 检查 Runtime Adapter 上报 `RuntimeEvent.performance` 的覆盖情况。
2. 基于 `callId` 配对 started/completed，统计唯一 Tool Call。
3. 处理 missing ID、start only、complete only、duplicate、终态未完成等异常序列。
4. Trace/Span 增加必要的 correlationId/parentSpanId，不改变 Runtime 工具权限。
5. 增加执行总览卡片与时间线。
6. 显示首个可见响应，不能误标「模型首 Token」。
7. 保留事件通知数，和真实调用数分开。
8. 展示不可采集指标说明。
9. 只在 Runtime/Provider 提供真实 usage 时显示 Token Usage。
10. 对事件量和报告大小做上限控制。

### 交付

- Runtime Event->Telemetry 映射。
- ToolCallSummary 数据和列表 UI。
- 多种 Runtime 的能力差异记录。
- 事件重复、乱序、丢失、取消、失败测试。

## 阶段 4｜Agent 执行树与验证摘要（P1）

### 目标

展示本轮明确关联的子 Agent 和真实验证数据。

### 任务

1. 识别当前 AgentTaskRunner 的 parent/orchestration/run/turn 关联字段。
2. 将当前轮新建 AgentTask 与 Trace 关联；历史任务不自动加入。
3. 明确分组：`platform_agent_task` 与 `runtime_native_agent`。
4. 仅展示任务摘要、角色、状态、耗时、Runtime/Model（有真实字段时）。
5. 调查当前自动 build/test 的触发点和 RunLifecycle 记录，确定验证是否能关联当前 Trace。
6. 对未关联验证记录明确标识，不允许将其展示成“本轮已通过”。
7. 完成 Agent 执行树、验证摘要两个区域。

### 交付

- AgentExecutionSummary 和 VerificationSummary 数据。
- 无 Agent、无验证、仅历史任务、当前轮有子任务/验证的测试。

## 阶段 5｜集成、回归与交付（P0）

### 任务

1. 回归 Codex、Claude Agent SDK、Jinggong、Grok Runtime 基本聊天/工具流程。
2. 回归 Context Retrieval 关闭、性能开关关闭、索引失败时的 fallback。
3. 回归项目切换、独立 Session、Worktree、Session 切换和历史 Trace 查看。
4. 回归性能设置、导出、诊断导出、索引重建和测试计划功能。
5. 检查 320px、420px、840px 右侧面板宽度。
6. 真实执行 build、test、desktop test；日志和报告放到应用 verification 目录，不能写入项目源码目录。
7. 输出变更文件、真实执行命令、退出码、未执行项和已知限制。

### 完成交付标准

- 全部必测项通过。
- 没有 Mock 冒充真实 Runtime 数据。
- 没有破坏现有性能策略与 Runtime 执行。
- 1.0 UI 里所有指标都注明真实、估算或不可用。
- 文档与实际代码一致。

## 建议开发分支策略

- 从 `develop/desktop-poc` 最新 HEAD 创建独立分支，例如 `feature/runtime-observability-1.0`。
- 每阶段形成一个可审查提交；不要直接在用户主要工作分支上做未经验证的大改。
- 如果用 Codex 子 Agent：阶段 0 可让独立 Agent 做只读审查；代码阶段由主 Agent 负责跨模块集成。只允许在文件范围完全隔离时并行开发。
- 不要同时让 Claude Code 和 Codex 改相同工作区；需要交叉审查时使用只读模式或独立 Worktree。
