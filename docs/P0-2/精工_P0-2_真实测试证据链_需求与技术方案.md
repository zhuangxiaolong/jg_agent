## 0. 给 Codex 的实施约束

本文件是目标需求，不代表当前代码中已经存在相应模块、表结构或目录。实现前必须先检查仓库，不得直接按本文假设创建重复架构。

1. **先勘察，后设计，最后修改。** 检查当前项目使用的桌面框架、主进程/渲染进程边界、SQLite 数据访问方式、Codex Runtime 调用方式、命令执行封装、Git 服务、测试服务、Markdown 报告生成器和现有测试。先输出一份简短的现状映射，再提出最小改动方案。
2. **优先复用现有能力。** 如果已有命令执行服务、会话事件、Git 状态采集、报告组件或数据库迁移体系，应扩展现有实现，不应另造一套平行流程。
3. **不能伪造当前能力。** 不得把应用级模拟测试描述成真实项目端到端验收；不得把 Agent 自述作为测试通过的证据。
4. **状态由应用端计算。** LLM 只能生成解释性摘要或建议，不能直接指定测试状态、测试数量、Exit Code、运行时间或证据哈希。
5. **渐进兼容。** 旧会话、旧测试报告和既有 SQLite 数据必须可读；数据库升级应有迁移和回滚/备份策略。
6. **保护用户现场。** 测试命令不得默认清理、重置或覆盖用户文件；执行前后必须采集 Git/工作区状态。
7. **每个里程碑均补测试。** 至少覆盖纯单元测试、命令执行集成测试、报告生成测试和桌面冒烟测试。不要只以 `npm run build` 作为验收。
8. 若现有 Runtime 无法提供可靠的进程执行回调或工作区标识，先明确技术限制并提供适配方案，不得通过解析模型聊天文本假装拥有执行证据。

### 0.1 本轮交付物

- 本文要求的功能设计和技术实现。
- 数据库迁移及必要的本地证据文件存储。
- 测试执行采集、结果解析、状态判定和报告生成能力。
- 现有测试工作流接入新证据模型。
- 自动化测试及桌面验证记录。
- 简短的实现说明：修改文件、迁移方式、兼容性、未完成项和验证结果。

# 第一部分：产品需求方案

## 1. 背景与问题

精工当前已经具备构建/测试工作流，并能生成 Markdown 测试结果。但“能生成报告”不等于“报告中的结果真实”。如果状态来自 Agent 对自己执行过程的总结，就可能出现：

- 测试实际没有执行，报告却显示通过。
- 命令执行失败，但 Agent 根据部分输出总结为通过。
- 测试统计数字由模型生成，无法找到原始测试结果。
- 测试完成后代码又发生变化，旧测试结果仍被当成当前结果。
- 测试命令、执行目录、项目版本和日志没有保存，无法复核。
- 构建通过被误认为测试通过，或者跳过测试被误认为通过。
- 应用异常退出后，测试已执行但结果没有可靠归档。

本需求要建立一条由桌面应用控制的证据链：

**当前工作区快照 → 应用发起真实命令 → 采集进程结果 → 解析机器可读测试结果 → 校验代码是否变化 → 生成确定性状态 → 固化报告与证据。**

## 2. 产品目标

### 2.1 目标

1. 测试状态只能由应用采集到的真实执行结果计算。
2. 每个测试结果都能追溯到任务、会话、项目、Worktree、Git 状态和实际执行命令。
3. 用户可以查看原始日志、测试摘要、解析结果和证据文件。
4. 测试结论与被测代码版本绑定；代码发生变化后，旧结论自动变为过期。
5. 区分构建、测试、静态检查等不同验证类型，不混为一个“通过”。
6. 遇到执行中断、解析失败、环境异常或证据缺失时，宁可显示“无法判定”，也不能乐观显示通过。
7. 现有 Markdown 测试报告继续可用，但报告中的状态和统计数字由结构化证据生成。

### 2.2 非目标

本阶段不做：

- 不实现完整 CI/CD 平台。
- 不承诺任意客户 MES/WMS 项目都能自动构建或测试。
- 不自行生成或虚构测试用例来证明代码正确。
- 不把模型的代码 Review 结论当作自动化测试证据。
- 不宣称本地证据对拥有机器管理员权限的人绝对不可篡改。
- 不把测试通过等同于客户验收、生产上线或业务正确性。
- 不在本需求中重做 P0-1 的操作系统级沙箱；但执行命令时必须沿用当前权限控制，并避免扩大权限。

## 3. 用户与典型场景

### 3.1 目标用户

- MES5、MES6、WMS 开发人员。
- 需要复核 AI 修改和测试结果的开发负责人。
- 需要查看 Jira 任务交付证据的项目经理/交付负责人。

### 3.2 典型场景

开发人员通过精工处理 Jira 任务，Agent 修改代码后，用户在“构建与测试”区域选择项目验证配置并执行。精工实时展示执行状态，结束后生成带有执行命令、Exit Code、测试统计、日志、代码版本标识的报告。用户确认后再将测试说明反馈 Jira。

## 4. 核心概念与术语

| 概念 | 定义 |
|---|---|
| 验证运行（Run） | 应用发起的一次构建、测试或静态检查进程执行 |
| 验证套件（Suite） | 某个项目配置的一组验证命令，如后端测试、前端测试 |
| 执行证据（Evidence） | 应用采集的命令、进程结果、日志、解析文件、代码快照等 |
| 工作区指纹（Workspace Fingerprint） | 执行前后用于识别当前代码状态的稳定摘要 |
| 原始证据 | 从实际进程采集的 stdout/stderr、机器可读结果文件及元数据 |
| 派生报告 | 根据结构化证据自动生成的 Markdown/界面报告 |
| 过期证据（Stale） | 测试完成后，被测工作区发生变化，原结果不再代表当前代码 |
| 无法判定（Indeterminate） | 执行或解析证据不足，不能可靠判定通过或失败 |

## 5. 用户流程

### 5.1 标准流程

1. 用户选择项目/会话/工作区。
2. 精工采集执行前工作区状态：仓库、分支、HEAD、暂存/未暂存/未跟踪文件摘要。
3. 用户选择一个已配置的构建或测试套件，或确认 Agent 提议的命令。
4. 精工通过应用端统一执行服务启动进程。
5. 执行过程中实时展示运行中状态、输出摘要、已用时间；允许用户取消。
6. 执行结束后，应用采集 Exit Code、开始/结束时间、超时/取消状态、日志和测试结果文件。
7. 对机器可读报告进行解析，计算通过、失败、跳过数量。
8. 采集执行后工作区指纹，并与执行前指纹比较。
9. 应用按规则计算状态，不接收 LLM 对状态的覆盖。
10. 生成报告并保存证据；用户查看详情、复制摘要或导出 Markdown。
11. 后续代码变化时，历史结果保留，但当前状态标记为“已过期，需要重新验证”。

### 5.2 异常流程

- 用户取消、应用退出、命令超时、进程启动失败：保留已采集到的部分信息，状态不可为通过。
- 没有生成机器可读测试报告：若该套件要求解析报告，标记无法判定；不得仅凭模型总结通过。
- 测试报告格式损坏/统计冲突：标记无法判定，并展示解析错误。
- 执行期间代码变化：标记无法判定或证据冲突，要求重新执行；不得把结果绑定到不确定的代码快照。
- 执行结束后代码变化：证据保留，状态标记为已过期。
- 测试数量为 0：默认不能判定通过；只有管理员显式配置“允许零测试”并给出原因时，才可按特殊规则处理，默认仍建议标为无法判定。

## 6. 功能需求

### EVD-001：统一验证运行入口

- 构建、测试、静态检查等任务必须通过统一的应用端执行服务启动。
- 每个 Run 必须有唯一 ID，并关联项目、会话、工作区、Jira Issue（若有）、Runtime 会话（若可获取）。
- 执行配置应具有明确类型：`build`、`test`、`lint`、`typecheck`、`custom` 等。
- 每个命令必须记录可展示的 executable、参数、工作目录和配置来源。
- 不允许由 LLM 自己填写执行成功状态。

### EVD-002：执行前工作区快照

执行前应记录：

- 项目标识、仓库根目录（展示时进行必要脱敏）。
- 当前分支名、HEAD Commit SHA。
- Git 是否干净。
- 暂存、未暂存、未跟踪文件清单及摘要。
- 子模块状态（若仓库使用子模块且当前实现可读取）。
- 计算出的 Workspace Fingerprint。

不得将用户原有未提交变更错误标记为 Agent 本轮变更。需要区分：会话开始时已有变更、Agent 修改、用户在会话期间新增变更。

### EVD-003：真实进程执行采集

应用执行层至少采集：

- 进程启动是否成功。
- 实际 executable/参数（保存脱敏后用于展示的版本；不可保存明文密钥）。
- 工作目录。
- 开始时间、结束时间、耗时。
- 退出码（Exit Code）。
- 是否超时、取消或被系统终止。
- stdout、stderr 日志文件及大小。
- 执行期间的进程状态。

技术要求：

- stdout/stderr 应流式写入文件，避免长输出撑爆 UI 或内存。
- UI 展示内容设置合理上限；完整日志通过文件或分页查看。
- 设置最大运行时长和日志大小策略；达到上限时应停止/截断并明确记录，不能悄悄丢失。
- 取消操作应尝试终止进程树，而非只关闭 UI 状态。
- 应用重启后，未完成 Run 需被识别为中断/状态未知，不能自动恢复成成功。
- 对环境变量只保存变量名及必要的非敏感信息；密钥、Token、密码不得进入证据数据库或报告。

### EVD-004：测试报告解析器

首期至少支持当前项目真实使用的测试框架。Codex 必须先盘点仓库和项目，再确定首期解析器清单，不得仅凭本文臆测项目语言。

建议优先适配：

- JUnit XML（Java、部分 .NET/Node 工具可输出）。
- TRX（.NET/VSTest）。
- NUnit XML（若现有项目使用）。
- 当前仓库已使用且能稳定产生机器可读结果的其他格式。

每个解析器应输出统一结构：

- total、passed、failed、skipped、errors（可选）。
- 测试名称、测试套件、失败原因和堆栈（可选）。
- 报告文件路径、文件哈希、解析器名称和版本。
- 解析是否完整、是否存在格式错误。

要求：

- 解析器是确定性代码，不依赖 LLM。
- 同一份报告重复解析应产生相同结果。
- 统计不一致、报告为空、零测试、报告格式异常必须有明确状态。
- 同一次 Run 产生多个报告时，应有去重和汇总策略，不能重复计算同一测试。
- 解析失败不能用 stdout 中出现的“PASS”“success”等字样替代机器可读证据。

### EVD-005：确定性状态判定

状态至少包括：

| 状态 | 含义 | 能否显示为通过 |
|---|---|---|
| `passed` | 命令真实执行，满足该验证类型的通过条件，证据完整，工作区指纹有效 | 是 |
| `failed` | 真实执行，但 Exit Code 非零或测试结果存在失败/错误 | 否 |
| `not_run` | 尚未执行，或没有对应 Run | 否 |
| `indeterminate` | 执行中断、无法解析、证据不完整、代码快照不一致等 | 否 |
| `stale` | 原本有结果，但当前工作区已变化 | 否（需重新执行） |

可另设 `cancelled` 作为执行过程状态，但最终验证结论仍不得为通过。

#### 通过规则（必须在代码中落实）

测试 Run 只有同时满足以下条件，才可标记 `passed`：

1. 进程真实启动并正常结束。
2. 未取消、未超时、未被异常终止。
3. Exit Code 为 0。
4. 对于配置为“必须解析测试报告”的套件，至少有一份有效机器可读报告。
5. 解析结果没有 failed、errors 或其他失败项。
6. total 大于 0；若确实允许零测试，必须由项目配置明确声明并显示提示。
7. 执行前后工作区指纹一致，或者使用明确的受控策略能证明测试对应同一份代码。
8. 证据文件完整且哈希校验通过。

若套件是纯构建命令，则只能将**构建验证**标记为通过，不能生成“测试通过”结论。

若测试命令没有有效测试结果解析器，默认标记为 `indeterminate`，可显示“命令执行成功，但测试结果未被机器验证”，不能显示整体测试通过。

#### 汇总规则

- 任何必需测试套件失败：整体失败。
- 所有必需套件均通过且证据完整：整体通过。
- 存在未执行的必需套件：整体未完成/未执行，不可通过。
- 存在无法判定的必需套件：整体无法判定。
- 代码发生变化：整体过期。
- 非必需套件的失败需显示，但不应被隐藏；是否影响整体状态由项目配置明确决定。

### EVD-006：工作区指纹与证据新鲜度

需要设计稳定且计算成本可控的 Workspace Fingerprint。建议组合：

- HEAD Commit SHA。
- Git 暂存区 Diff 摘要。
- Git 未暂存 Diff 摘要。
- 未跟踪文件内容哈希清单（排除明确配置的缓存/构建产物）。
- 子模块状态摘要（适用时）。

可基于规范化文件清单和内容 SHA-256 生成总指纹。实现前评估大型仓库的耗时，并提供缓存/增量方案。

必须记录：

- `fingerprint_before`：执行前。
- `fingerprint_after`：执行完成后。
- `fingerprint_current`：用户查看时按需重新计算。

规则：

- before 与 after 不同：本次 Run 期间工作区发生变化，结果不能直接作为可信的当前代码验证。
- after 与 current 不同：证据标记为 `stale`。
- 如果工作区在测试进程运行期间被 Agent 或用户并发修改，应显示明确提示，并建议隔离/停止后重新运行。

注意：工作区指纹证明的是代码状态摘要，不代表测试覆盖充分，也不代表业务逻辑正确。

### EVD-007：证据文件存储与完整性校验

每次 Run 的证据建议独立目录存放，具体路径遵循当前应用的数据目录约定，不得硬编码用户目录：

```text
<app-data>/evidence/<project-id>/<session-id>/<run-id>/
  manifest.json
  stdout.log
  stderr.log
  test-results/...
  parsed-summary.json
  report.md
```

要求：

- 所有证据文件生成 SHA-256。
- manifest 保存各文件相对路径、大小、MIME/格式、哈希和产生时间。
- 数据库记录 Run 与 manifest 的关联。
- 路径必须做规范化和目录穿越防护。
- 证据目录不能因删除会话 UI 数据而被静默部分删除；删除前提示并按现有产品数据保留策略处理。
- 对重要证据可增加本地 HMAC/签名清单：密钥放 Windows DPAPI 等安全存储；密钥不可明文落盘。
- 采用追加式事件/记录，不直接覆盖历史 Run；修正结果应新增事件或新 Run。

**诚实边界：** 本地哈希/HMAC 能提高篡改可发现性，但若攻击者拥有本机管理员权限且能控制应用与密钥，不应宣传为绝对不可篡改。产品文案使用“可校验、可追溯、篡改可发现”，不使用“绝对防伪”。

### EVD-008：确定性 Markdown 报告

报告由应用模板生成，LLM 只允许提供可选说明，且必须与系统字段分区展示。

建议报告结构：

1. 任务信息：项目、Jira、会话、运行 ID。
2. 验证结论：构建状态、测试状态、静态检查状态分别显示。
3. 代码版本：分支、HEAD SHA、Workspace Fingerprint。
4. 实际执行：命令、工作目录、起止时间、耗时、Exit Code。
5. 测试统计：总数、通过、失败、跳过、错误。
6. 失败详情：测试名、错误摘要、日志定位。
7. 证据附件：原始日志、机器可读报告、manifest 哈希。
8. 环境说明：项目工具链版本（仅采集实际存在的信息）。
9. 局限声明：未执行项、环境限制、未覆盖范围。

不得使用笼统的“全部测试通过”覆盖未执行项、跳过项、无法判定项。

### EVD-009：测试证据界面

在现有构建/测试 UI 中扩展，尽量复用现有视觉和布局。

建议包含：

- 当前结论状态及明确文字。
- 构建、单元测试、集成测试、静态检查分项卡片。
- 运行命令与耗时。
- 测试数量统计。
- 代码指纹/Commit 信息。
- 原始日志查看/复制/导出。
- 解析报告查看。
- 历史 Run 列表。
- 过期状态提示及“重新执行”入口。
- 证据不完整时给出具体原因，不只显示红色错误图标。

状态展示文字建议：

- 通过：`已执行并通过（N 项）`
- 失败：`执行失败（失败 N 项 / Exit Code X）`
- 未执行：`未执行`
- 无法判定：`执行完成，但缺少有效测试证据`
- 已过期：`代码已变化，当前结果需要重新验证`

### EVD-010：Jira/会话关联

- Run 可关联当前 Jira Issue 和会话。
- 导出 Jira 测试说明时，只引用系统确认的状态和统计。
- Jira 写入功能继续走现有确认流程；本需求不自动改变 Jira 状态。
- Jira 写入结果与本地证据 Run 分开记录，不能把“本地报告生成成功”显示成“Jira 已写入成功”。

### EVD-011：历史数据兼容

- v0.6.8 及以前的历史 Markdown 测试报告不能被自动升级成真实证据。
- 对无结构化执行记录的历史报告标记为“历史报告（未验证证据）”。
- 新旧数据在界面和导出内容中明确区分。

## 7. 验收标准

### 7.1 功能验收

| ID | 场景 | 预期结果 |
|---|---|---|
| AC-EVD-01 | 测试命令 Exit Code=0，JUnit/TRX 有效且全部通过 | 状态 passed，统计正确，报告可追溯 |
| AC-EVD-02 | 测试命令 Exit Code 非 0 | 状态 failed，保留日志和失败摘要 |
| AC-EVD-03 | Agent 声称通过但没有实际 Run | 状态 not_run，不允许生成通过结论 |
| AC-EVD-04 | 命令 Exit Code=0，但没有要求的机器可读报告 | 状态 indeterminate |
| AC-EVD-05 | 解析报告显示失败，即使 stdout 中包含 success | 状态 failed |
| AC-EVD-06 | 测试报告为空或 total=0 | 默认 indeterminate，不得通过 |
| AC-EVD-07 | 测试运行期间工作区变化 | 状态 indeterminate，提示快照不一致 |
| AC-EVD-08 | 测试结束后修改任意纳入指纹的源文件 | 历史 Run 标记 stale |
| AC-EVD-09 | 用户取消/超时/应用崩溃 | 不得显示 passed，留下中断记录 |
| AC-EVD-10 | 用户打开历史 Run | 可查看命令、Exit Code、日志、测试统计和哈希 |
| AC-EVD-11 | 修改 manifest 或证据文件 | 校验提示完整性异常 |
| AC-EVD-12 | 旧历史报告 | 显示历史未验证，不伪装成新证据 |
| AC-EVD-13 | 只有构建通过，没有测试 Run | 构建可通过，测试必须显示未执行 |
| AC-EVD-14 | 多个必需套件中一个失败/未执行 | 整体不能显示全部通过 |
| AC-EVD-15 | 原始日志包含疑似密码/Token | 报告和证据中按规则脱敏，不保存执行环境中的明文凭据 |

### 7.2 质量门槛

- 状态判定规则具备完整单元测试。
- 解析器具备有效、失败、空文件、损坏文件、重复报告、零测试等测试样本。
- 执行服务具备超时、取消、进程启动失败、非零退出码、长日志和应用异常退出测试。
- 桌面 UI 的状态与数据库结构化状态一致。
- `npm run build`、`npm test`、`npm run test:desktop`（以仓库实际脚本为准）通过。
- 不接受任何“未执行但显示通过”的回归缺陷。

## 8. 权限与安全要求

1. 测试命令执行复用现有命令执行服务，不绕过权限策略。
2. 未经用户确认，不自动执行破坏性命令、生产数据库操作或会修改工作区以外文件的命令。
3. 执行命令参数与工作目录做安全校验，避免路径注入和命令拼接风险。
4. 不把 Token、密码、连接串、环境变量秘密值写入日志、数据库或 Markdown。
5. 证据目录仅通过应用 API 访问，不允许 UI 任意拼接路径读取本地文件。
6. 删除证据应有明确确认和产品级保留策略。
7. 不能将“哈希校验通过”宣传成操作系统级安全沙箱或不可篡改存证。

# 第二部分：技术方案

## 9. 技术设计原则

- **Host is source of truth：** 进程、退出码、时间、文件和 Git 状态由桌面应用主执行层采集。
- **LLM is not source of truth：** 模型输出不参与状态判定。
- **Immutable run record：** 一次 Run 结束后保留原始证据；新执行产生新 Run。
- **Deterministic evaluation：** 结果解析和状态聚合是确定性代码。
- **Workspace-bound evidence：** 每条证据绑定代码指纹。
- **Fail closed：** 缺少关键证据时不判通过。
- **Backward compatible：** 通过数据库迁移及适配层兼容旧报告。

## 10. 建议架构

应根据仓库现有分层映射以下职责，不要求照搬模块名：

```text
Renderer / UI
  ├── VerificationPanel
  ├── RunHistory
  ├── EvidenceDetail
  └── ReportPreview
          │ IPC / typed bridge
          ▼
Desktop Main Process / Application Services
  ├── VerificationOrchestrator
  │     ├── WorkspaceSnapshotService
  │     ├── CommandExecutionService（优先复用）
  │     ├── TestResultParserRegistry
  │     ├── EvidenceIntegrityService
  │     ├── VerificationPolicyEngine
  │     └── MarkdownReportGenerator
  ├── GitService（优先复用）
  ├── ProjectProfileService
  └── EvidenceRepository
          │
          ├── SQLite（结构化元数据）
          └── Local Evidence Store（日志及报告文件）
```

### 10.1 模块职责

**VerificationOrchestrator**

- 编排一个 Run 的完整生命周期。
- 校验项目、工作区、套件配置。
- 获取执行前快照。
- 请求命令执行服务执行。
- 调用解析器。
- 获取执行后快照。
- 调用规则引擎计算状态。
- 保存证据并生成报告。

**CommandExecutionService**

- 启动子进程并流式采集 stdout/stderr。
- 处理取消、超时、进程树终止。
- 返回真实的进程结果。
- 不负责判断测试是否通过。

**TestResultParserRegistry**

- 根据报告格式选择解析器。
- 将不同格式转换为统一数据结构。
- 返回解析错误和原始文件引用。

**VerificationPolicyEngine**

- 根据 Run 类型、Exit Code、进程状态、解析结果和指纹计算状态。
- 不接收模型提供的状态字段。

**EvidenceIntegrityService**

- 生成文件 SHA-256、manifest 和可选 HMAC。
- 读取时校验完整性。

**MarkdownReportGenerator**

- 根据结构化证据生成 Markdown。
- 禁止将 LLM 文本覆盖结构化结论。

## 12. 结果状态计算伪代码

以下伪代码用于说明规则，实际实现应遵循项目语言和代码规范：

```ts
type VerificationStatus =
  | 'passed'
  | 'failed'
  | 'not_run'
  | 'indeterminate'
  | 'stale';

function evaluateTestRun(input): VerificationStatus {
  if (!input.runExists) return 'not_run';
  if (!input.processStarted) return 'indeterminate';
  if (input.cancelled || input.timedOut || input.crashed) return 'indeterminate';
  if (input.exitCode === null || input.exitCode === undefined) return 'indeterminate';
  if (input.exitCode !== 0) return 'failed';
  if (input.requireMachineReport && !input.parseResult) return 'indeterminate';
  if (input.parseResult?.status !== 'parsed') return 'indeterminate';
  if (input.parseResult.errorCount > 0 || input.parseResult.failedCount > 0) return 'failed';
  if (input.parseResult.totalCount <= 0 && !input.allowZeroTests) return 'indeterminate';
  if (!input.evidenceIntegrityValid) return 'indeterminate';
  if (!input.fingerprintBefore || !input.fingerprintAfter) return 'indeterminate';
  if (input.fingerprintBefore !== input.fingerprintAfter) return 'indeterminate';
  return 'passed';
}
```

查看历史 Run 时，再比较 `fingerprintAfter` 与 `fingerprintCurrent`：不一致则展示 `stale`。不要直接覆盖历史 Run 的原始执行状态，应保留 `execution_status` 与派生的 `freshness_status`，或采用等效模型，防止历史被篡改。

### 12.1 Build 与 Test 分离

- `build` 通过只能证明构建命令成功。
- `test` 通过需要满足测试报告策略。
- 一个项目整体状态由项目配置的 required suites 聚合。
- UI 不应把 build passed 显示为 test passed。

## 13. 工作区指纹实现建议

推荐实现步骤：

1. 读取 HEAD SHA。
2. 获取 Git index/working tree 差异摘要。
3. 对未跟踪且非忽略的文件建立排序后的相对路径清单，并对文件内容计算 SHA-256。
4. 纳入子模块状态（若存在）。
5. 对所有字段做稳定序列化，计算最终 SHA-256。

注意：

- 排除 `.git`、依赖缓存和构建输出，但排除规则必须是明确且版本化的配置；不能误排源代码。
- 对大型仓库限制单次扫描大小并支持增量计算。
- 指纹算法版本写入 manifest，例如 `fingerprint_algorithm_version`，算法改变后可识别历史数据。
- 对 Git LFS、大文件、符号链接、大小写敏感路径等情况做兼容测试。
- 若获取指纹失败，Run 仍可保存原始执行记录，但不能标记为可信通过。

## 14. 命令执行实现注意事项

- 使用项目当前的主进程进程启动封装，不在 Renderer 直接调用 shell。
- executable 和 args 尽量使用数组传递，避免 shell 字符串拼接。
- 明确 cwd，确保工作目录位于所选项目/Worktree 的允许范围内。
- stdout/stderr 以流式方式写入文件，UI 只订阅进度和尾部日志。
- 超时后终止进程树；验证 Windows 上子进程、Java/Node/.NET test host 等进程是否会残留。
- 记录 Node、Java、.NET SDK 等版本时，只采集实际执行或检查到的信息。
- 环境变量值默认不存储；对日志做凭据和敏感信息脱敏。
- 任何自动重试都必须区分幂等测试命令与可能产生副作用的自定义命令，默认不自动重跑 custom 命令。

## 15. API / IPC 合约建议

命名应按现有 IPC 风格调整，下面只描述接口语义：

```ts
// 获取当前项目可用验证套件
listVerificationSuites(projectId)

// 启动验证
startVerification({ projectId, sessionId, workspaceId, suiteId, confirmedCommand? })

// 订阅运行状态/输出
subscribeVerificationRun(runId, listener)

// 取消执行
cancelVerification(runId)

// 查询历史运行
listVerificationRuns({ projectId, sessionId?, limit, cursor? })

// 读取运行详情
getVerificationRun(runId)

// 读取日志片段/下载证据
readVerificationArtifact({ runId, artifactId, offset?, limit? })
exportVerificationReport(runId)

// 校验完整性
verifyEvidenceIntegrity(runId)
```

IPC 安全要求：

- Renderer 只能传业务 ID 和受控参数，不能传任意本地文件路径作为证据读取路径。
- 主进程验证项目、会话、Run 的归属关系。
- 输出 DTO 做字段白名单，禁止返回环境变量秘密值。
- 对进程输出订阅进行节流，避免大量 IPC 消息造成 UI 卡顿。

## 16. 测试方案

### 16.1 单元测试

- 状态规则全覆盖。
- 不同 Exit Code、取消、超时、崩溃组合。
- JUnit/TRX 有效、空、损坏、重复、零测试、失败样本。
- 多套件聚合。
- Manifest 哈希校验及篡改检测。
- Workspace Fingerprint 稳定性和变化检测。
- Markdown 报告字段与状态一致性。

### 16.2 集成测试

使用临时 Git 仓库和可控测试脚本：

- 返回 0 且输出有效测试报告。
- 返回非零。
- 无报告但返回 0。
- 测试过程中修改文件。
- 结束后修改文件。
- 超时、取消、产生子进程。
- 大量 stdout/stderr。
- 报告路径不存在、路径穿越、损坏 XML。
- 应用启动后发现上次 Run 未完成。

### 16.3 桌面冒烟测试

- 启动 Run、查看实时状态、取消 Run。
- 打开 Run 详情及日志。
- 历史结果列表和过期提示。
- 导出 Markdown。
- 应用重启后历史 Run 正常显示。
- 用户原有 Git 修改不被误归为 Agent 修改或被清理。

## 17. 分阶段实施顺序

### 阶段 A：现状勘察与最小数据模型

- 盘点当前 Build/Test 实现及调用路径。
- 盘点 SQLite Schema 和迁移机制。
- 盘点进程执行、Git 和报告生成模块。
- 输出改造映射及风险，不修改无关功能。
- 确定首期真实测试框架解析器。

### 阶段 B：证据采集与确定性状态

- 增加 Run/Artifact/Result 数据模型及迁移。
- 将测试流程接入统一进程执行服务。
- 采集命令、时间、Exit Code、日志。
- 实现首期测试结果解析器。
- 实现状态规则和零测试保护。
- 实现执行前后工作区快照及过期检查。

### 阶段 C：报告、界面与恢复

- 生成确定性 Markdown 报告。
- 增加测试证据详情和历史列表。
- 增加 Manifest 与完整性校验。
- 补应用异常退出后的未完成 Run 恢复。
- 兼容旧历史报告。

### 阶段 D：回归与灰度

- 用至少 3 类真实代码库验证（若当前可用）。
- 先对第二战区内部项目灰度。
- 记录误判、解析器缺口、性能和用户操作问题。
- 未通过 P0 验收前，不将“测试证据链”宣传为完整能力。

## 18. 完成定义（Definition of Done）

- [ ] 完成当前代码架构勘察并附在实现说明中。
- [ ] 所有测试状态由应用端确定性计算。
- [ ] 未执行、没有报告、零测试、解析失败均不能显示 passed。

- [ ] Manifest 哈希校验可用。
- [ ] 旧测试报告不被伪装成真实证据。
- [ ] 不泄漏命令环境中的密码、Token 和连接串。
- [ ] 相关自动化测试、构建和桌面测试通过。
- [ ] 最终说明所有未支持的测试框架和限制。
