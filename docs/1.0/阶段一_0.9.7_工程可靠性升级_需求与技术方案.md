# 精工 Agent 0.9.7｜工程可靠性升级

## 需求规格说明书 + 技术实施方案

-   文档版本：V1.0
-   目标版本：0.9.7
-   优先级：P0
-   适用项目：`zhuangxiaolong/jg_agent`，`develop/desktop-poc`
-   交付对象：Codex
-   原则：在现有架构上增量开发，不重写 Runtime，不改变现有项目/会话/Git
    数据模型的兼容性。

------------------------------------------------------------------------

# 1. 背景与目标

精工 Agent 已具备桌面端会话、项目 Worktree、Runtime
适配、模型配置、工具活动、子 Agent、Git、真实验证等基础能力。0.9.7
不以增加大量新功能为目标，优先补齐长任务运行的可靠性、性能可观测性和异常恢复能力。

## 1.1 本版本目标

1.  任务中断、应用异常退出或 Runtime
    断连后，能够识别任务状态并提供安全恢复。
2.  建立可重复的 Runtime 性能基准测试，避免仅凭主观感受判断速度。
3.  对可恢复错误提供有上限的自动重试与纠错闭环。
4.  减少无效上下文注入、重复读取和重复扫描。
5.  所有"成功""测试通过""恢复完成"等状态必须由真实事件或执行证据支撑。
6.  保持现有 Runtime 能力和用户数据兼容，不允许静默切换 Runtime 或模型。

## 1.2 非目标

-   不重新实现 Codex / Claude Agent 的推理循环。
-   不替换现有 Runtime，不擅自升级固定 Runtime 版本。
-   不在本版本实现新的专家体系或知识图谱。
-   不允许 Agent
    自动执行生产数据库写入、主分支合并、强制推送等高风险动作。
-   不以单次 benchmark 结果宣称某 Runtime 永远更快。

# 2. 功能需求

## FR-01 任务运行状态持久化

为每次用户任务建立可恢复的运行记录，至少记录：

-   `runId`、`sessionId`、`projectId`
-   Runtime 类型、Runtime 版本、Provider 标识、模型标识
-   任务开始时间、最后心跳时间、结束时间
-   当前状态：`queued / preparing / running / waiting_tool / stopping / completed / failed / cancelled / interrupted / recovery_required`
-   当前工作区路径、Git 分支、基准 commit
-   当前 turn/thread 标识（仅保存 Runtime 提供的非敏感标识）
-   最近已确认的事件序号
-   任务计划/检查点摘要（不保存隐藏推理内容）
-   失败类型、可恢复性判断、恢复尝试次数

运行事件采用追加式记录，禁止用后到的旧事件覆盖新状态。事件至少包括：任务创建、Runtime
启动、turn
开始、工具开始/结束、文件变更摘要、验证开始/结束、用户停止、Runtime
退出、恢复尝试。

## FR-02 崩溃检测与恢复入口

应用启动时扫描未终结的运行记录：

1.  若 Runtime 进程仍存活且会话标识有效，检查协议状态后允许重新连接。
2.  若 Runtime 已退出，标记为 `interrupted`，展示恢复选项。
3.  若工作区状态与检查点不一致，不自动回滚、不覆盖文件；进入
    `recovery_required`。
4.  若无法确认 Runtime
    是否仍执行，先执行安全探测，不得启动第二个相同任务。
5.  恢复前展示：任务目标、最近状态、未完成步骤、工作区路径、Git
    状态和潜在风险。

恢复动作： - **继续任务**：在 Runtime
协议支持且上下文可恢复时继续；否则使用检查点重建新
turn，并明确标注"从检查点继续"。 - **仅打开工作区**：不启动
Runtime，供用户检查现有代码。 -
**放弃恢复**：只结束运行记录，不删除工作区和变更。

禁止自动清理中断任务的 Worktree。

## FR-03 检查点机制

检查点必须是可验证的结构化状态，不是模型自由文本摘要。建议结构：

``` json
{
  "schemaVersion": 1,
  "runId": "uuid",
  "sessionId": "uuid",
  "createdAt": "ISO-8601",
  "goal": "用户任务目标",
  "plan": [
    {"id":"step-1","title":"分析入口","status":"completed","evidence":["event-id"]},
    {"id":"step-2","title":"修改实现","status":"in_progress","evidence":[]}
  ],
  "completedActions": [],
  "pendingActions": [],
  "workspace": {
    "path": "session worktree path",
    "branch": "agent/session",
    "baseCommit": "sha"
  },
  "validation": [],
  "knownRisks": []
}
```

检查点更新由主进程根据真实事件、用户确认和结构化计划状态产生。模型可建议更新，但不能自行伪造
`completed` 状态或验证证据。

## FR-04 自动重试与纠错

对错误分类后再决定是否重试：

  错误类别                             默认处理
  ------------------------------------ -------------------------------
  临时网络错误、限流、可恢复连接断开   有上限退避重试
  Runtime 进程崩溃                     转入恢复流程
  模型上下文超限                       提示压缩/拆分任务，不盲目重试
  用户取消                             不重试
  权限拒绝/高风险动作拦截              不重试，要求用户处理
  代码构建失败                         可进入修复建议/修复回合
  测试失败                             分析失败原因，允许有限修复
  配置错误、认证失败                   不重试，提示配置修复
  数据库连接失败                       不自动更换连接或写入目标

重试默认最多 2 次，可配置为 0--3
次。采用指数退避并加入随机抖动。每次重试都记录原因、等待时间和结果。

自动修复流程： 1. 收集真实构建/测试输出。 2.
生成失败摘要（仅基于日志和结构化结果）。 3. 要求 Agent
先定位原因，再提出最小修复。 4. 执行修复后重新运行同一验证命令。 5.
达到次数上限仍失败则停止并展示证据。

不得把"模型说已修复"视为成功；必须重新执行验证。

## FR-05 Runtime 性能基准

新增独立 Benchmark 页面/面板，支持用户选择：

-   Runtime
-   Provider / 模型
-   项目与任务样本
-   测试轮数
-   是否清理缓存（仅清理平台明确管理的缓存）
-   测试场景

首批场景： 1. 首字响应：发送固定短问答，记录请求至首个可见文本的时间。
2. 简单代码定位：在固定仓库中定位指定类/方法。 3.
多文件只读分析：分析固定范围并输出结构化结果。 4. 小型代码修改：在临时
Worktree 中修改固定文件并运行指定验证。 5.
工具链任务：读取文件、搜索、执行只读命令的组合任务。

采集指标： - `timeToFirstTokenMs` - `totalDurationMs` -
`runtimeStartupMs` - `toolCallCount` - `toolDurationMs`（可采集时） -
`retryCount` - 输入/输出 Token（Provider 有真实数据时） - 任务完成状态 -
验证退出码 - 错误分类

每条结果标记环境信息：OS、CPU/内存可采集信息、应用版本、Runtime
版本、模型、Provider、网络端点别名（不得保存 API Key 或完整敏感 URL）。

报告展示中位数、P90、成功率和样本数；样本数不足 5
时标记"样本不足"。不同模型、不同任务、不同项目的结果不得直接混成一个排名。

## FR-06 上下文优化与预算

建立上下文来源清单： - 系统指令 - 项目识别信息 - 开发规范 -
数据字典/操作手册 - 项目记忆 - Jira 任务及附件摘要 - 当前会话消息 -
工具结果

要求： 1. 每轮记录各来源的字符数/估算 Token
数和注入耗时（能采集才展示）。 2.
对大文档先做目录/标题索引，按问题检索相关片段。 3.
关键开发规范不得静默截断；超预算时明确提示用户调整资料范围或拆分任务。
4. 相同会话内可复用稳定的文件摘要，但文件 SHA256 变化后必须失效。 5.
不把模型隐藏推理内容保存为记忆或检查点。 6. 记忆/知识检索结果要保留来源
ID，方便后续溯源。

## FR-07 运行监控与诊断导出

提供"诊断包导出"，包括： - 应用版本、Runtime 版本、操作系统信息 -
最近一次任务状态与事件时间线 - 脱敏后的错误日志 - 验证报告摘要 - Git
状态摘要

默认排除：API Key、密码、Webhook、完整凭据、项目源代码、代码
Diff、用户未选择的文件内容。导出前展示清单并要求确认。

# 3. 交互要求

## 3.1 中断任务卡片

展示： - 任务标题 - 中断时间 - Runtime / 模型 - 最近完成步骤 -
工作区是否存在未提交变更 - 恢复 / 打开工作区 / 放弃恢复

## 3.2 自动重试提示

展示"第 1/2
次重试"、错误类别、重试原因、倒计时和取消按钮。用户取消后立即停止后续重试。

## 3.3 Benchmark 页面

提供筛选、运行测试、结果列表、单次详情、对比视图、导出
CSV/JSON。禁止用装饰性评分掩盖原始数据。

# 4. 技术方案

## 4.1 架构原则

沿用现有 Electron 主进程、Renderer、SQLite、Runtime Adapter、Worktree
和验证执行模块。新增能力优先作为独立 service，不把业务逻辑塞进 React
组件。

建议模块（命名按仓库现有风格调整）：

``` text
src/
  main/
    services/
      run-lifecycle/
      checkpoint/
      recovery/
      retry-policy/
      benchmark/
      context-budget/
      diagnostics/
  shared/
    contracts/
      run-record.ts
      run-event.ts
      checkpoint.ts
      benchmark.ts
  renderer/
    features/
      recovery/
      benchmark/
      run-monitor/
```

以上为逻辑边界示例，Codex
必须先检查实际目录结构再决定落点，不得机械创建重复目录。

## 4.2 数据库迁移

新增表建议：

-   `agent_runs`
-   `agent_run_events`
-   `agent_run_checkpoints`
-   `runtime_benchmark_runs`
-   `runtime_benchmark_samples`

所有表有 `created_at`、必要索引和 schema
version。迁移必须幂等、可从旧版本升级；不删除或重建现有表。新增字段优先
nullable/default，确保旧数据兼容。

## 4.3 状态机

``` text
queued -> preparing -> running <-> waiting_tool
running -> stopping -> cancelled
running -> completed
running -> failed
running -> interrupted -> recovery_required
interrupted -> preparing (用户确认恢复)
recovery_required -> interrupted (检查后仍无法恢复)
```

状态迁移必须集中管理，禁止多个 UI
组件自行修改状态。所有迁移校验合法前置状态。

## 4.4 Runtime 恢复适配

建立 Runtime capability 声明： - `supportsResumeThread` -
`supportsReconnect` - `supportsCancel` - `supportsStructuredEvents` -
`supportsUsageMetrics`

能力由 Runtime Adapter 明确声明，不能根据 Runtime
名称猜测。对不支持恢复的
Runtime，采用"检查点重建"路径并提示用户，不伪装为原线程续跑。

恢复时重新注入当前有效的安全策略、系统规范和项目上下文；不得恢复过期权限。恢复后核对工作区路径和
Git 分支，禁止把旧线程恢复到其他项目。

## 4.5 并发与一致性

-   同一 `runId` 只能有一个活跃执行者。
-   使用 SQLite 事务/唯一约束实现运行租约。
-   心跳超时只是"疑似中断"，必须探测进程后再定状态。
-   事件按单调序号写入；重复事件需幂等。
-   应用退出时先停止接收新任务，再按现有 Runtime 协议尝试 graceful
    shutdown，超时后记录未完成状态。

## 4.6 性能采集

采用统一
`PerformanceRecorder`，所有耗时使用单调时钟计算，持久化墙钟时间用于展示。不能用
`Date.now()`
差值作为高精度性能唯一依据。缺少指标显示"不可采集"，不得推算成精确 Token
或工具耗时。

# 5. 安全与风险控制

1.  恢复任务不等于自动恢复授权。权限策略必须重新校验。
2.  自动修复仅限当前 Agent Worktree。
3.  Benchmark 使用临时 Worktree/测试仓库，不得修改真实客户项目分支。
4.  诊断包默认脱敏，导出前用户确认。
5.  不记录 API Key、密码、Webhook、Authorization Header。
6.  不执行自动数据库写入、Git push、合并、删除项目目录等高风险动作。
7.  任何自动清理均须确保无未提交变更，并要求用户明确确认。

# 6. 验收标准

-   [ ] 应用运行任务时强制退出，重启后能识别为中断，不丢失会话和工作区。
-   [ ] 对支持 Runtime
    恢复的适配器可恢复；不支持的适配器明确走检查点重建。
-   [ ] 同一个运行任务不会被重复启动。
-   [ ] 中断恢复不会覆盖用户文件、删除 Worktree 或切错项目。
-   [ ] 网络临时错误最多按配置重试，用户取消后不再重试。
-   [ ] 构建失败自动修复后必须重新执行真实构建，失败证据可查看。
-   [ ] Benchmark 能记录至少 5 类指标，结果有环境、模型和 Runtime 版本。
-   [ ] 样本不足、数据不可采集有明确提示。
-   [ ] 上下文超预算时显式阻止或要求调整，不静默裁剪规范。
-   [ ] 诊断包不包含密钥、代码和未经授权的文件内容。
-   [ ] 旧版本 SQLite
    数据升级后项目、会话、Provider、记忆、凭据引用均正常。
-   [ ] Windows
    安装版、开发版均通过启动、任务执行、停止、恢复、升级回归测试。

# 7. Codex 实施要求

1.  先检查当前分支真实代码、package.json、SQLite schema、Runtime
    Adapter、任务生命周期、事件流和测试结构。
2.  输出《现状映射表》：需求对应已有模块、缺失模块、拟修改文件。
3.  不得按本方案示例目录盲目新建；遵循仓库实际结构。
4.  先完成数据库迁移和状态服务，再做 UI。
5.  每个阶段先实现最小闭环并运行测试，不要一次性大规模重构。
6.  不升级 Electron、Runtime、依赖主版本，除非证明必要并单独说明。
7.  新增自动化测试覆盖状态机、恢复、重试、幂等和脱敏。
8.  完成后提供变更文件清单、迁移说明、测试命令和真实测试结果。
9.  如果当前代码已有等价能力，复用并补齐缺口，不重复造轮子。
10. 对不确定的 Runtime
    协议字段先查固定版本类型定义和协议测试，不凭猜测实现。
