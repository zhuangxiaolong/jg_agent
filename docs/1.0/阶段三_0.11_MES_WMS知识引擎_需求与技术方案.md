# 精工 Agent 0.11｜MES/WMS 专业知识引擎

## 需求规格说明书 + 技术实施方案

-   文档版本：V1.0
-   目标版本：0.11
-   优先级：P1
-   适用分支：`develop/desktop-poc`
-   交付对象：Codex
-   依赖：现有资料导入、系统识别、项目会话、Memory；阶段二专家知识绑定能力。

------------------------------------------------------------------------

# 1. 背景与目标

现有精工 Agent 已支持 MES5、MES6、WMS
等资料导入和开发规范注入。下一阶段从"把资料放进上下文"升级为"可检索、可溯源、可关联代码和业务的专业知识引擎"。

核心目标： 1.
用户提出问题时，系统能找到相关文档、代码、数据库结构和项目经验。 2.
回答中的关键结论可以定位到来源。 3. 能分析代码入口、调用关系、实体和 SQL
之间的关联。 4. 能识别 MES5/MES6/WMS 技术体系，避免跨系统知识污染。 5.
项目知识可以长期沉淀，并支持版本、过期和冲突治理。

## 1.1 非目标

-   不在本版本训练或微调基础模型。
-   不要求建立全公司的完整业务本体。
-   不自动扫描或上传用户未授权的整个磁盘。
-   不允许把客户敏感数据无差别发送给第三方模型。
-   不把模型推测的关系标记为已验证事实。

# 2. 知识类型与边界

知识分为五类：

  --------------------------------------------------------------------------------------------
  类型                    内容                                  典型来源
  ----------------------- ------------------------------------- ------------------------------
  产品知识                MES5/MES6/WMS 操作手册、功能说明      PDF/DOCX/XLSX/MD

  开发知识                开发规范、架构文档、接口约定          AGENTS.md、开发要求

  代码知识                类、方法、接口、实体、SQL、调用关系   已授权 Git 仓库

  数据知识                表、字段、主外键、索引、视图          DDL、实体映射、用户导入结构

  项目知识                客户配置、问题、决策、解决方案        Jira、项目文档、人工确认记录
  --------------------------------------------------------------------------------------------

每条知识必须记录： - 来源类型 - 来源 ID / 文件路径 / Git commit -
系统类型（MES5/MES6/WMS/通用） - 项目 ID（如适用） - 版本/更新时间 -
SHA256（适用时） - 解析状态 - 可信级别 - 是否过期/已撤销

可信级别： - `verified`：由文件、代码、DDL 或用户明确确认支持 -
`inferred`：系统根据代码/文档关系推断 -
`unverified`：尚未核验的用户输入或模型建议

# 3. 功能需求

## FR-01 知识库统一管理

增加知识库页面，按知识空间组织： - 通用知识 - MES5 - MES6 - WMS -
项目知识 - 专家专属知识

支持导入、启用、停用、删除、重新解析、查看来源、查看解析错误、查看版本和
SHA256。沿用现有文档导入能力，不重复实现一套文件上传系统。

## FR-02 混合检索

同时支持： 1. 关键词检索：标题、正文、文件名、代码符号、表名、字段名。
2. 向量检索：语义相近内容。 3.
元数据过滤：系统类型、项目、知识类别、文件、版本、启用状态。 4.
结果融合：关键词与向量结果按可解释规则合并排序。

建议初始策略： - 先做精确标识符命中（类名、方法名、表名、字段名）。 -
再执行全文/关键词检索。 - 再执行向量语义检索。 - 使用 RRF
或可解释加权融合。 - 对结果做去重和来源分组。

检索必须返回来源、片段位置、相关性分数/排序依据。分数仅用于排序，不代表事实可信度。

## FR-03 文档切分与索引

不同资料采用不同切分策略： - Markdown：按标题层级切分，保留标题路径。 -
TXT：按段落和长度切分。 - DOCX：保留标题、段落、表格上下文。 -
XLSX：按工作表、表头、行区间切分；保留 sheet 名和单元格范围。 -
PDF：优先保留页码、标题和段落；扫描件/OCR
能力若当前无实现，明确标记不支持或解析失败，不伪造内容。 - SQL/DDL：按
CREATE TABLE、VIEW、INDEX、COMMENT 等语句切分。 -
源代码：按类、函数、接口和文件切分，尽量避免跨符号拼接。

每个 chunk 保存： - `chunkId` - `documentId` - `content` -
`headingPath` - `startLocator` / `endLocator` - `systemType` -
`projectId` - `contentHash` - `embeddingModel` / `embeddingVersion` -
`createdAt`

不得静默截断关键开发规范。文档过大时分块索引，而非将全部文本塞进每轮
Prompt。

## FR-04 向量模型与离线策略

向量模型可配置： - Provider / Base URL - Embedding Model - API Key（沿用
DPAPI 凭据存储） - 维度 - 批量大小 - 超时

用户没有配置 Embedding 服务时： - 关键词检索仍可用。 -
页面明确显示"语义检索未配置"。 - 不得假装已经进行向量检索。

向量模型变化或维度变化时建立新索引版本，不能混用不同维度向量。

## FR-05 代码知识索引

按仓库授权范围索引代码。首批支持以静态解析和符号扫描为主： -
文件清单和语言识别 - namespace/module - class/interface/enum -
method/function - API 路由（可静态识别时） - DTO/实体 - SQL 文件和内嵌
SQL（能安全解析时） - 项目引用关系 - 符号定义位置 -
符号引用位置（按语言能力逐步支持）

MES5 重点识别 Controller/Service/Repository/DTO/Entity 和手写 SQL。 MES6
重点识别 Application/Domain/Models/ViewModels/Enums、Service 路由特性和
SqlSugar 实体映射。 WMS 先识别实际仓库技术栈，不预设项目分层。

索引记录 Git commit 和文件
hash。分支切换或文件变化后，仅增量更新变化文件及其依赖关系。

## FR-06 调用链和影响面分析

用户可以询问： - 某接口入口在哪里？ - 这个方法调用了哪些服务？ -
哪些接口引用了这个实体？ - 修改这个字段可能影响哪些模块？ -
某业务流程涉及哪些表？

输出必须区分： - 静态直接调用（已找到代码引用） -
配置/反射/动态路由推断 - 仅根据命名或文档推测

每个节点提供文件路径、行号/符号和 Git
commit。无法完整追踪时标注"调用链不完整"，不补造链路。

## FR-07 数据库知识关联

支持导入 DDL、数据库结构导出文件和项目实体映射。可建立： - 表与字段 -
主键/索引 - 外键（仅在源数据明确时） - 实体映射 - SQL 查询引用表 -
业务模块引用实体

本版本默认只读文件，不主动连接客户生产数据库。若未来接只读数据库连接，必须单独增加连接授权、网络范围、SQL
只读校验和审计。

## FR-08 业务知识关联

先建设轻量关系模型，不做大而全知识图谱。

首批实体： - 业务模块 - 业务流程 - API - 服务/方法 - 数据表 - 字段 -
产品手册章节 - 项目问题 - 解决方案

关系示例： - API `implements` Service - Service `reads/writes` Table -
Entity `maps_to` Table - ManualSection `describes` Process -
ProjectIssue `resolved_by` Solution

每条关系记录来源和可信级别。由模型推断的关系必须标记
`inferred`，经人工核验后才能变成 `verified`。

## FR-09 回答引用与溯源

知识型回答在关键结论后展示引用： - 文件名/路径 - 文档页码或标题 -
代码文件和行号 - Git commit - 资料更新时间

点击引用可打开对应文件/代码位置。引用必须真实存在且 locator
可验证。若来源已变化，提示"来源版本已更新"，不能悄悄引用旧内容。

## FR-10 项目长期知识

项目知识可记录： - 客户特有业务规则 - 特殊配置 - 已确认的需求决策 -
已解决问题 - 未解决风险 - 部署环境说明（不得包含密码/Token） -
项目接口约束

新增项目记忆必须包含： - 标题 - 内容 - 类型 - 来源/证据 -
创建人或创建方式 - 可信级别 - 更新时间 - 过期/复核日期（可选）

模型可建议沉淀，用户确认后写入。禁止自动把整段聊天、未经确认的推测或秘密写入长期记忆。

## FR-11 知识冲突与过期

检索到相互矛盾资料时： - 同一文件新版本优先，但保留历史来源。 -
用户明确标记为废弃的资料不参与默认检索。 -
同一主题不同客户项目的配置不能混为通用事实。 -
冲突无法判断时同时展示并要求用户确认。 -
过期资料显示更新时间和复核提醒。

# 4. 技术方案

## 4.1 组件边界

``` text
KnowledgeManager
  ├── SourceRegistry
  ├── DocumentParser
  ├── ChunkingPipeline
  ├── KeywordIndex
  ├── EmbeddingProvider
  ├── VectorIndex
  ├── CodeIndexer
  ├── SymbolResolver
  ├── RelationStore
  ├── HybridRetriever
  ├── CitationResolver
  └── ProjectMemoryService
```

先盘点现有资料导入、SQLite、Memory、开发要求服务，复用已有能力。

## 4.2 存储设计

建议表： - `knowledge_sources` - `knowledge_documents` -
`knowledge_chunks` - `knowledge_embeddings` - `code_index_snapshots` -
`code_symbols` - `code_references` - `knowledge_relations` -
`project_knowledge_items` - `knowledge_index_jobs`

向量存储选择必须先做技术调研： - 若现有 SQLite 生态已有可用向量扩展且
Windows 打包稳定，优先本地 SQLite 扩展。 -
否则采用独立本地向量索引文件，SQLite 仅存元数据。 - 不要在未验证
Electron Windows 安装包兼容性前引入需要复杂原生编译的依赖。 -
所有索引可重建，原始资料不因索引失败而丢失。

## 4.3 增量索引

1.  读取授权仓库 Git commit。
2.  比较上次索引的文件 hash。
3.  仅解析新增/修改文件。
4.  删除已不存在文件的索引记录，但保留审计快照（按现有数据保留策略）。
5.  更新受影响符号和关系。
6.  新索引完成后原子切换活动版本。

索引任务可取消、可恢复，不能阻塞 UI 主线程。

## 4.4 检索 API

统一接口示例：

``` ts
type KnowledgeQuery = {
  query: string;
  systemType?: "MES5" | "MES6" | "WMS" | "FRONTEND" | "GENERAL";
  projectId?: string;
  categories?: string[];
  sourceIds?: string[];
  topK?: number;
};

type KnowledgeHit = {
  sourceId: string;
  title: string;
  content: string;
  locator?: string;
  score?: number;
  matchType: "identifier" | "keyword" | "vector" | "hybrid";
  confidence: "verified" | "inferred" | "unverified";
  version?: string;
};
```

检索层只返回结果，不直接拼接
Prompt。由上下文组装器根据预算、任务类型和权限决定注入内容。

## 4.5 安全与数据隔离

-   项目知识默认仅对所属项目会话可见。
-   通用知识不能包含客户机密。
-   不索引 `.env`、密钥文件、证书、私钥、凭据配置和用户排除目录。
-   忽略 `node_modules`、`bin`、`obj`、构建输出、Git
    内部目录、二进制文件等非源代码目录。
-   索引过程遵守项目只读授权，不修改源文件。
-   发送给模型前按现有敏感信息规则脱敏。
-   删除资料后同步失效 chunk、embedding 和关系引用。

# 5. UI 设计要求

知识中心至少包含： 1. 知识空间导航 2. 来源文件列表 3. 解析/索引状态 4.
搜索框和筛选器 5. 搜索结果及命中片段 6. 来源定位 7. 版本和可信级别 8.
项目记忆管理 9. 索引任务进度

会话中支持"知识依据"折叠面板，展示本次回答使用的知识来源。不要把所有引用堆在回答正文中。

# 6. 验收标准

-   [ ] 已导入文档可按标题、关键词和系统类型检索。
-   [ ] 配置 Embedding 后语义检索可用；未配置时明确降级到关键词检索。
-   [ ] MES5/MES6/WMS 的知识过滤有效，不发生跨系统误注入。
-   [ ] Markdown、DOCX、XLSX、PDF、SQL 按支持范围保留定位信息。
-   [ ] 代码索引可定位类、方法、实体和文件。
-   [ ] 对 MES5/MES6 至少各准备 10 个固定代码问答评测样例。
-   [ ] 调用链区分直接证据与推断，无法追踪时明确说明。
-   [ ] 表结构和实体关系有来源定位。
-   [ ] 回答引用可打开对应文件/代码位置。
-   [ ] 文件修改后索引增量更新，旧 hash 结果不再冒充最新代码。
-   [ ] 项目知识按项目隔离。
-   [ ] 删除知识后检索结果和向量索引同步失效。
-   [ ] 敏感文件不进入索引。
-   [ ] Windows 打包安装、升级和重建索引通过回归测试。

# 7. Codex 实施要求

1.  先审计现有资料导入、记忆、SQLite、全文检索、代码扫描能力。
2.  输出数据流图和存储方案，特别验证 Windows 原生依赖打包风险。
3.  第一迭代优先完成来源管理、关键词检索、引用定位。
4.  第二迭代加入 Embedding 与混合检索。
5.  第三迭代加入代码符号索引、调用链和关系。
6.  不得先做"知识图谱大屏"再补数据质量；先确保关系有证据。
7.  建立 MES5、MES6、WMS 的检索准确率评测集。
8.  所有索引可重建，所有引用可溯源。
9.  新增 schema 迁移和索引版本迁移说明。
10. 最终输出真实测试结果、性能数据、未支持格式和限制。
