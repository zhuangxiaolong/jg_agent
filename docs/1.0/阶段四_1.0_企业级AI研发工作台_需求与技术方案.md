# 1. 产品定位

精工 Agent 不以替代 Cursor、Codex 或 Claude Code 为目标，而是以成熟
Runtime 为执行引擎，在其上构建企业研发与交付工作流。

产品核心： - Runtime：复用 Codex、Claude 等成熟执行引擎。 - Agent：总控
Agent 与专业专家协作。 - Knowledge：MES5/MES6/WMS 领域知识和项目知识。 -
Workflow：Jira 需求到开发、验证、审查、交付的流程闭环。 -
Governance：权限、审计、证据和企业配置。 -
Workspace：桌面端项目、会话、代码、终端和执行可视化。

# 2. 1.0 产品目标

1.  用户能从 Jira 或自然语言任务发起一个完整研发任务。
2.  系统能识别项目类型、理解任务、检索知识、规划专家协作。
3.  Agent 能在隔离 Worktree 内执行代码分析和修改。
4.  平台能运行真实构建/测试，记录可审计证据。
5.  用户可以理解每一步执行状态并控制高风险动作。
6.  任务完成后生成可交付的变更、验证、风险和需求追踪报告。
7.  企业管理员可统一管理模型、Runtime、知识、专家、权限和版本策略。

# 3. 典型用户与场景

## 3.1 开发人员

-   领取 Jira 缺陷。
-   自动读取任务与附件。
-   分析 MES5/MES6/WMS 代码。
-   由开发专家实施修改。
-   测试专家制定验证建议。
-   平台执行构建和测试。
-   代码审查专家审查 Diff。
-   开发人员确认后提交 Git。

## 3.2 项目经理/交付负责人

-   导入项目计划、问题清单和客户资料。
-   由项目经理、实施和交付总监专家分析。
-   形成进度、风险、验收、回款和资源问题清单。
-   关键数据必须来自输入资料或连接器，缺失项标记待补充。

## 3.3 企业管理员

-   配置模型 Provider 和 Runtime。
-   管理专家模板和知识空间。
-   设置权限策略。
-   管理版本、审计和组织级默认配置。
-   查看使用量、失败率和运行成本。

# 4. 核心功能需求

## FR-01 统一任务工作台

首页展示： - 最近项目和会话 - 我的待处理任务 - 正在运行任务 -
中断/失败任务 - 最近验证结果 - 常用专家 - 最近知识更新

支持按项目、状态、任务类型和时间筛选。首页指标必须来自真实数据库记录，不使用模拟数字。

## FR-02 任务创建与需求入口

任务来源： - 自然语言输入 - Jira 任务 - 本地文件/资料 - 已有会话续办

创建任务时可关联： - 项目 - Jira Issue - 系统类型 - 任务类型 - Runtime /
模型策略 - 权限策略 - 知识空间

任务类型： - 需求分析 - Bug 修复 - 功能开发 - 重构 - 代码审查 -
测试分析 - 项目交付分析 - 技术调研

需求缺少关键条件时生成澄清清单。不得因准入提示而无条件阻断用户，但涉及高风险操作或无法确定目标项目时必须暂停确认。

## FR-03 智能任务规划

总控 Agent 生成： - 目标 - 范围 - 假设 - 专家分工 - 依赖关系 -
文件/模块范围 - 验收标准 - 风险级别 - 所需权限

计划展示后用户可修改和批准。执行过程中如需扩大范围或新增高风险动作，必须再次申请确认。

## FR-04 专家协作工作流

复用阶段二专家 Registry 和 Orchestrator。1.0 增加可配置工作流模板： -
Bug 修复工作流 - 新功能开发工作流 - 代码审查工作流 - MES/WMS
需求分析工作流 - 项目交付分析工作流

模板定义专家、任务依赖、权限、验收项和失败处理。用户可以复制模板，但不能修改平台强制安全规则。

## FR-05 知识引擎集成

复用阶段三知识引擎。任务创建时自动根据项目类型和任务内容检索知识： -
产品手册 - 开发规范 - 代码符号 - 数据结构 - 项目记忆 - 历史问题

上下文来源需在任务面板中可查看。用户可排除某知识源。跨项目知识默认不共享，只有显式标记为通用知识才可共享。

## FR-06 任务执行时间线

展示真实事件时间线： - 任务创建 - 计划生成/批准 - 专家启动/完成 -
Runtime 启动 - 文件读取/搜索摘要 - 文件变更摘要 - 命令执行 - 构建/测试 -
审查结果 - 用户确认 - Git 操作

每条事件显示时间、执行者、状态、耗时和关联证据。不得展示模型隐藏推理链。文件读取事件只展示安全摘要，不泄漏敏感文件内容。

## FR-07 统一代码工作区

保留现有 Worktree 机制。工作区支持： - 文件树 - Diff - 终端/命令输出 -
Git 状态 - 验证报告 - 任务关联信息

1.0 不强制实现完整 IDE 编辑器。优先保证现有代码编辑/查看能力与外部 IDE
协同稳定。

## FR-08 验证与质量门禁

任务可配置验证策略： - build - typecheck - unit test - integration
test（仅在安全测试环境） - lint - 开发规范检查 - 代码审查

每项验证记录： - 命令 - 工作目录 - 代码 commit / Diff hash -
开始/结束时间 - 退出码 - 输出报告 - 执行环境

验证结果状态： - `passed` - `failed` - `not_run` - `blocked` - `stale`

代码变更后，之前基于旧 Diff 的验证标记为
`stale`。不能把建议测试、模型判断或人工口头确认显示为自动化测试通过。

## FR-09 交付报告

每个任务完成后生成标准报告： 1. 需求摘要 2. 实际完成范围 3. 变更文件清单
4. 核心实现说明 5. 构建与测试证据 6. 未完成项 7. 风险与影响面 8.
数据库变更（如有） 9. 部署注意事项 10. 人工验收项 11. Jira 关联信息

报告可导出 Markdown/HTML/PDF（按现有文件导出能力实现）。默认先实现
Markdown，其他格式作为后续扩展。

## FR-10 Jira 集成闭环

沿用现有 Jira 只读能力，1.0 可增加用户确认后的写回能力： -
添加工作日志/评论 - 更新任务状态（若权限允许） - 附加交付报告链接或内容

所有写回动作必须： 1. 展示将要写入的内容和目标 Issue。 2. 用户明确确认。
3. 记录请求、响应、操作者和时间。 4. 失败时不伪称成功。 5. 不自动关闭
Jira 任务，除非用户明确确认且工作流授权。

## FR-11 模型智能路由

建立可配置任务路由策略： - 简单问答/代码定位 - 普通代码修改 -
复杂架构分析 - 长上下文任务 - 代码审查 - 文档生成

路由依据可以包括任务类型、模型能力标签、上下文窗口、历史
benchmark、成本预算和用户指定优先级。

规则： - 用户显式指定模型时优先尊重。 -
自动路由前展示当前策略，允许用户覆盖。 - Provider
不可用时不静默切换到未授权服务。 - 不向用户隐瞒实际使用的模型和
Runtime。 - 路由日志不得记录密钥和完整敏感请求正文。 - 根据阶段一
benchmark 数据做推荐，样本不足时标记低置信度。

## FR-12 权限与风险控制

无

## FR-13 企业配置管理

1.0 先支持本机/单用户企业配置文件，不在本版本强行引入复杂多租户服务端。

支持： - Provider 配置模板 - Runtime 版本策略 - 专家模板 -
知识空间默认值 - 权限策略 - 验证命令模板 - Jira 连接配置 -
更新源与发布通道

导入配置前展示差异；凭据不随普通配置文件导出。

## FR-14 使用量与成本分析

在 Provider 提供真实 usage 时记录 Token
和费用估算；否则标记不可采集。费用按用户维护的价格表估算，并标注价格来源和更新时间。

指标： - 任务数 - 完成率 - 失败率 - 平均任务耗时 - 首字时间 - Runtime
分布 - 模型使用分布 - Token 用量（真实可采集时） - 估算成本 -
自动重试率 - 验证通过率

不得把估算成本显示为账单实付金额。

## FR-15 产品可用性与更新

-   Windows 安装、升级、卸载完整验证。
-   数据库迁移失败有备份/恢复提示。
-   Runtime 缺失或版本不兼容时明确提示。
-   离线时仍可查看本地项目、会话和已索引知识。
-   更新发布必须有版本说明、校验和和签名策略。
-   用户数据与凭据升级后保留。

# 5. 总体技术架构

## 5.1 分层架构

``` text
Desktop Presentation
  ├── Task Workspace
  ├── Expert Center
  ├── Knowledge Center
  ├── Run Timeline
  ├── Git / Diff / Verification
  └── Admin Settings

Application Orchestration
  ├── Task Manager
  ├── Planner
  ├── Workflow Engine
  ├── Expert Orchestrator
  ├── Model Router
  ├── Permission Resolver
  └── Report Generator

Agent & Runtime Layer
  ├── Runtime Adapter Registry
  ├── Codex Runtime
  ├── Claude Agent SDK Runtime
  ├── Other Supported ACP Runtime
  └── Tool Execution Gateway

Knowledge Layer
  ├── Document Knowledge
  ├── Code Index
  ├── Database Schema Index
  ├── Project Memory
  └── Hybrid Retrieval

Engineering Layer
  ├── Project Registry
  ├── Git Worktree
  ├── Verification Runner
  ├── Event Store
  ├── Checkpoint / Recovery
  └── Audit Log

Infrastructure
  ├── SQLite
  ├── Local File Store
  ├── DPAPI Credential Store
  ├── Runtime Processes
  └── Update Service
```

## 5.2 技术原则

-   Electron 主进程负责系统能力、凭据、文件、进程、Git 和权限校验。
-   Renderer 负责展示和用户交互，不直接访问 Node/文件系统。
-   所有 IPC 使用 schema 校验、明确通道和最小权限。
-   Runtime Adapter 统一协议差异，但不把不同 Runtime
    的能力伪装成完全一致。
-   任务、专家、知识和验证统一使用稳定 ID 关联。
-   SQLite 是本机元数据与审计主存储；大文件和索引文件放本地数据目录。
-   关键操作使用事务和幂等键。
-   长任务全部异步，不阻塞 UI。
-   任何自动化动作都必须能被取消、追踪和复盘。

## 5.3 统一领域模型

建议核心实体： - `Project` - `Session` - `Task` - `Run` - `RunEvent` -
`Checkpoint` - `Expert` - `ExpertTask` - `WorkflowTemplate` -
`KnowledgeSource` - `KnowledgeChunk` - `ProjectKnowledge` -
`VerificationRun` - `AuditEvent` - `PermissionGrant` - `Provider` -
`RuntimeProfile`

Codex
应先检查现有表结构并复用已有实体，避免重复建模。新增表必须通过迁移创建。

## 5.4 事件驱动

任务状态通过事件推进。事件采用统一结构：

``` json
{
  "eventId": "uuid",
  "eventType": "verification.completed",
  "taskId": "uuid",
  "runId": "uuid",
  "actorType": "system|user|agent|expert",
  "actorId": "id",
  "timestamp": "ISO-8601",
  "payload": {},
  "correlationId": "uuid"
}
```

事件需支持幂等、审计和时间线展示。事件 payload
不得存放密钥或不必要的原始敏感内容。

## 5.5 模型路由接口

统一 `ModelRouter` 接口，输入： - taskType - requestedModel -
runtimeCapabilities - contextSizeEstimate - benchmarkStats -
costPreference - providerAvailability

输出： - providerId - modelId - runtimeId - reason - confidence -
fallbackAllowed

若路由低置信度或 Provider 不可用，询问用户，不自动切换到未授权服务。

# 6. 质量、安全与运维要求

## 6.1 安全

-   凭据使用 DPAPI 或现有安全存储。
-   日志脱敏。
-   项目路径授权和 Worktree 边界由主进程验证。
-   防止路径穿越、符号链接/硬链接逃逸。
-   禁止未经确认的生产数据库写入。
-   禁止默认自动 Git push/merge。
-   Jira 写回逐次确认。
-   知识空间和项目记忆隔离。
-   更新包校验签名与哈希。

## 6.2 可观测性

每个任务能追踪： - 任务 ID - Runtime / Provider / Model - 专家任务链 -
知识检索来源 - 工具事件 - 文件变更 - 验证结果 - 用户确认 - 错误与恢复

## 6.3 性能

建立真实基线： - 应用冷启动时间 - 新建会话时间 - 首字时间 -
简单任务完成时间 - 大仓库检索时间 - 代码索引时间 - 任务恢复时间 - UI
主线程卡顿

目标值必须在目标硬件和固定样本上测量后确定，不在没有基线前承诺绝对毫秒数。

1.  先合入 0.9.7 的可靠性和事件基础。

# 9. Codex 总体执行指令

请以当前 `develop/desktop-poc` 分支代码为唯一实现事实来源。

开始开发前： 1. 读取仓库根目录及 `desktop-poc` 下的
README、AGENTS、package.json、架构文档、数据库 schema、Runtime Adapter
和测试。 2. 盘点已实现功能，不重复实现。 3. 为每条 FR
建立"现有能力/缺失/改造/验收"矩阵。 4. 输出拟修改文件和数据迁移方案。 5.
识别与现有架构冲突的地方，先报告，不擅自推倒重来。

开发过程： - 以小 PR/小迭代实现。 - 先后端服务、契约和数据迁移，再
UI。 - 所有功能可取消、可审计、可恢复。 - 所有成功状态必须有真实证据。 -
不更改现有 Runtime 的核心推理循环。 - 不降低现有权限安全约束。 -
不升级关键依赖，除非有充分依据。

交付时： - 输出完成/未完成需求矩阵。 -
列出变更文件、数据库迁移、配置变化。 - 执行并报告 lint、typecheck、unit
test、build 和 Windows 打包验证（按仓库实际脚本）。 - 提供至少一个
MES5、一个 MES6、一个 WMS 真实任务验收记录。 -
明确列出已知限制、风险和后续建议。
