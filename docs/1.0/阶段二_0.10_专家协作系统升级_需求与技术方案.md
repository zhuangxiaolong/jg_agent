# 精工 Agent 0.10｜专家协作系统升级

## 需求规格说明书 + 技术实施方案

-   文档版本：V1.0
-   目标版本：0.10
-   优先级：P0
-   适用分支：`develop/desktop-poc`
-   交付对象：Codex
-   依赖：阶段一的运行状态、事件、任务恢复能力；若阶段一尚未合入，先适配现有任务生命周期，不复制实现。

------------------------------------------------------------------------

# 1. 产品目标

将现有子 Agent 能力升级为可配置、可调度、可追踪、可验收的专家协作系统。

专家不是简单的人设 Prompt，也不是多个聊天窗口。每个专家必须具有： -
明确职责与边界 - 适用任务类型 - 专属指令与知识范围 - 可用工具权限 -
输入/输出契约 - 交付物和验收规则 - 可观测的执行状态

总控 Agent
负责理解用户目标、规划任务、选择专家、分配任务、整合结果和最终质量检查。

## 1.1 本版本不做

-   不重新实现底层 Agent Runtime。
-   不允许专家绕过现有权限与 Worktree 隔离。
-   不允许专家自行修改 Jira 状态、推送 Git 。
-   不做跨用户/跨组织的云端专家市场。
-   不以专家数量作为产品完成度指标。

# 2. 专家目录与默认配置

首批内置专家：

----------------------------------------------------------------------------------------
  专家 ID                 名称                    职责
----------------------- ----------------------- ----------------------------------------
  `mes5-dev`              MES5 开发专家           MES5 代码分析、实现与兼容性

  `mes6-dev`              MES6 开发专家           MES6 分层、服务、ORM 和业务开发

  `wms-dev`               WMS 开发专家            WMS 业务与代码开发

  `frontend-dev`          前端开发专家            React/Vue 等前端项目开发

  `database`              数据库专家              SQL、表关系、索引和查询性能

  `architecture`          架构专家                技术方案、影响面和架构风险

  `test`                  测试专家                测试策略、用例、回归和缺陷分析

  `code-review`           代码审查专家            Diff 审查、安全、性能和规范

  `product-requirement`   产品需求专家            需求澄清、PRD、验收标准

  `delivery-director`     项目交付总监            计划、里程碑、风险、验收与回款关注点

  `project-manager`       项目经理专家            任务拆分、进度、沟通和问题闭环

  `implementation`        实施工程师专家          业务调研、基础资料、流程配置和上线准备
  ----------------------------------------------------------------------------------------

专家可按系统/团队配置启用。内置专家不是硬编码分支；通过配置定义其元数据、指令模板和能力声明。

## 2.1 专家角色边界

-   MES5 专家必须遵守 MES5 规范，不得套用 MES6 Furion/DDD 写法。
-   MES6 专家必须遵守 MES6 现有分层和 SqlSugar 规范。
-   WMS 专家应先识别仓库实际技术栈，不假设 WMS 与 MES 同构。
-   前端专家先识别根目录框架和组件体系。
-   数据库专家只做结构分析和经授权的只读查询；写入操作需要人工确认。
-   测试专家不得把"生成测试用例"说成"测试已通过"。
-   代码审查专家默认只读，不直接修改代码。
-   交付类专家输出管理建议，不替代真实项目数据或用户决策。

# 3. 用户故事与功能需求

## FR-01 专家中心

新增/完善专家中心，支持： - 专家列表、分类、搜索 -
专家详情：职责、适用系统、能力、限制、工具权限 - 启用/停用 -
编辑用户自定义专家 - 克隆专家 - 恢复内置默认配置 - 专家版本与修改历史 -
测试专家指令（沙盒会话）

内置专家的系统 ID
不可修改；用户可以复制后自定义。删除自定义专家前检查是否被工作流引用。

## FR-02 总控 Agent 自动召唤

用户不必每次手动选择专家。总控 Agent
根据任务内容和项目类型推荐协作计划。

调度逻辑分三档： 1. 单专家：简单任务，直接委派一个专家。 2.
顺序协作：例如需求分析 → 架构评估 → 开发 → 测试 → 审查。 3.
并行协作：互不依赖的只读分析任务并行执行。

自动调度前显示简要计划；用户可： - 接受 - 修改专家 - 删除某个子任务 -
改为单 Agent 执行 - 取消计划

用户可在设置中选择"自动执行低风险计划"或"每次先确认"。默认每次确认。

## FR-03 专家任务契约

每个子任务必须使用结构化契约：

``` json
{
  "taskId": "uuid",
  "expertId": "mes6-dev",
  "objective": "定位并分析报工接口",
  "projectId": "project-id",
  "sessionId": "session-id",
  "systemType": "MES6",
  "scope": {
    "paths": ["ProductionManagement/"],
    "mode": "read_only"
  },
  "constraints": ["不修改文件", "不执行数据库写入"],
  "expectedOutput": [
    "entrypoints",
    "callGraph",
    "relatedEntities",
    "risks",
    "evidence"
  ],
  "acceptanceCriteria": [
    "每个结论包含文件路径和符号位置"
  ]
}
```

专家输出必须符合 schema。解析失败时标记
`invalid_output`，要求重新输出一次；再次失败交给总控处理。

## FR-04 专家协作编排

支持： - 任务依赖 DAG - 并行只读任务 - 顺序任务 - 最大并发数设置 -
子任务超时 - 单任务取消 - 全部取消 - 失败重试上限 - 专家结果汇总 -
结果冲突检测

默认并发： - 只读分析：最多 3 个 - 写入任务：同一 Worktree 同一时间最多
1 个写入专家 -
代码审查与测试分析可与只读分析并行，但不得与未稳定的文件写入产生竞态。

## FR-05 专家工具权限

权限按专家声明与用户全局策略取交集，不能由专家自行扩大。

权限档位： - `read_only`：读取文件、搜索、分析 -
`workspace_write`：当前会话 Worktree 内修改 -
`command_execute`：执行白名单/用户允许的命令 -
`external_access`：访问网络/API，默认关闭或沿用用户会话授权 -
`high_risk`：数据库写入、Git
push、删除、外部系统写回，必须人工确认且本版本默认不开放给专家

默认权限： - 架构、数据库、代码审查、需求专家：只读 - 开发专家：Worktree
写入和当前会话允许的命令 -
测试专家：测试命令执行，不得更改业务代码；若需修复，向总控申请开发专家任务 -
交付/项目经理/实施专家：项目资料只读，不自动操作客户系统

## FR-06 专家知识配置

每个专家可绑定： - 通用知识 - 系统知识（MES5/MES6/WMS/前端） -
专家专属文件 - 用户自定义指令 - 不适用知识排除项

知识源需记录 ID、名称、版本、摘要和
SHA256（适用时）。知识内容在本版本可沿用现有数据字典/开发规范存储，不重复建设知识检索引擎。

## FR-07 专家执行面板

显示： - 专家名称和头像 - 任务目标 -
状态：待调度/排队/执行中/等待输入/成功/失败/已取消 - 当前 Runtime
和模型 - 开始/结束时间 - 工具活动摘要 - 结果与证据 - 重试次数 - 取消操作

不得展示或持久化隐藏推理链。只展示可公开的任务计划、工具事件和结果摘要。

## FR-08 总控结果验收

总控 Agent 必须按验收标准逐项核对专家交付物： - 结构完整 - 证据可定位 -
不超出任务范围 - 未声称未执行的验证 - 专家间结论冲突已标记 -
未解决问题明确列出

无法验收时，不得将整个协作任务标记为成功。

# 4. 关键工作流

## 4.1 MES6 代码修改工作流

1.  总控识别 MES6。
2.  MES6 开发专家只读分析入口和同类实现。
3.  架构专家评估影响面（只读）。
4.  总控生成修改计划并让用户确认。
5.  MES6 开发专家在当前 Worktree 实施。
6.  测试专家制定测试建议/检查覆盖点。
7.  平台执行真实构建/测试。
8.  代码审查专家读取真实 Diff。
9.  总控汇总变更、验证证据和风险。

## 4.2 项目交付分析工作流

1.  项目经理专家整理进度、问题、责任人和下一步。
2.  交付总监专家分析里程碑、验收、回款和资源风险。
3.  实施专家分析现场准备、基础数据和业务流程问题。
4.  总控合并冲突和缺失信息，输出管理建议。
5.  未提供的数据必须标注"待补充"，不得编造。

# 5. 技术方案

## 5.1 架构

沿用现有子 Agent / Runtime Adapter。增加统一 Expert
Registry、Planner、Orchestrator、Task Contract Validator 和 Result
Aggregator。

逻辑模块：

``` text
ExpertRegistry
  ├── BuiltinExpertDefinitions
  ├── UserExpertDefinitions
  └── ExpertVersionStore

ExpertPlanner
  ├── TaskClassifier
  ├── ProjectSystemResolver
  └── CollaborationPlanBuilder

ExpertOrchestrator
  ├── DAGScheduler
  ├── ConcurrencyLimiter
  ├── PermissionResolver
  ├── RuntimeDispatcher
  └── CancellationManager

ExpertResult
  ├── ContractValidator
  ├── EvidenceResolver
  ├── ConflictDetector
  └── ResultAggregator
```

Codex 必须先映射现有子 Agent
实现，尽量将其重构为上述职责，不得再造一套并行执行引擎。

## 5.2 数据模型

建议实体： - `experts` - `expert_versions` - `expert_tasks` -
`expert_task_dependencies` - `expert_task_events` -
`expert_knowledge_bindings` - `collaboration_plans`

字段使用现有 SQLite
命名规范。所有用户自定义配置必须可迁移、可导出备份。专家 ID 稳定且唯一。

## 5.3 Planner 输出

Planner 只能输出结构化计划，不允许直接执行工具。建议 schema：

``` json
{
  "planId": "uuid",
  "goal": "用户目标",
  "tasks": [
    {
      "taskId": "uuid",
      "expertId": "architecture",
      "objective": "分析改动影响面",
      "dependsOn": [],
      "mode": "read_only",
      "acceptanceCriteria": ["列出受影响模块和证据"]
    }
  ],
  "requiresUserApproval": true,
  "riskLevel": "low"
}
```

通过 JSON Schema 校验后才交给
Orchestrator。计划中未知专家、循环依赖、超出权限、超并发数量时拒绝执行。

## 5.4 专家调用与上下文隔离

每个专家调用只获得完成该子任务所需的上下文： - 用户目标摘要 -
当前项目识别结果 - 授权路径 - 相关规范/知识 - 任务契约 -
必要的上游专家结果

不得把所有历史聊天、全部知识库和其他专家的完整上下文无差别注入。

专家输出需保留来源文件路径、行号/符号、工具事件
ID。引用必须能在当前工作区或资料库验证。

## 5.5 失败与恢复

专家任务状态与主任务状态关联。支持单专家失败重试、单任务取消和整体取消。主任务中断后沿用阶段一的运行恢复机制。重试不得创建重复写入任务。

## 5.6 UI

专家中心： - 分类标签 - 搜索 - 专家卡片 - 专家详情 - 编辑/克隆/测试

任务执行： - DAG/列表两种视图 - 专家状态 - 任务依赖 - 执行日志 -
结果证据 - 冲突提醒

避免把界面做成纯装饰性的"AI
头像墙"。专家的核心信息是职责、状态、成果和证据。

# 6. 验收标准

-   [ ] 内置专家至少覆盖本方案列出的研发、测试、架构、需求、交付角色。
-   [ ] 可新增、编辑、克隆、停用自定义专家。
-   [ ] Planner 能生成合法结构化计划并识别项目系统。
-   [ ] 用户可在执行前修改或拒绝计划。
-   [ ] DAG 依赖正确执行，循环依赖会被拒绝。
-   [ ] 并行只读任务受并发上限控制。
-   [ ] 同一 Worktree 不会出现两个并发写入专家。
-   [ ] 专家权限不能超过会话和全局授权。
-   [ ] 每个专家结果通过 schema 校验并包含可验证证据。
-   [ ] 结果冲突和未解决问题不会被隐藏。
-   [ ] 专家失败/取消不会导致主会话或其他任务状态错误。
-   [ ] 任务中断后可恢复计划和专家状态。
-   [ ] 专家不具备默认 Git push、生产数据库写入或 Jira 写回权限。
-   [ ] 专家中心与执行面板在 Windows 桌面端完成回归。

# 7. Codex 开发步骤

1.  盘点当前子 Agent、专家中心 UI、Runtime 调度和任务状态代码。
2.  输出"现有能力复用/缺失/改造"映射表。
3.  先实现 Expert Registry 与契约 schema。
4.  再实现 Planner 的结构化计划和用户确认。
5.  再实现 Orchestrator、DAG、并发和权限。
6.  最后实现 UI、结果聚合和回归。
7.  不要先批量写专家 Prompt；先把运行机制、契约和权限做对。
8.  每个专家至少提供 3 个测试样例，覆盖正确路由、错误路由和边界任务。
9.  对所有新增数据库表提供迁移和回滚说明。
10. 最终输出变更文件、测试证据、未完成事项和兼容性说明。
