## 1. 版本目标与产品判断

### 1.1 本次版本要解决的问题

精工 Agent 当前已经具备多 Runtime 执行、产品操作手册知识库、项目数据字典、项目开发规范、Skill/插件管理、Memory Engine、Agent Orchestrator、任务治理和验证能力。但这些能力分布在不同模块中，用户仍需要通过任务描述、会话上下文或手工选择，让 Agent 知道当前应该采用什么专业方法。

0.9.3 不以新增一个“专家管理页面”为最终目标，而是把已有专业资产组合成可复用、可验证的专家工作能力：

1. 默认知道自己正在处理 MES5、MES6 还是 WMS 项目。
2. 能区分开发、需求分析、实施问题等任务类型，并采用对应工作流程。
3. 能按当前项目和任务检索正确的操作手册、数据字典、开发规范及项目资料。
4. 能按需选择已经安装、已信任且与当前 Runtime 兼容的 Skill。
5. 输出能说明依据、来源、推断和不确定性。
6. 通过固定测试集和用户反馈验证专家是否真的比普通 Agent 做得更好。

### 1.2 核心产品决策：默认专家

**精工 Agent 的默认专业入口定义为“MES/WMS 需求与研发总专家”（`mes-wms-engineering`）。**它是一个路由专家（Router），不是独立 Runtime，也不负责亲自扮演所有细分岗位。

总专家下面配置可独立评测的专业角色档案（Specialist Profile），包括：

- 需求分析专家：业务需求、现状差异、范围拆解、方案和验收标准。
- 后端开发专家：服务端代码、业务逻辑、数据库、接口、事务、性能。
- 前端开发专家：页面、组件、状态管理、交互、样式和接口联调。
- 全栈开发专家：跨前后端的完整功能改造与联调。
- 测试质量专家：测试策略、测试用例、缺陷复现和回归验证。

项目交付另设“项目交付总专家”（`project-delivery`）路由入口，下面分为：

- 项目总监专家：项目群经营、资源调度、项目盈亏、重大风险、验收与回款总体分析。
- 项目经理专家：单项目范围、进度、计划、客户协同、风险、验收和回款计划。
- 实施工程师专家：系统配置、业务操作、基础数据、培训、上线和现场问题排查。

上述细分角色是**专家配置与工作流切换**，不是多个自主 Agent。0.9.3 默认在同一个会话、同一个 Runtime 中执行，不启动多专家并行任务。用户选中总专家后，系统按任务自动解析细分角色；用户也可以手动指定角色覆盖自动判断。

默认启用规则：新建 MES5、MES6、WMS 项目会话时绑定 MES/WMS 需求与研发总专家。项目交付总专家可在用户选择或识别到明显项目经营/交付管理任务时启用，不替代研发默认专家。

总专家和细分专家都通过结构化配置组合角色原则、工作流、知识源绑定、Skill 规则、输出规范、权限边界和评测规则，不以一段超长 Prompt 代替专业能力。

### 1.3 默认启用规则

| 当前会话情况 | 默认行为 |
|---|---|
| 项目系统明确为 MES5 | 自动启用 MES/WMS 开发与需求专家，知识范围优先 MES5 + COMMON |
| 项目系统明确为 MES6 | 自动启用 MES/WMS 开发与需求专家，知识范围优先 MES6 + COMMON |
| 项目系统明确为 WMS | 自动启用 MES/WMS 开发与需求专家，知识范围优先 WMS + COMMON |
| 独立会话，无关联项目 | 默认专家保持可用；根据用户请求判断是否适用 MES/WMS 专业模式，不强行注入所有知识 |
| 项目类型为 SRM/JMOM/PDA/前端/其他 | 不把项目强行识别为 MES/WMS；默认专家显示不适用或仅提供通用对话，用户可以手动选择其他专家 |
| 项目产品类型未知或冲突 | 不猜测产品；允许用户在会话中指定产品范围，指定后只作用于当前会话 |

项目类型以现有项目指纹识别结果和项目配置为准。不能因为用户某一轮消息提到“MES6”就永久修改项目产品类型。

### 1.4 专业能力建设的层次

| 层次 | 组成 | 0.9.3要求 |
|---|---|---|
| 角色定义 | 总专家、细分专家角色、职责边界 | 建立路由专家和专业角色档案 |
| 专业知识 | 按研发、交付、实施等岗位组合手册、字典、规范和项目资料 | 复用现有知识模块，按角色过滤和排序 |
| 工具与工作流 | 已有 Skill、任务步骤、输出模板、工具能力 | 为不同角色绑定不同工作流，不自建 Runtime |
| 能力验证 | 各专业角色独立测试、评价、基准对比和反馈 | 验证细分角色是否优于通用总专家 |
| 角色路由 | 项目系统、文件类型、任务意图和数据范围 | 自动识别岗位视角，并允许用户覆盖 |

### 1.5 一句话目标

**让精工 Agent 默认具备 MES/WMS 需求与研发总专家，并能在需求分析、后端、前端、全栈、项目总监、项目经理和实施工程师等岗位视角间准确切换；用真实知识、工作流和评测证明专业提升。**

## 2. 当前基础与复用原则

当前仓库 `develop/desktop-poc` 的 0.9.2 已存在以下能力，开发前必须再次阅读源码确认具体接口：

| 现有模块/文件 | 已有能力 | 本次扩展方式 |
|---|---|---|
| `packages/operation-manuals` | MES5/MES6/WMS/SRM/JMOM/PDA/COMMON 分类、手册版本、章节切片、来源定位、引用格式 | 为专家配置产品知识范围，调用现有检索和引用能力 |
| `apps/desktop/src/main/operation-manual-library.ts` | 手册导入、替换、解析任务和本地索引管理 | 专家不复制或重新存储手册 |
| `apps/desktop/src/main/context-sources.ts` | 操作手册、数据字典和记忆的上下文候选构建 | 扩展候选过滤和专家上下文组装 |
| `packages/dictionary-context` | 字典只读检索与片段读取工具 | 按专家绑定范围启用现有工具 |
| `packages/knowledge` | 文档安全检查、资料限制等 | 复用安全校验，禁止把资料内容当系统指令 |
| `packages/plugin-manager` | 插件解析、信任状态、Skill 描述符 | 复用已有插件和 Skill，不重复导入 |
| `packages/plugin-manager/src/skill-matcher.ts` | 按提示词、系统类型、范围匹配 Skill | 将专家配置作为额外筛选/加权因素 |
| `packages/domain/src/skill-intelligence.ts` | Skill 兼容状态、范围和使用事件 | 用于专家 Skill 快照及兼容判断 |
| `packages/memory-engine` | 可复用偏好、规则和经验记忆 | 与显式知识库分离，不把手册写入 Memory |
| `packages/agent-orchestrator` | 子任务、任务契约、依赖和预算治理 | 0.9.3 不扩展为多专家自动并行 |
| `packages/agent-runtime` | Codex、精工、Claude、Grok 等 Runtime 适配 | 专家上下文由平台统一组装后注入，不在 Runtime 内各写一套 |
| `packages/policy`、Runtime 能力认证 | 权限及能力治理 | 保持原有认证门禁，不降低或绕过 |
| `packages/performance` | 上下文候选和预算相关能力 | 复用现有上下文预算和性能指标 |
| `packages/storage` | sql.js 本地存储及迁移 | 在现有数据库和迁移体系内扩展 |
| `apps/desktop/src/preload/index.ts` | Desktop API 暴露 | 按现有 IPC 白名单方式增加专家 API |
| `apps/desktop/src/renderer` | 当前各管理面板 | 按现有 UI 组件和样式约定开发专家中心 |

**禁止**：新建第二套手册库、第二套字典库、第二套 Skill 管理器、第二套 Runtime 调用器或绕过现有 Agent Orchestrator 的平行执行系统。

## 3. 用户与典型场景

### 3.1 主要用户

- MES/WMS 项目经理：分析客户需求、影响范围、项目实施问题和交付风险。
- MES/WMS 实施顾问：检索产品操作、分析业务流程、处理基础数据差异。
- MES/WMS 开发人员：阅读项目结构、开发规范、数据字典，完成代码开发和验证。
- 交付负责人：统一项目分析口径，复用项目经验和工作模板。

### 3.2 典型场景

| 场景 | 输入示例 | 专家预期行为 |
|---|---|---|
| 新开发任务 | “在 MES6 增加工单完工数量校验” | 读取当前项目规范和相关代码，识别影响范围，列出实现方案，执行代码变更并验证 |
| Jira 需求 | “分析这个 Jira 需求，先给我方案” | 读取 Jira 内容和附件，结合产品手册/项目代码分析，先输出需求方案和技术方案，不擅自直接编码 |
| 客户需求分析 | “客户想在 WMS 增加批次追溯” | 区分现有能力与新增需求，拆分业务规则、数据、流程、权限、接口和验收点 |
| 操作问题 | “MES5 委外领料怎么操作？” | 检索 MES5 手册，输出菜单路径、前置条件、步骤和引用位置 |
| 基础数据导入 | “客户模板和系统导入模板不一样，怎么处理？” | 比较字段、数据类型、编码规则、必填约束，给出映射与转换方案；必要时生成映射表或转换脚本，但未经授权不覆盖源文件 |
| 代码影响分析 | “修改这个字段会影响哪些功能？” | 检索字典、代码引用、项目规范，区分静态证据和推断 |
| 测试用例 | “根据这个需求生成测试用例” | 按需求场景、前置条件、测试数据、步骤、预期结果组织用例 |
| 专家纠错 | 用户反馈“这个菜单路径不对” | 保存反馈与专家运行关联，支持追踪引用来源及检索错误，不把单次反馈直接自动改写专家规则 |

## 4. 功能范围与版本边界

### 4.1 0.9.3 P0（本次必须实现）

1. MES/WMS 需求与研发总专家（默认路由专家）及需求分析、后端开发、前端开发、全栈开发细分角色。
2. 项目交付总专家及项目总监、项目经理、实施工程师三个细分角色。
3. 测试质量专家。
4. 新会话默认绑定工程研发总专家；默认绑定不构成手动锁定，任务级可在工程研发与项目交付家族间切换，再路由到细分角色；支持用户手动锁定角色/家族。
5. 专家上下文构建：角色规则 + 当前产品/技术栈 + 工作流 + 现有知识候选 + 可用 Skill + 输出约束。
6. 各角色独立的知识源、Skill 推荐标签、输出模板和验收清单。
7. 操作手册、数据字典、开发规范、项目资料与交付经营数据的绑定策略。
8. 知识来源引用展示和无结果/冲突提示。
9. 专家运行快照和脱敏运行记录，能够追溯“路由专家 + 实际细分角色”。
10. 用户对专家结果提交有帮助/无帮助/不准确反馈。
11. 评测用例管理、基准运行和角色级评测结果查看的最小闭环。

### 4.2 0.9.3 P1（资源允许时完成）

- 专家中心管理页：列表、详情、编辑、复制、停用、恢复默认。
- 用户自定义专家档案。
- 专家输出模板管理。
- 评测用例批量导入/导出 Markdown 或 JSON。
- 专家版本差异查看。

若实现时间受限，优先保证默认专家、知识绑定、工作流和评测，不得为了先做漂亮管理界面而省略专业能力。

### 4.3 明确不在 0.9.3 范围

- 多专家自动并行协作、专家团自动讨论和投票；0.9.3 的多个角色只是在同一 Runtime 内切换专业上下文，不是多 Agent 并发。
- 重新实现 Runtime、模型路由、上下文压缩或模型协议。
- 模型微调、训练专属模型、自动更新模型权重。
- 专家自动修改自身规则、自动发布新 Skill。
- 未经认证的子 Agent 自动创建、自动执行或自动写入。
- 云端专家市场、团队账号同步和服务端专家配置中心。
- 自动执行生产数据库写入、客户系统部署或未经用户授权的外部操作。

## 5. 专家档案模型与内置专家

### 5.1 专家档案必备字段

| 字段 | 说明 |
|---|---|
| `id` | 稳定标识，如 `mes-wms-engineering` |
| `familyId` | 专家家族 ID，如工程研发、项目交付 |
| `parentExpertId` | 细分角色所属总专家 ID；总专家为空 |
| `profileKind` | `router`（总专家）或 `specialist`（细分角色） |
| `roleKey` | 专业角色枚举，如 `backend_developer`、`project_manager` |
| `name` | 专家名称 |
| `description` | 用一句话说明职责 |
| `category` | `engineering` / `delivery` / `quality` / `custom` |
| `version` | 专家档案版本，整数递增或遵循现有版本策略 |
| `builtIn` | 是否内置 |
| `enabled` | 是否启用 |
| `isDefault` | 是否为默认专家；全局同一时刻最多一个默认值 |
| `productScope` | 适用产品集合，MES5/MES6/WMS 等 |
| `roleDefinition` | 角色职责和专业立场 |
| `capabilities` | 能力声明，不代表权限授权 |
| `routeRules` | 仅总专家使用，定义细分角色触发条件和优先级 |
| `workflowBindings` | 绑定的工作流 ID |
| `knowledgeBindings` | 绑定的知识源类型、产品范围和过滤规则 |
| `skillBindings` | 推荐/固定 Skill ID，不能包含 Skill 正文或秘密 |
| `outputTemplates` | 工作流输出结构 |
| `guardrails` | 禁止事项、未知处理和引用规则 |
| `createdAt` / `updatedAt` | 时间 |
| `contentHash` | 档案规范化内容 SHA-256 |

角色提示词必须拆分为职责、目标、流程、边界、输出规范等结构化字段，不允许只保存一段超长 Prompt 作为唯一配置。

### 5.2 内置专家 1：MES/WMS 开发与需求专家（默认）

- ID：`mes-wms-engineering`
- 适用产品：MES5、MES6、WMS
- 默认状态：启用、默认
- 主要任务：开发、需求分析、实施支持、数据问题分析、技术方案、测试用例。
- 知识绑定：当前产品对应的操作手册 + COMMON；当前项目数据字典；项目开发规范；当前项目资料/决策；用户明确选择的会话附件。
- Skill 绑定：不预设不存在的 Skill ID。运行时从已信任、已启用且兼容当前 Runtime 的 Skill 中按任务动态匹配；内置档案可以声明推荐标签。
- 权限：不授予任何额外系统权限。开发权限沿用当前会话 Runtime 与现有权限策略；只读分析任务沿用原有任务契约。

#### 开发工作模式

1. 确认项目系统和技术栈，读取项目根目录 `AGENTS.md`、README 和构建入口。
2. 用户未指定实现细节时，先分析目标、影响范围和风险；需求任务要求先出方案时，不得跳过方案直接修改。
3. 修改代码前先检查同目录/同模块至少 2–3 个同类实现，遵守项目既有架构和编码规范。
4. 优先复用现有服务、数据模型、工具和 UI 组件，不重复建设。
5. 明确修改文件、业务影响、数据兼容和异常处理。
6. 执行项目正式构建、相关测试和必要验证；没有执行的验证必须标记未执行。
7. 总结改动、验证结果、限制和遗留风险。

#### 专业角色拆分（0.9.3 正式范围）

默认总专家必须能区分以下角色。它们不是只换名称的提示词，而是各自绑定任务工作流、知识源优先级、Skill 标签、输出结构和验收清单。

| 角色 ID | 显示名称 | 主要任务 | 专属能力重点 |
|---|---|---|---|
| `mes-wms-requirements` | 需求分析专家 | 客户需求、Jira 需求、现状差异、方案 | 业务流程、范围、字段/数据/接口、权限、验收标准 |
| `mes-wms-backend` | 后端开发专家 | 服务端开发、缺陷、性能和数据库任务 | API、Service、Repository、SQL、事务、缓存、权限、异常、性能 |
| `mes-wms-frontend` | 前端开发专家 | 页面、组件和交互开发 | 项目 UI 规范、组件复用、状态管理、表单校验、交互和样式 |
| `mes-wms-fullstack` | 全栈开发专家 | 同一需求跨前后端完整交付 | 前后端影响关系、接口契约、联调、端到端验证 |

后端/前端必须依据当前仓库真实技术栈执行，不得仅凭 MES5/MES6/WMS 产品类型假设语言、框架或架构。项目产品识别与开发方向识别是两个独立维度：例如 MES6 是产品系统，后端/前端是本轮任务角色。

**后端开发工作重点**：先读项目 `AGENTS.md`、根目录 README、入口和构建方式；识别后端框架、ORM、数据库方言、事务和权限模式；修改前查看同模块同类实现；避免跨模块副作用；完成正式构建和可执行测试。

**前端开发工作重点**：先读根目录 package.json、框架/构建配置、现有组件和状态管理；优先复用现有 UI 组件、设计 token、交互模式；关注响应式布局、加载/禁用/错误/空状态、键盘可达性和接口错误处理；在可用环境中执行前端构建及桌面冒烟。

**全栈开发工作重点**：先明确需求边界和接口契约，再拆分前后端影响；后端与前端实现必须在同一功能目标下保持字段、状态码、校验和权限一致；至少完成接口契约检查、构建和联调验证。若当前仓库没有某一端代码，不得虚构该端已完成。

#### 需求分析工作模式

1. 识别需求来源、角色、业务目标、触发条件、当前痛点和范围边界。
2. 结合操作手册和当前产品版本，分析现有功能及其不足；没有证据时不得断言系统已支持或不支持。
3. 拆解业务流程、角色权限、单据状态、字段、校验、接口、异常、报表和历史数据影响。
4. 标注明确需求、合理推断、待客户确认事项和不在范围事项。
5. 输出需求清单、流程说明、边界/规则、技术实现建议、影响分析和验收标准。
6. 按需求生成正向、逆向、边界、权限和异常测试用例。
7. 若用户只要求需求方案，不进入代码修改阶段；得到用户继续开发的明确指令后再开发。

#### 实施支持工作模式

1. 优先匹配当前产品手册和版本。
2. 输出业务前置条件、菜单路径、操作步骤、注意事项和真实出处。
3. 结合字典分析基础资料字段、编码、关联关系和数据约束。
4. 遇到客户模板与系统模板差异时，先做字段映射分析；未经授权不覆盖文件、不写入生产系统。
5. 手册未覆盖的内容要显式说明，并给出需要现场确认的问题。

### 5.3 内置专家 2：项目交付总专家及三个细分角色

项目交付采用“总专家路由 + 三个岗位角色”的结构。总入口 ID：`project-delivery`。它根据用户问题判断是项目群经营管理、单项目管理还是现场实施执行。

#### 5.3.1 项目总监专家（`project-director`）

定位：项目群/交付组织经营管理视角，面向交付总监、战区负责人和项目交付管理层。

主要职责：

- 多项目健康度、项目组合优先级、重大风险和升级事项。
- 交付收入、项目成本、毛利/亏损、应收和回款计划分析（仅在有真实数据时计算）。
- 人员负载、项目资源冲突、团队产能和人员配置建议。
- 项目经理绩效和项目管理机制分析。
- 重大客户关系、项目停滞、验收障碍和跨部门协同。
- 输出管理决策、资源调整建议、责任人、截止日期和风险影响。

不得把缺失的经营数据当成零；金额、毛利率、回款率必须说明统计口径和数据来源。无法读取项目组合/经营数据时，先列出缺失资料，不得编造项目经营结论。

#### 5.3.2 项目经理专家（`project-manager`）

定位：单个 MES/WMS 项目的经营与交付负责人视角。

主要职责：

- 项目范围、合同交付边界、蓝图、里程碑、主计划和进度偏差。
- 需求变更识别、任务分解、工作量和资源协调。
- 客户关键人、客户待办、内部责任人、沟通纪要和问题升级。
- 风险/问题/依赖管理、延期纠偏和项目周报。
- 阶段验收、签字资料、验收计划、开票与回款计划跟踪。
- 输出项目状态、红黄绿风险、下周计划、责任人和完成时间。

分析必须区分合同范围、已确认变更、口头诉求和待确认事项；不能仅以项目经理自述替代项目证据。

#### 5.3.3 实施工程师专家（`implementation-engineer`）

定位：一线实施交付与现场问题处理视角。

主要职责：

- MES/WMS 业务流程、菜单操作、系统配置和参数核对。
- 主数据、基础数据、导入模板字段映射和数据质量检查。
- 现场问题复现、日志/报错信息整理、排查步骤和复测。
- 用户培训、操作说明、上线检查、切换准备和交接文档。
- 现场问题清单、客户待配合事项、实施日报和遗留问题。

必须优先引用当前产品/版本操作手册与真实系统证据；涉及生产数据库、客户环境或数据覆盖的操作必须遵循现有权限及用户授权，不因“实施工程师”角色自动获得写入权限。

#### 5.3.4 项目交付路由规则

- 多项目、团队/资源、经营指标、项目盈亏或重大升级：优先项目总监专家。
- 单项目计划、范围、进度、客户协同、验收/回款计划：优先项目经理专家。
- 菜单操作、系统配置、基础数据、现场异常、培训和上线执行：优先实施工程师专家。
- 一条问题同时涉及多个层级时，默认先确定主视角，再在同一回答中补充上下游影响；不启动三个 Agent 并行讨论。

### 5.4 内置专家 3：测试质量专家

- ID：`mes-wms-quality`
- 适用：MES5/MES6/WMS 需求验证和软件质量。
- 核心任务：测试策略、测试用例、缺陷复现、回归范围、边界条件、构建/测试证据审查。
- 输出必须区分“测试设计完成”和“测试已实际执行”。

## 6. 专家选择与工作模式路由

### 6.1 选择优先级

专家选择遵循以下优先级：

1. 用户在当前轮明确指定的专家家族或细分角色。
2. 用户在当前会话手动锁定的专家家族/细分角色（`selectedBy=user`）；手动锁定期间不因任务意图自动切换家族。
3. 如果会话绑定来自系统默认（`selectedBy=default`），允许系统根据当前任务意图在工程研发家族与项目交付家族之间自动切换；默认绑定不是强制锁定。
4. 在确定家族后，再解析该家族内的细分角色。
5. 任务意图不清晰或不适用时，回退到当前默认总专家的通用分析视角；不要强行注入不相关专业知识。

例如：MES6 项目会话默认绑定工程研发总专家，但用户在同一会话询问“第二战区多项目亏损和人员资源怎么调整”，本轮应自动切换到项目交付总专家，并路由至项目总监专家。若用户手动锁定了后端开发专家，则不自动切换到项目交付家族，除非用户本轮明确指定。

专家档案不能覆盖用户明确给出的任务要求。

### 6.2 自动专家角色路由

用户默认选择总专家的 `auto` 模式。系统需解析“专家家族（工程/交付）+ 实际细分角色”，不能把后端/前端或项目总监/项目经理/实施工程师都压成一个模糊工作模式。

工程家族角色：

- `requirements`：需求分析专家。
- `backend_development`：后端开发专家。
- `frontend_development`：前端开发专家。
- `fullstack_development`：全栈开发专家。
- `implementation_support`：实施支持；默认使用实施工程师的业务操作视角。
- `quality`：测试质量专家。
- `combined`：确实跨多个专业阶段时使用同一会话内的组合工作流。

交付家族角色：

- `project_director`：项目总监专家。
- `project_manager`：项目经理专家。
- `implementation_engineer`：实施工程师专家。

**识别优先级**：

1. 用户本轮明确指定的专家/角色。
2. 用户在当前会话手动锁定的专家角色。
3. Jira 任务类型、当前工作区/项目结构和当前任务上下文。
4. 用户措辞和任务意图。
5. 无法可靠判断时采用总专家通用分析，不擅自选取高影响角色或执行写操作。

**工程角色判定**：

- 明确修改 Service/API/Repository/SQL/数据库/后端服务时选后端开发。
- 明确修改页面/组件/样式/交互/前端状态时选前端开发。
- 同一功能明确涉及前后端或需要端到端联调时选全栈开发。
- 客户业务需求、Jira 需求、流程和范围梳理时选需求分析。
- 仅当用户要求操作指导、现场问题或系统配置分析时选实施支持。
- 不能只根据文件扩展名判断职责；应结合仓库根级技术栈、调用链和实际改动范围。

**交付角色判定**：

- 多项目组合、战区经营、交付收入成本、资源调度、项目群重大风险、组织产能：项目总监。
- 单个项目的范围/计划/进度/客户沟通/验收/回款：项目经理。
- 现场系统操作/配置/基础资料/导入/培训/上线/问题排查：实施工程师。

路由必须优先使用现有任务元数据、项目识别和用户措辞；不得为每次路由额外单独请求模型。若需模型辅助分类，必须在同一主任务调用中完成，不增加单独的模型往返。系统展示角色名称和路由原因，支持用户覆盖。

### 6.3 会话配置

用户可在聊天区或会话详情中看到：

- 当前专家名称。
- 当前工作模式（自动/开发/需求/实施支持/综合）。
- 当前产品知识范围（MES5、MES6、WMS、COMMON 等）。
- 当前是否启用手册、字典和项目规范检索。

用户可在当前会话临时切换专家或工作模式。切换不应修改项目的全局产品识别结果。

## 6.4 专家家族和细分角色的运行边界

- “总专家”负责路由和通用兜底；“细分专家”负责特定岗位视角，不是独立对话窗口。
- 一轮任务只能解析出一个主细分角色；必要时可在同一个工作流中补充第二视角，但不创建并行 Agent。
- 用户可以从聊天区手动选择“自动”或指定角色，也可切换专家家族。
- 角色切换不能变更项目系统类型、Runtime、模型、当前权限或工作区授权。
- 角色配置只影响专业知识、Skill 推荐、执行步骤、输出结构和质量检查。
- 用户要求一个任务从需求到开发落地时，走全栈/综合流程，按阶段推进，不把多个专家假装成多个 Agent。

## 7. 专业知识绑定和检索要求

### 7.1 知识来源分类

专家只保存“知识源引用与过滤规则”，不复制知识正文。

| 知识类型 | 当前来源 | 专家使用方式 |
|---|---|---|
| 产品操作手册 | `OperationManualLibrary` | 按产品类型、启用状态、版本、手册范围检索 |
| 数据字典 | 现有 ManagedDocument / DictionaryBroker | 按当前项目系统、用户授权范围检索，只读 |
| 开发规范 | 项目根目录 `AGENTS.md`、项目规则和现有规范文件 | 开发任务优先读取当前项目规范；遵循当前代码事实 |
| 项目资料 | 项目文件、项目上下文、已保存事实/决策/资源 | 仅当前项目可见，项目隔离 |
| 会话附件 | 当前会话附件 | 仅当前会话生效，不自动变为全局知识 |
| Skill | Plugin Manager 已登记的 Skill | 通过 ID 引用；按信任、启用、兼容性和范围过滤 |
| Memory | Memory Engine | 只注入与任务相关的可复用偏好/约束，不用于存储手册正文 |

### 7.2 产品匹配

- MES5 项目：优先 MES5，随后 COMMON。
- MES6 项目：优先 MES6，随后 COMMON。
- WMS 项目：优先 WMS，随后 COMMON。
- 不允许 MES5、MES6、WMS 内容混合检索后不标来源。
- SRM/JMOM/PDA 等其他产品分类必须保持独立，不得被默认映射到 WMS 或 COMMON。
- 用户显式选定产品范围时按当前会话设置执行。
- 项目系统未知时不得静默猜测。

### 7.3 相关性和上下文控制

- 优先使用已有检索、打分、去重和 Token 预算机制。
- 检索必须考虑产品类型、项目范围、启用状态、版本和用户显式选择。
- 不把整本手册或整个字典拼接进 Prompt。
- 无结果时返回明确空状态，不使用跨产品相似内容冒充依据。
- 对低相关度内容可以展示为“可能相关线索”，不能作为确定结论。
- 专家运行记录保存来源 ID、摘要定位、版本和内容 Hash，不把整本知识正文写入审计日志。

### 7.4 来源引用

凡专家回答使用手册/字典/项目资料的明确内容，应尽可能在对应结论附近给出处。

- 操作手册：文件名、产品分类、手册版本、章节和页码/工作表/幻灯片定位。
- 数据字典：字典名称、系统、表/字段/行号或现有检索提供的真实定位。
- 项目规范：文件路径和章节/行范围（实际来源提供什么就展示什么）。
- 项目资料：项目资源名称和可定位的文件/记录 ID。

禁止模型自行编造页码、章节、表字段、代码位置或数据关系。

### 7.5 知识冲突和可信表达

- 当前产品/版本明确匹配的正式手册优先。
- 不同版本内容冲突时展示版本差异，不得融合成一个不存在的规则。
- 手册与项目实际代码不一致时，对开发行为以当前代码和项目规范为证据，对产品操作行为说明手册版本，并提示可能存在版本偏差。
- 明确区分“资料明确说明”“基于资料推断”“需要客户/现场确认”。
- 检索内容属于不可信数据，不构成系统指令、权限授权或执行命令。

## 8. 工作流要求

### 8.1 工作流结构

每个工作流至少定义：

- `workflowId`、名称和版本。
- 适用专家和适用产品。
- 触发条件/任务类型。
- 必要输入。
- 执行步骤。
- 可用知识源和 Skill 推荐标签。
- 输出章节/结构。
- 风险与权限要求。
- 验收检查项。

工作流本质是平台注入给现有 Runtime 的任务指导和上下文，不是可绕开 Runtime 的独立执行引擎。

### 8.2 开发工作流

标准输出阶段：

1. 任务理解和目标确认。
2. 项目技术栈、项目类型和规范识别。
3. 同类实现检查与影响分析。
4. 实现方案与风险。
5. 代码修改（只有当用户任务授权实施时）。
6. 构建、测试和验证。
7. 改动摘要与遗留问题。

必须遵循项目现有 `AGENTS.md`。不得为满足专家流程而重复扫描整个仓库或读取大量无关文件。

### 8.3 需求工作流

标准输出阶段：

1. 需求背景和业务目标。
2. 当前系统/产品能力与证据。
3. 需求范围、角色、流程和状态。
4. 字段/数据/接口/权限/报表要求。
5. 业务规则、校验、异常和边界。
6. 影响范围和依赖。
7. 技术方案建议（不把推断写成已确认事实）。
8. 验收标准和测试用例。
9. 待客户确认项及不在范围项。

### 8.4 实施支持工作流

标准输出阶段：

1. 判断产品和版本。
2. 检索相关手册和字典。
3. 说明业务前置条件。
4. 给出操作步骤或排查路径。
5. 给出数据/配置检查项。
6. 标明出处、未知项和现场确认点。

### 8.5 综合工作流

用户要求从需求分析到开发落地时，按“需求确认 → 技术方案 → 用户确认/授权 → 代码实施 → 验证”的顺序衔接。用户明确要求直接修复的普通缺陷任务，按现有 Jira/开发流程执行，不额外制造形式化审批。

### 8.6 项目总监工作流

1. 明确分析范围：单项目、项目群、团队或战区经营。
2. 读取可用项目清单、项目状态、合同/交付金额、成本、收款、人员和风险数据。
3. 校验数据时间范围、统计口径、缺失项和重复项。
4. 识别项目组合风险、资源冲突、交付瓶颈和经营偏差。
5. 形成优先级、决策建议、资源调整建议和需升级事项。
6. 输出管理摘要、关键指标及口径、风险清单、责任人和决策待办。

### 8.7 项目经理工作流

1. 确认项目目标、合同范围和阶段目标。
2. 汇总主计划、实际进度、里程碑、任务和客户依赖。
3. 识别范围变更、延期原因、风险和问题责任。
4. 形成纠偏计划、客户沟通事项和内部协同任务。
5. 更新验收准备、签字资料、开票和回款计划视图。
6. 输出项目状态、问题清单、下阶段计划和客户待办。

### 8.8 实施工程师工作流

1. 识别产品版本、业务模块和用户操作目标。
2. 检索匹配的操作手册、配置说明和项目资料。
3. 收集报错、日志、样例数据和复现步骤。
4. 检查基础数据格式、字段映射、编码、关联和必填规则。
5. 给出一步一步的实施/排查方案和验证方法。
6. 输出现场问题记录、客户配合项、实施结果和遗留问题。


---

## 9. Skill 使用要求

1. 不复制 Skill 文件正文到专家档案；只保存 Skill ID 和推荐条件。
2. Skill 必须来自现有 Plugin Manager，且插件已启用、信任状态有效、Skill 已启用、内容合法、兼容当前 Runtime。
3. 当前 Runtime 的兼容性为 `Full`、`Partial`、`MetadataOnly`、`Unsupported`、`Invalid` 时，沿用现有 `skillCompatibilityStatus` 规则；Unsupported/Invalid 不得执行。
4. 用户显式选择 Skill 优先于自动推荐，但不允许绕过信任、内容安全和 Runtime 兼容检查。
5. 默认专家可以按任务描述、产品类型和专家标签给 Skill 匹配加权；最终匹配仍使用现有 Skill Matcher。
6. 记录 Skill 推荐、选择、加载成功/失败等现有使用事件；日志不记录敏感 Skill 正文和秘密值。
7. 如果没有合适 Skill，正常执行现有模型能力和工具，不得伪造某 Skill 已加载。

## 10. 用户界面与交互

### 10.1 聊天区

在模型/Runtime 等会话状态附近增加轻量专家状态展示：

- 专家名称（默认 MES/WMS 开发与需求专家）。
- 专家家族：工程研发 / 项目交付 / 测试质量。
- 角色选择：自动，需求分析、后端开发、前端开发、全栈开发、项目总监、项目经理、实施工程师、测试质量。
- 自动模式显示当前实际命中的专家角色和路由原因。
- 产品知识范围：自动匹配或当前产品。
- 专家设置入口。

尽量复用现有会话详情面板和 UI 组件，不大幅重构聊天主界面。

### 10.2 专家中心

建议包含：

- 专家列表：名称、类型、适用产品、默认状态、启用状态、版本。
- 专家详情：职责、工作模式、知识绑定、Skill 规则、输出规范和边界。
- 专家编辑：编辑用户自定义专家；内置专家可编辑副本，不允许直接篡改系统内置定义。
- 专家复制：基于内置专家复制并修改，创建独立用户档案。
- 恢复默认：仅对内置专家覆盖配置清空，不删除历史运行记录。

### 10.3 运行详情

在专家运行详情中显示：

- 专家名称、版本和内容 Hash。
- 当前产品系统与工作模式。
- Runtime、Provider/模型（若实际可得）。
- 检索到的知识来源及引用位置。
- 使用的 Skill 名称、版本 Hash 和选择来源。
- 运行状态、失败原因和用户反馈。

不得展示 API Key、Access Token、密码、环境变量值或完整敏感提示词。

### 10.4 反馈入口

每次专家回答允许用户选择：

- 有帮助。
- 无帮助。
- 不准确。

选择“不准确”时可补充原因：知识引用错误、产品版本不匹配、业务理解错误、流程遗漏、代码建议错误、其他。反馈默认只形成记录，不自动修改专家档案。

### 10.5 评测工作台

提供最小可用评测功能：

- 查看评测集、分类和案例数。
- 新增/编辑案例。
- 选择普通 Agent 或指定专家进行测试。
- 选择相同 Runtime/模型配置进行对照。
- 查看每个案例的结果、评分、引用、失败点和综合得分。
- 导出评测结果。

评测页面不能宣称自动评分是客观真值；评分规则和评审方式必须展示。

## 11. 专家能力评测与验收目标

### 11.1 基准集要求

首批建立至少 40 个真实或脱敏案例，按细分角色覆盖：

- 需求分析：8 个。
- 后端开发：6 个。
- 前端开发：5 个。
- 全栈开发：4 个。
- 项目总监：5 个。
- 项目经理：5 个。
- 实施工程师：5 个。
- 测试质量：2 个。

每个案例包含输入、产品系统/项目范围、期望细分角色、预期关键点、权威参考来源（如有）、评分规则和评审备注。案例应来自真实工作，去除客户密码、Token、个人信息和敏感业务数据。每类角色分别统计，不得只提供混合总分。

### 11.2 对照测试规则

- 普通 Agent 与默认专家使用同一个 Runtime、Provider、模型、推理强度、任务输入和会话上下文基线。
- 对照测试应记录配置差异，不能把模型升级导致的提升算作专家提升。
- 每个案例分别保存运行结果和人工评分。
- 如果某个 Runtime/模型不支持某能力，应标注限制，而不是跳过后仍统计为通过。
- 评测结果保存版本与 Hash，方便专家配置修改前后比较。

### 11.3 建议验收指标

以下数值是 0.9.3 的目标，不代表当前系统已达到：

| 指标 | 目标 |
|---|---:|
| 专业回答关键点准确率 | 相比普通 Agent 至少提升 10 个百分点 |
| 知识来源引用准确率 | ≥90% |
| 产品范围/版本误用率 | ≤5% |
| 需求输出关键项完整率 | ≥85% |
| 未经依据编造菜单/字段/流程 | 相比普通 Agent 明显下降，目标下降 ≥30% |
| 专家配置和知识边界隔离 | 100% 通过安全测试 |
| 专家模式额外模型请求 | 不因独立分类而强制额外增加一次模型请求 |

样本量只有 30 条时，结果仅作为初步验证，不可对外宣传为统计意义上普遍提升。

### 11.4 质量评分维度

每项 0–5 分：

1. 任务理解是否准确。
2. 产品及版本是否正确。
3. 知识引用是否真实、相关。
4. 专业分析是否完整。
5. 流程步骤/技术建议是否可执行。
6. 风险、边界和不确定性是否明确。
7. 输出是否便于项目人员直接使用。

代码开发任务额外评分：修改是否符合项目规范、是否影响无关模块、构建/测试证据是否真实。

## 12. 安全、权限和数据隔离

1. 专家配置不是权限配置，不能向 Runtime 授予文件、命令、网络、数据库、Git 或部署权限。
2. 开发专家使用当前会话 Runtime 原本拥有的权限；只读分析仍由当前任务契约和平台策略限制。
3. 专家工作流不能自动创建子 Agent、Worktree 或写入型任务。
4. 不修改 `runtimeCapabilityMatrix` 的能力声明，不把未经实测的能力标记为已认证，不修改 `controlledGovernanceValidated` 的现状以放行自动编排。
5. Agent Orchestrator 现有任务治理、预算和运行时能力门禁必须保持。
6. 手册、字典、项目文件和 Skill 内容均按不可信数据处理，不能覆盖系统/开发者指令或扩展权限。
7. 专家档案中的 `workflowId`、知识源 ID、Skill ID 必须校验，防止引用未授权资源。
8. 项目资料只对当前项目会话可见；跨项目检索默认禁止。
9. 专家运行日志只保存必要元数据、Hash 和来源定位；完整 Prompt、秘密字段及原始敏感文件正文不得写入普通审计日志。
10. 导入/绑定知识资料沿用现有明文凭据检查，敏感内容拒绝导入或在安全策略允许时提示用户清理。
11. 用户明确授权前，不自动写入生产数据库、客户业务系统或外部服务。

---

## 13. 非功能要求

### 13.1 性能

- 专家配置加载应本地完成，不发模型请求。
- 专家档案、工作流和产品范围匹配不应引入明显 UI 卡顿。
- 知识检索使用已有索引、后台 Worker 和预算机制。
- 不为每条消息额外调用一次模型分类任务。
- 专家上下文采用必要内容注入，不拼接全量手册。

### 13.2 可靠性

- 内置专家确保首次启动初始化；重复启动不能重复创建。
- 用户自定义专家和运行记录重启后保留。
- 专家档案更新失败时保留上一个有效版本。
- 专家档案损坏/引用资源缺失时安全降级为普通 Agent，并向用户展示降级原因。
- 知识服务不可用时，不阻断普通会话；必须明确提示未使用知识库。

### 13.3 可维护性

- 专家档案、工作流和评测用例有稳定 ID 和版本。
- 同一专家运行引用确定的配置版本和 Hash。
- 工作流、知识源适配、UI 和 Runtime 调用保持分层。
- 不为每个 Runtime 单独实现专家 Prompt 和知识检索。

## 14. 验收标准

### 14.1 默认专家

- [ ] MES5、MES6、WMS 新项目会话自动绑定 MES/WMS 需求与研发总专家。
- [ ] 总专家能正确路由需求分析、后端开发、前端开发和全栈开发角色。
- [ ] 项目交付总专家能正确路由项目总监、项目经理和实施工程师角色。
- [ ] 会话和单轮运行能显示路由专家、实际细分角色和路由原因。
- [ ] SRM/JMOM/PDA/前端项目不被误判为 MES/WMS。
- [ ] 用户可在会话内切换专家和模式，切换不会污染项目全局产品类型。
- [ ] 独立会话和未知项目有安全降级逻辑。

### 14.2 专业知识

- [ ] MES5 项目优先检索 MES5 + COMMON。
- [ ] MES6 项目优先检索 MES6 + COMMON。
- [ ] WMS 项目优先检索 WMS + COMMON。
- [ ] 不混用其他产品分类资料。
- [ ] 专家回答引用真实的手册/字典/项目来源。
- [ ] 知识无结果时能够明确说明。
- [ ] 版本冲突能被识别和提示。

### 14.3 工作流

- [ ] 用户要求先出需求方案时，不直接修改代码。
- [ ] 后端开发模式遵循项目后端架构、ORM/数据库方言、事务和服务端规范。
- [ ] 前端开发模式遵循根级框架配置、UI 组件、状态管理和设计规范。
- [ ] 全栈模式保持前后端接口契约一致并执行端到端验证。
- [ ] 项目总监模式不臆造项目群经营/财务数据。
- [ ] 项目经理模式输出可执行的项目计划、风险、客户依赖和验收/回款行动项。
- [ ] 实施工程师模式给出有来源的操作/配置/数据处理和验证步骤。
- [ ] 开发完成后如实记录构建和测试结果。
- [ ] 实施支持能提供手册来源和待确认事项。
- [ ] 不因专家模式自动执行额外高权限操作。

### 14.4 Skill 与权限

- [ ] 未信任、未启用或不兼容当前 Runtime 的 Skill 不执行。
- [ ] 专家无法绕过现有 Runtime 和任务权限。
- [ ] 专家无法绕过 Agent Orchestrator 认证门禁。
- [ ] 无专家功能对当前正常 Runtime 使用造成回归。

### 14.5 评测

- [ ] 首批至少 40 个案例可以建立、保存和执行，并能够按细分角色统计。
- [ ] 可以在相同 Runtime/模型条件下对照普通 Agent 与专家。
- [ ] 运行结果、版本、评分和知识来源可追踪。
- [ ] 可以查看分类统计和案例级差异。
- [ ] 用户反馈能关联具体专家运行。

## 15. 推荐开发顺序

1. 盘点现有 Session、Context Builder、LocalStore、IPC 和 UI 接口。
2. 定义专家数据契约、默认专家档案和工作流契约。
3. 实现默认专家初始化、会话绑定、专家/模式选择。
4. 接入已有操作手册、字典、项目规范、项目资料和 Skill 检索。
5. 实现统一专家上下文组装并接入所有现有 Runtime 的共享上下文入口。
6. 增加引用展示、运行快照和用户反馈。
7. 建立评测集、对照评测和结果查看。
8. 完成专家中心管理页和专家自定义能力。
9. 补齐迁移、单元测试、集成测试、桌面冒烟测试和构建验证。

## 16. Codex 开发交付要求

Codex 开发时必须：

1. 先阅读当前分支代码，确认本文档所列模块与当前实现一致；文档和源码不一致时，以当前源码为准，并在交付报告说明差异。
2. 先检查 2–3 个同类 Service、IPC、Storage、Renderer 组件实现，沿用项目现有模式。
3. 先输出实际改动计划和涉及文件，再分阶段实施；用户通过 Jira 需求工作流要求先方案时遵循既有流程。
4. 不得删减或弱化现有测试、权限、认证和安全检查来使新功能通过。
5. 必须兼容已有会话、专家未启用时的旧行为和现有 Runtime。
6. 不允许把评测目标写成已经达成的事实。
7. 完成后提交：改动文件清单、架构说明、数据迁移、测试清单及测试结果、构建结果、已知限制、演示路径。
8. 构建、测试和桌面冒烟按仓库 `README.md` 中正式命令执行；未执行项必须明确标注。

## 17. 后续版本预留

后续版本可以在能力认证和隔离工作区成熟后，考虑：

- 专家团：需求、后端、前端、项目管理和测试角色进行受控协作；前提是 Runtime 能力、权限拦截和隔离工作区完成认证。
- 多专家结果对比和复核。
- 专家使用效果统计和组织级分发。
- 经人工审批后，将反复验证有效的项目经验沉淀为 Skill。

**多专家协作不得作为 0.9.3 默认交付项，也不得通过现有子 Agent 能力门禁未认证的 Runtime 实现。**

## 18. 最终定义

0.9.3 的成功标准不是用户能在页面中看到几个专家头像，而是：

- MES/WMS 项目打开会话就能默认使用专业开发/需求能力；
- 专家能正确使用现有操作手册、字典、开发规范和 Skill；
- 不同任务采用对应工作流程；
- 结果具有真实出处和可检查的验证记录；
- 通过对照评测证明专业质量相对普通 Agent 有提升。

如果专家只增加角色名称和一段提示词，却没有知识绑定、工作流和评测，不视为本需求完成。
