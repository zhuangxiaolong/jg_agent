# 多智能体系统架构调研与差距分析

调研日期：2026-11-10  
仓库：精工Agent 0.6.8（TypeScript / Electron）  
依据：`精工 Agent 多智能体协作系统（Subagents）.md` V1.0、当前工作区源码及锁定 Runtime 源码。

## 结论

本轮已落地一个可运行的 Subagents MVP：主进程维护独立的 Agent Task 控制面，任务绑定会话和项目，按依赖 DAG 调度，最多同时运行 3 个只读 Runtime 实例；任务、事件、结果和失败恢复状态写入 SQLite，并通过 IPC 和右侧 Inspector 展示。当前由用户在面板手动创建任务；主 Agent 尚不能通过工具/API 自动委派子任务。Codex Runtime 与 Jinggong Runtime 共用统一 Adapter 接口，但仍分别启动独立进程，没有启用 Runtime 原生 `features.multi_agent` 能力。

MVP 的边界也很明确：第一阶段子 Agent 只读分析，不创建 worktree、不修改代码、不提交或推送；并发上限是进程内固定值；启动恢复会把遗留的 RUNNING 任务标记为失败并重新调度 PENDING 任务，但不会重放已开始的任务。当前只读沙箱和项目读取工具已经做协议校验，操作系统级“只能读当前工作区”的边界尚未完成独立的 hostile-path 验证，因此文档和界面不能把它表述为完整的工作区隔离。

## 当前架构盘点

| 范围 | 当前实现 | 对 Subagents 的意义 |
| --- | --- | --- |
| Runtime 适配 | `packages/agent-runtime/src/manager.ts` 的 `RuntimeAdapter` 仅提供 Runtime 健康检查、会话启动/恢复、单轮发送、取消和关闭；Manager 按 Runtime 类型选择单个 Adapter。 | 缺少 Agent/Task 的创建、枚举、状态、消息、结果与等待接口。 |
| Codex 协议 | `packages/agent-runtime/src/index.ts` 启动 `app-server --listen stdio://`，调用 `thread/start`、`thread/resume`、`turn/start` 和 `turn/interrupt`；接收器处理当前主线程事件。 | 现有 JS 包没有子 Agent 管理 SDK；须通过锁定版本 app-server 协议适配并验证通知事件，不能假定支持。 |
| Codex 能力门控 | Runtime 握手和桌面 CLI 配置均将 `features.multi_agent` 与 `features.multi_agent_v2` 关闭。锁定版本的 Rust 源码与测试中存在原生委派实现及 feature gate。 | 可研究并接入原生能力，但目前既未启用，也未观测或映射子线程。 |
| Jinggong Runtime | `JinggongRuntimeAdapter` 复用 `CodexRuntime`；主进程当前只持有一个 `runtime` 和一个 `RunLifecycle`。新运行会关闭旧 Runtime。 | 需要 Runtime 实例池和真实调度器，不能靠顺序多轮调用冒充并行 Agent。 |
| 会话与事件 | `Session` 绑定项目、工作区、Runtime；SQLite `events` 以会话为单位保存展示事件，主进程通过 `agent:event` 推送。 | 可沿用会话和实时事件通道；Agent Task 要有单独持久化身份、父子关系和结构化结果。 |
| 存储 | `LocalStore` SQLite schema version 8 新增 Agent Task 与 Agent Task Event；任务结果、错误、尝试次数和事件日志按会话保存，启动时把遗留 `RUNNING` 标为失败并按依赖链重算状态。已有任务的会话不允许改绑项目。 | 已具备任务控制面持久化、事件追踪和恢复基础；没有用量计费或跨设备同步。 |
| 上下文 | 主进程按会话系统筛选开发资料、字典和项目记忆，再通过 `buildDeveloperContext` 注入 Runtime。 | 已有资料可作为公共上下文来源；需为每个子任务构造最小公共上下文及私有任务历史，禁止复制整个主会话历史。 |
| 工具与权限 | 子 Agent 为每个任务创建独立 Runtime home，继承筛选后的开发资料和项目记忆；使用 read-only sandbox、网络关闭、项目读取工具，关闭通用 shell、浏览器和写入工具。 | 已有任务级权限边界和事件归属；只读沙箱的操作系统级路径隔离仍需独立验证。 |
| Git 隔离 | `GitConnector.createWorkspace` 通过受管 `git worktree` 为会话创建 `agent/<id>` 分支，并校验受管路径；push 是显式操作。 | 可以复用 worktree 原语，但新增按 Agent Task 管理的创建/清理/差异集成流程。 |
| 验证 | `packages/verification` 和主进程 `VerificationRunService` 从真实进程状态、退出码、源码指纹及产物生成验证记录。 | Testing Agent 应复用该真实执行证据；模型回复或 Agent 的 COMPLETED 状态不能替代测试通过。 |
| 前端 | `AgentTasksPanel` 已接入右侧 Inspector，可创建任务、填写依赖、查看状态/角色/尝试次数/结果/事件，并按任务停止；主会话取消会级联停止本会话的子任务。任务保存会话模型信息，但 UI 尚不显示模型。 | 当前没有 Agent Registry、自定义 Agent 配置、暂停/恢复和父任务树；主 Agent 仍由现有会话面板表示。 |

## 统一 Runtime Adapter 建议

控制面应以平台 `AgentTask` 为稳定身份，不要求不同 Runtime 暴露相同内部线程 ID。Adapter 的最小契约建议包含：

- 创建任务执行实例，输入 Runtime kind、项目/会话范围、Agent 定义、独立工作区、模型配置、权限及超时。
- 启动或恢复任务，并提供带平台 Agent ID 和 Task ID 的事件流。
- 查询平台映射后的真实状态、发送追加指令、取消/等待任务、读取结构化结果及关闭执行资源。
- 明确声明 capability；未实现的暂停、恢复、原生 Subagents 管理等操作必须返回不支持，不能静默模拟。

Jinggong Adapter 应由平台 Orchestrator 调度独立 Runtime 执行实例，每个写任务绑定独立 worktree。Codex Adapter 应先通过固定版本 app-server 协议接入原生 Subagents，映射 parent/child thread 与 platform task，保留 Runtime 原生状态和事件；若协商或运行时不支持该能力，应在 UI 中明确标示不可用并失败关闭。

## 分阶段实施边界

1. 本轮交付 P0 的只读分析 MVP 子集，尚不能视为 P0 验收完成：Agent Task 类型、依赖 DAG 校验/状态转换、固定 3 槽位调度、独立 Runtime 实例、任务级事件和结果、超时/取消/有限重试、SQLite 持久化与启动恢复、IPC 和 UI 面板。此仓库是 Electron/TypeScript 工程，不含 MES5/MES6 `.sln` 或 `.csproj`；当前需求不直接修改 MES 业务服务。
2. 当前 P0 尚未完整覆盖：主 Agent 尚无委派工具/API，子任务只能由用户手动创建；虽保存 `parentTaskId`，但 UI 未按父子关系呈现，取消也仅支持单任务或整会话级联；结果只有通用摘要/错误文本，尚无主 Agent 可消费的结构化完成回调。并发上限尚未配置化，没有暂停/恢复、用量统计、跨会话 Agent Registry，也没有将测试服务证据自动绑定到任务结果。
3. Codex 和 Jinggong 当前都通过平台 Orchestrator 启动独立 Runtime；Codex 原生多智能体能力仍关闭，不能把 Runtime 内部委派能力当作平台功能。
4. 写入型 Agent、独立 worktree、差异集成和冲突检查属于后续阶段。接入前必须补齐任务级工作区生命周期和用户确认，自动执行不得推送远程仓库。
5. 后续 P1 包括自定义 Agent、独立模型/权限/知识库配置、父子任务视图、暂停恢复、可配置并发和更细的运行指标。真实 MES/WMS 验收还需要目标项目与 Runtime 凭据/环境，不能在此处宣称完成。

## 主要风险与约束

- Codex 上游源码存在能力不代表当前协议接入可用；必须以锁定二进制的真实交互和事件记录验证。
- 主 Agent 的主运行票据与子任务 Runtime 已分离；发送主 Agent 新一轮消息时会阻止同一会话的子 Agent 并发，降低上下文竞争风险。
- 当前子 Agent 只读，不产生代码差异；未来并行写操作即使位于独立 worktree，也可能产生文件冲突，集成需保留基线、计算差异并由用户确认，禁止自动 push。
- 失败重试只在当前 MVP 的只读任务上执行；未来任何写入型或外部操作任务都必须先定义幂等性，不能默认自动重放。
- 任务状态来自 Runtime/进程事件；结果摘要可以结构化，但代码修改、构建和测试结果必须关联实际文件差异及验证服务记录。
- 当前工作区已有多处未提交修改及未跟踪文件。本轮实现只在此基础上局部扩展，不覆盖或撤销既有改动。
