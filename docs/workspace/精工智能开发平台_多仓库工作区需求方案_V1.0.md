> 文档类型：产品需求补充方案  
> 产品名称：精工Agent  
> 需求主题：多仓库工作区（Multi-Repository Workspace）  
> 版本：V1.0  
> 日期：2026-11-09  
> 适用范围：Windows 桌面客户端、Codex Runtime、Jinggong Runtime  
> 文档状态：待产品与研发评审

## 1. 需求背景

目前精工Agent以单个 Git 仓库作为主要代码开发上下文。但实际 MES/WMS 项目经常采用前后端分离或微服务架构，一个完整业务需求可能同时涉及：

- 前端 Web 仓库；
- 后端 API/业务服务仓库；
- 公共 DTO、SDK 或基础组件仓库；
- 定时任务、集成服务或其他微服务仓库；
- 自动化测试、接口契约或部署配置仓库。

如果用户只能在一个会话中选择一个 Git 仓库，AI 很难完整理解跨前后端的业务链路，也无法在一次任务里协同修改多个仓库。

因此，需要新增“工作区 Workspace”概念，将多个独立 Git 仓库组织成一个逻辑开发单元，让 AI 在同一任务上下文中读取、分析和修改多个仓库。

## 2. 产品目标

### 2.1 核心目标

用户可以创建一个工作区，把一个业务系统相关的前端、后端和其他 Git 仓库加入同一工作区；在工作区会话中描述一个完整需求，AI 能够理解仓库之间的关系，规划任务，并根据授权在多个仓库中完成代码修改、测试和变更汇总。

### 2.2 典型使用场景

例如用户创建“MES 生产执行系统”工作区，加入：

| 仓库别名 | 类型 | 示例内容 |
|---|---|---|
| `mes-web` | 前端 | Vue/React 页面、路由、前端 API |
| `mes-api` | 后端 | Controller、Service、DTO、业务逻辑 |
| `mes-common` | 公共组件 | 公共模型、工具类、共享协议 |
| `mes-integration` | 集成服务 | ERP、设备或第三方接口 |

用户提出需求：

> 在生产报工页面增加一个“异常原因”字段，后端增加对应接口字段和数据库保存逻辑，前端完成表单展示、校验和提交，并补充测试。

AI 应能在同一个任务中：

1. 分析前端、后端和公共仓库现状；
2. 找出前后端接口及数据结构的关联；
3. 给出跨仓库实施计划和变更范围；
4. 按依赖顺序修改后端、公共模型和前端；
5. 分别执行各仓库的构建、测试或静态检查；
6. 汇总每个仓库的文件变更、Diff、测试结果和风险；
7. 由用户统一审核，但 Git 提交仍按仓库独立进行。

### 2.3 非目标

本需求不要求：

- 把多个 Git 仓库合并成一个 Git 仓库；
- 自动把多个仓库改造成 Monorepo；
- 将多个仓库合并成一个 Git 分支或一个提交；
- 首期实现跨仓库自动发布、部署或生产变更；
- 首期实现多个 Agent 无限制并行修改同一仓库；
- 要求所有仓库必须放在同一个父目录或同一磁盘。

## 3. 核心产品定义

### 3.1 工作区定义

**工作区（Workspace）是多个独立本地 Git 仓库的逻辑集合。**

工作区不是 Git 仓库本身，也不要求仓库在物理目录上相邻。一个工作区可以引用 C 盘、D 盘或网络映射盘上的多个本地 Git 仓库，但每个仓库必须分别识别其 Git 根目录。

工作区负责管理：

- 仓库列表及仓库角色；
- 仓库之间的依赖和关联说明；
- 工作区级开发说明；
- 各仓库独立的开发规范及运行命令；
- AI 会话和任务范围；
- 多仓库任务计划、执行状态、Diff 和测试汇总。

### 3.2 关键概念区分

| 概念 | 定义 | 关系 |
|---|---|---|
| 工作区 Workspace | 多个仓库的逻辑集合 | 一个工作区包含一个或多个仓库 |
| Git Repository | 独立 Git 仓库 | 每个仓库有自己的 remote、branch、commit 和 status |
| Workspace Session | 绑定某个工作区的 AI 会话 | 会话可在工作区的授权仓库范围内工作 |
| Agent Task | 一次具体开发任务 | 一个任务可涉及工作区中的一个或多个仓库 |
| Task Worktree | 为任务创建的隔离 Git 工作树 | 每个参与任务的仓库分别创建自己的 worktree |

### 3.3 基本原则

1. 一个会话绑定一个工作区，避免不同项目的代码上下文混淆。
2. 一个工作区至少包含一个 Git 仓库，允许单仓库工作区，保证旧功能兼容。
3. 仓库仍然独立管理 Git 状态，不得假设多个仓库共享 Git 元数据。
4. AI 可以跨仓库读取和分析；写入必须受任务范围及用户授权控制。
5. Runtime 必须明确知道本次任务可访问的全部仓库根目录。
6. 各仓库的 Diff、测试、分支、提交及错误状态必须分别展示。
7. Runtime 切换不改变工作区结构和仓库配置。

## 4. 用户角色

首期仍采用本地桌面用户模式，不新增服务器账号体系。

| 角色 | 权限 |
|---|---|
| 平台使用者 | 创建、编辑、删除自己的本地工作区；添加和移除仓库；发起 AI 任务 |
| 开发人员 | 使用工作区开发、查看 Diff、运行测试、管理任务分支 |
| 高级开发人员/技术负责人 | 配置工作区规则、仓库角色、跨仓库依赖及开发命令 |
| 本机管理员 | 管理模型、Runtime、凭据及全局安全选项 |

## 5. 功能需求

优先级定义：P0 = 首个可用版本必须具备；P1 = 首个版本后优先完善；P2 = 后续增强。

### 5.1 工作区管理

#### FR-WS-001 创建工作区（P0）

用户可以在桌面客户端创建工作区，至少填写：

- 工作区名称；
- 工作区描述；
- 可选业务系统/项目标签；
- 默认主仓库（Primary Repository，可选，默认第一个仓库）；
- 工作区级开发说明。

验收标准：创建后工作区在工作区列表中显示，关闭并重新打开客户端后仍然存在。

#### FR-WS-002 添加本地 Git 仓库（P0）

用户可以通过目录选择器添加一个或多个本地仓库。

系统必须：

1. 检查目录是否存在；
2. 通过 Git 命令或 Git 库识别仓库根目录；
3. 获取仓库名称、当前分支、默认分支（可识别时）、remote URL 和工作区状态；
4. 如果用户选择的是仓库子目录，自动定位 Git 根目录并提示；
5. 阻止同一仓库重复加入同一个工作区；
6. 允许同一仓库被不同工作区引用，但必须提示并发任务可能产生文件冲突。

首期只要求添加本地已有仓库。通过 URL 克隆远端仓库列为 P1。

#### FR-WS-003 配置仓库角色和别名（P0）

每个仓库可以设置：

- 唯一别名，例如 `frontend`、`backend`、`common`；
- 显示名称；
- 仓库类型：前端、后端、公共组件、微服务、测试、部署、文档、其他；
- 是否主仓库；
- 是否允许 AI 读取；
- 是否允许 AI 修改；
- 仓库说明及与其他仓库的关系。

工作区内仓库别名必须唯一。仓库真实目录名可以重复。

#### FR-WS-004 移除仓库（P0）

移除仓库只解除工作区关联，不得删除用户本地 Git 仓库或远端代码。

若仓库正在执行任务，必须阻止直接移除，或要求用户先停止/完成任务。

#### FR-WS-005 编辑工作区（P0）

支持修改工作区名称、描述、主仓库、仓库角色、别名、读写权限和关联说明。

#### FR-WS-006 工作区列表与切换（P0）

提供工作区列表，展示：

- 工作区名称；
- 仓库数量；
- 仓库类型摘要；
- 最近使用时间；
- 最近任务状态。

切换工作区后，新会话必须绑定新工作区。不得将上一工作区的代码路径和隐私上下文自动带入新工作区。

### 5.2 工作区视图

#### FR-WS-007 多仓库总览（P0）

工作区主页应展示每个仓库卡片或列表项：

- 别名和仓库名称；
- 仓库路径；
- 当前分支；
- Git 工作区状态（干净/有未提交变更/冲突/不可访问）；
- 是否主仓库；
- AI 访问权限；
- 最近任务及测试状态。

#### FR-WS-008 仓库状态刷新（P0）

支持单仓库刷新和全部仓库刷新。刷新不得修改仓库内容。

#### FR-WS-009 仓库关联关系（P1）

允许用户维护仓库关系，例如：

- 前端调用后端 API；
- 后端依赖公共组件；
- 集成服务依赖后端 DTO；
- 测试仓库覆盖前后端契约。

支持关联说明、方向和可选接口文档路径。AI 规划任务时应读取这些关系。

### 5.3 AI 工作区会话

#### FR-WS-010 工作区会话（P0）

用户在工作区中创建会话后，AI 的上下文应包含：

- 工作区名称和说明；
- 已加入仓库的别名、角色和绝对路径；
- 当前分支及 Git 状态；
- 每个仓库的开发说明和 `AGENTS.md`；
- 仓库之间的关联说明；
- 当前任务允许读取、修改和执行命令的仓库范围。

不得只把主仓库路径交给 Agent 而遗漏其他仓库。

#### FR-WS-011 跨仓库需求分析（P0）

用户可用自然语言描述跨前后端任务。AI 应先识别需求可能涉及哪些仓库，并给出：

- 任务理解；
- 涉及仓库；
- 预估修改模块和文件；
- 仓库间依赖；
- 实施顺序；
- 测试计划；
- 风险和需要确认的事项。

在用户确认实施计划前，默认只允许读取和分析，不应直接修改代码。

#### FR-WS-012 仓库范围选择（P0）

允许用户选择：

- 全部仓库；
- 仅选择部分仓库；
- 指定主仓库并允许 AI 推荐关联仓库。

默认建议为“AI 可读取工作区全部仓库，但写入仓库以任务计划和用户批准为准”。

AI 如需修改原计划外仓库，必须请求用户批准，并说明原因。

#### FR-WS-013 跨仓库执行（P0）

Agent 能在同一任务中对多个仓库完成：

- 搜索和读取代码；
- 理解前后端接口与数据结构；
- 修改不同仓库文件；
- 执行各仓库命令；
- 根据一个仓库的结果调整另一个仓库；
- 汇总任务执行过程。

首期以一个协调 Agent 串行编排依赖性修改为主。允许对互不冲突的只读分析并行执行。对同一仓库的并行写入必须禁止或通过文件/仓库锁协调。

#### FR-WS-014 跨仓库文件引用（P0）

AI 回复中引用文件时，必须显示仓库别名和相对路径，例如：

- `[backend] src/Controllers/ReportController.cs`
- `[frontend] src/views/report/index.vue`

不得仅显示模糊的相对路径 `src/index.ts`。

### 5.4 Git 与任务隔离

#### FR-WS-015 各仓库独立 Git 状态（P0）

每个仓库独立展示：

- 当前分支；
- 工作区变更；
- 暂存变更；
- 未跟踪文件；
- 冲突状态；
- 远端信息（可获取时）。

#### FR-WS-016 任务工作区隔离（P0）

建议默认采用 Git Worktree 为参与任务的每个仓库创建独立任务工作树。每个仓库独立创建任务分支，任务 ID 保持一致但分支仍属于各自仓库。

如果由于仓库状态、Git 版本或配置无法创建 worktree，必须明确提示并提供可选处理方案，不能静默覆盖用户现有变更。

#### FR-WS-017 未提交变更保护（P0）

任务开始前检查所有参与仓库：

- 有未提交变更时，默认不在原目录直接覆盖或清理；
- 优先将用户现有工作状态保留在原工作树，任务在独立 worktree 中执行；
- 无法安全隔离时，暂停并要求用户选择；
- 禁止自动执行 `reset --hard`、`clean -fd`、强制切换分支等破坏性操作。

#### FR-WS-018 多仓库 Diff 汇总（P0）

Diff 面板按仓库分组，展示每个仓库变更文件、增加/删除行数、变更类型和具体 Diff。

支持单仓库 Diff 和工作区全部 Diff 两种视图。

#### FR-WS-019 分仓库提交（P0）

用户可以分别选择仓库进行暂存、提交或合并。提交信息可以从同一任务摘要生成，但每个仓库独立提交。

首期禁止把多个仓库伪装为一个 Git 提交；默认不自动提交、不自动推送、不自动合并。

#### FR-WS-020 多仓库应用变更（P1）

支持用户审核后将各任务 worktree 的变更分别合并/应用回原仓库。每个仓库单独检测冲突和合并结果。

若部分仓库合并成功而其他仓库失败，应明确展示部分成功状态和回退建议，不得宣称整体原子成功。

### 5.5 开发命令与测试

#### FR-WS-021 仓库级开发配置（P0）

每个仓库可以配置：

- 开发语言及框架；
- 安装依赖命令；
- 构建命令；
- 单元测试命令；
- 静态检查命令；
- 启动命令；
- 环境要求及注意事项。

命令应由用户确认后保存；首次运行未知命令时需审批。

#### FR-WS-022 多仓库测试计划（P0）

AI 根据任务涉及仓库和依赖关系生成测试计划，分别执行各仓库测试。

结果至少包括：

- 仓库名称；
- 命令；
- 执行时间；
- 成功/失败/跳过；
- 摘要输出；
- 失败日志入口。

#### FR-WS-023 依赖顺序（P1）

支持配置仓库依赖顺序，例如先构建 `common`，再构建 `backend`，最后构建 `frontend`。

AI 不得仅根据仓库名称推测依赖关系；没有配置时可以给出建议，但需在执行前确认。

### 5.6 工作区记忆和规范

#### FR-WS-024 工作区级规则（P0）

支持工作区级指令，例如：

- 项目整体架构；
- 前后端接口约定；
- 数据格式约定；
- 编码语言和命名规则；
- 跨仓库兼容要求。

#### FR-WS-025 仓库级规则（P0）

支持每个仓库独立的 `AGENTS.md` 或平台规则文件。仓库级规则不得被工作区规则无条件覆盖；发生冲突时应显示规则来源并按明确的优先级处理。

建议规则优先级：平台安全策略 > 工作区强制规则 > 仓库规则 > 用户本次任务要求（安全与强制规范不可被用户提示绕过）。

#### FR-WS-026 工作区记忆（P1）

长期记忆按工作区隔离，记录经确认的架构事实、接口关系、开发约定和已验证经验。

禁止将一个工作区中的客户代码、路径、配置和项目记忆自动带入其他工作区。

### 5.7 Runtime 支持

#### FR-WS-027 双 Runtime 多根目录能力（P0）

Codex Runtime 与 Jinggong Runtime 都必须实现统一的多仓库工作区接口。

每次启动任务时，平台应向 Runtime 传递：

- 主工作目录；
- 全部参与仓库根目录；
- 仓库别名和访问权限；
- 当前任务写入范围；
- 每个仓库的任务 worktree 路径（如启用隔离模式）。

Runtime 不支持多根目录时必须明确报告能力不足并阻止越权写入，不能只把第一个仓库作为工作目录后假装其他仓库已加入。

#### FR-WS-028 Runtime 切换（P0）

保留平台既有双 Runtime 选择机制。默认 Runtime 按当前产品配置执行；切换 Runtime 不改变工作区仓库列表、任务数据和权限策略。

### 5.8 本地数据与兼容性

#### FR-WS-029 本地持久化（P0）

工作区配置、仓库映射、会话关联、任务计划和测试记录保存在本机数据库/配置文件中。

不得把本地仓库内容或敏感项目上下文上传到未配置的远端服务。

#### FR-WS-030 单仓库兼容（P0）

原有单仓库项目应能自动或通过向导转换为只有一个 Repository 的 Workspace。

升级后原会话、模型配置和 Runtime 选择不得丢失。

## 6. 界面需求

### 6.1 工作区入口

桌面主界面增加工作区选择器，至少显示：

- 当前工作区名称；
- 仓库数量；
- 切换工作区入口；
- 新建工作区入口。

### 6.2 工作区管理页

提供仓库列表和管理操作：

- 添加仓库；
- 修改别名、类型和权限；
- 设置主仓库；
- 刷新 Git 状态；
- 移除仓库；
- 配置开发命令；
- 配置仓库关联关系。

### 6.3 Agent 会话页

会话区域应清晰显示当前工作区和本次任务涉及的仓库范围。AI 计划区按仓库显示执行步骤。

### 6.4 Diff 与测试页

Diff、Git 状态和测试结果均按仓库分组。用户可以快速定位哪个仓库失败、哪些文件发生修改。

### 6.5 建议交互示意

```text
工作区：MES 生产执行系统  [切换]

仓库：
  [主] mes-web          前端      D:\code\mes-web
      mes-api          后端      D:\code\mes-api
      mes-common       公共组件  D:\shared\mes-common
      mes-integration  集成服务  E:\services\mes-integration

AI 会话：
  需求：增加生产报工异常原因字段

执行计划：
```

## 7. 主要业务流程

### 7.1 创建工作区

1. 用户点击“新建工作区”；
2. 输入名称、描述；
3. 选择一个或多个本地 Git 仓库；
4. 系统验证每个仓库并识别 Git 根目录；
5. 用户设置别名、类型、主仓库和权限；
6. 用户保存工作区；
7. 系统刷新各仓库 Git 状态并完成初始化。

### 7.2 跨仓库开发

1. 用户打开一个工作区；
2. 创建新的 AI 会话或选择已有会话；
3. 用户输入完整需求；
4. Agent 读取工作区仓库清单、规则和相关代码；
5. Agent 输出跨仓库分析与任务计划；
6. 用户确认涉及仓库和执行权限；
7. 平台检查 Git 状态并为各仓库准备任务工作树；
8. Agent 按依赖顺序修改代码；
9. 平台汇总各仓库 Diff；
10. 分别执行构建、测试和静态检查；
11. 用户审查各仓库变更；
12. 用户分别应用、提交或放弃各仓库变更。

### 7.3 中止与恢复

任务中止时保存：

- 当前任务步骤；
- 每个仓库的工作树路径和分支；
- 已完成的工具调用；
- 尚未完成的仓库步骤；
- 各仓库 Git 状态；
- 已产生的 Diff 和测试记录。

恢复时先重新校验所有工作树仍存在且未被外部修改，再允许继续。

## 8. 验收标准

### 8.1 基础工作区

- [ ] 可以创建一个包含前端、后端和公共组件三个仓库的工作区。
- [ ] 三个仓库可以位于不同磁盘或不同父目录。
- [ ] 系统能正确识别各仓库 Git 根目录、分支和状态。
- [ ] 同一工作区不允许重复添加同一仓库。
- [ ] 移除仓库不会删除本地代码。
- [ ] 重启客户端后工作区和仓库映射仍存在。

### 8.2 AI 跨仓库开发

- [ ] AI 能识别一次需求涉及前端和后端两个仓库。
- [ ] AI 计划中明确列出各仓库的工作步骤。
- [ ] AI 能读取一个仓库中的接口定义并在另一个仓库中正确引用。
- [ ] AI 能在同一任务中修改至少两个独立 Git 仓库。
- [ ] AI 的文件引用包含仓库别名。
- [ ] 未经批准，AI 不能修改任务范围外的仓库。

### 8.3 Git 安全

- [ ] 每个仓库独立显示 Git 状态和 Diff。
- [ ] 任务开始前检测未提交变更。
- [ ] 任务执行不会清理或覆盖用户已有未提交内容。
- [ ] 多仓库变更按仓库独立提交。
- [ ] 不自动 push、不自动 merge。
- [ ] 任务中断后能恢复或安全清理任务工作树。

### 8.4 测试与 Runtime

- [ ] 可以分别配置并执行前端、后端的构建和测试命令。
- [ ] 测试报告按仓库分组。
- [ ] Codex Runtime 和 Jinggong Runtime 都能接收完整工作区根目录列表，或明确报告能力不支持。
- [ ] 两个 Runtime 均不能访问未授权目录。
- [ ] Runtime 切换不会丢失工作区和仓库配置。

### 8.5 向后兼容

- [ ] 原有单仓库项目可以作为单仓库工作区继续使用。
- [ ] 旧会话可继续打开。
- [ ] 原有模型设置和 Runtime 设置保留。

## 10. 风险与约束

| 风险 | 影响 | 要求 |
|---|---|---|
| Runtime 只支持单一工作目录 | AI 看不到或无法修改其他仓库 | Runtime Adapter 必须支持多根目录能力检测 |
| 多仓库 Git 状态不一致 | 可能覆盖用户代码 | 任务前检查并优先采用 Git Worktree |
| 相同文件被并行修改 | 产生覆盖或冲突 | 同仓库写操作串行化或加锁 |
| 仓库间依赖理解错误 | 修改顺序和接口不正确 | 计划先行，用户确认依赖和修改范围 |
| Windows 路径和权限差异 | 文件读写/沙箱失败 | 处理盘符、UNC、大小写、junction、符号链接 |
| 一部分仓库合并成功、一部分失败 | 产生跨仓库版本不一致 | 各仓库独立状态展示和恢复方案 |
| 工作区上下文泄漏 | 项目数据风险 | 会话与工作区绑定，跨工作区隔离 |

## 11. 待确认事项

以下事项应由研发在技术设计和 PoC 中确认，不阻塞产品功能定义：

1. Codex Runtime 当前集成方式是否能安全传递多个独立目录；
2. Codex Runtime 对多根目录的读、写、Patch、命令执行和审批是否一致；
3. Jinggong Runtime 的多根目录沙箱如何在 Windows 上实现；
4. Git Worktree 对用户现有分支和未提交变更的处理策略；
5. 工作区元数据是否支持导出/导入；
6. 工作区规则文件是否采用 `.jinggong/workspace.md`、`workspace.yaml` 或应用本地配置。

## 12. 给 Codex 的实施要求

请在现有精工Agent代码上增量实现本需求，不得另起一个独立产品或破坏现有单仓库模式。

第一步必须盘点现有项目中的：

- 项目/仓库选择模型；
- 会话与项目关联方式；
- Codex Runtime Adapter；
- Jinggong Runtime Adapter；
- 文件操作和沙箱授权；
- Git 状态、Diff 和提交功能；
- 本地数据库与配置持久化。

然后输出影响分析、数据迁移方案、技术设计和拆分任务，再开始编码。

**验收底线：** 一个工作区包含至少前端和后端两个独立 Git 仓库；用户只创建一个 AI 会话、输入一个完整需求，AI 能在同一任务中理解并修改两个仓库，最后按仓库分别展示 Diff、测试和 Git 状态；所有修改仍然受用户授权和安全隔离约束。
