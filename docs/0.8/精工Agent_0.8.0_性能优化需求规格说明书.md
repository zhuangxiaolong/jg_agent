# 精工 Agent 0.8.0 性能优化需求规格说明书

> 文档类型：产品需求 / 迭代需求规格说明书（PRD）  
> 产品：精工 Agent（Windows Desktop）  
> 版本：0.8.0  
> 迭代主题：Codex Runtime 性能优化  
> 文档状态：待评审、待实施  
> 目标代码分支：`develop/desktop-poc`（实施前以仓库实际分支为准）

---

## 1. 迭代背景

精工 Agent 当前以 Electron + React + TypeScript 为桌面应用技术基础，使用本地 SQLite 保存应用数据，并通过 Codex App Server 与 Codex Runtime 进行编码任务执行。现有 Codex Runtime 已具备基础会话管理、流式事件接收、Runtime 复用等能力，但仍有进一步减少启动等待、控制上下文规模、降低工具调用总耗时和改善用户响应感知的空间。

本次 0.8.0 迭代以**提升实际任务完成速度和交互响应速度**为目标，不以更换底层模型或重写 Codex 执行引擎为目标。优先利用现有 Codex Runtime、App Server、上下文构建和工具体系，通过可观测、可验证的优化提升性能。

### 1.1 当前代码基线（实施前需再次核实）

根据此前对 `develop/desktop-poc` 代码的检查，当前基线包括：

- Codex 与 Jinggong Runtime 共用底层 `CodexRuntime` 执行实现，分别通过 Adapter 暴露。
- Codex Runtime 通过 Codex App Server 的 stdio JSONL 通信方式执行任务。
- Codex Runtime 已有一定的空闲实例复用能力，当前代码中空闲 TTL 约为 2 分钟，最多保留 3 个空闲实例。
- 当前空闲复用支持范围包含 `codex`，未包含 `jinggong`。
- `codexRuntimeReuseKey()` 已用于判断运行配置是否兼容，涉及运行时二进制、工作目录、模型服务配置、模型、推理等级、开发者指令、字典和工具配置等信息。
- 当前预热服务主要承担本地组件检查/完整性验证，不等同于 App Server 常驻，也不等同于模型请求预热。
- 原生 `multi_agent` / `multi_agent_v2` 当前显式关闭。
- 仓库已有 `scripts/performance-baseline.ts`，但其主要测试本地源码索引，不是完整的 Runtime 端到端性能基准。

以上是已知基线，不代表后续实施时可以跳过源码核对。Codex 必须先读取当前分支源码、测试和依赖版本，再按现状落地；不得照搬可能已变化的行号、接口或实现细节。

## 2. 迭代目标

### 2.1 核心目标

1. 减少同一会话连续交互时的 Runtime 启动和初始化开销。
2. 减少每轮请求中重复、冗余、与当前任务无关的上下文内容。
3. 降低独立只读工具任务的串行等待时间，同时保证写操作和有依赖关系的任务不被错误并发。
4. 降低 Token 流式事件对桌面 UI 的渲染负担，改善首字响应和持续输出体验。
5. 建立统一的性能指标、日志和可重复基准测试，使后续优化有数据依据。
6. 保证现有 Codex 会话、Jinggong Runtime、项目隔离、插件和工具能力不回退。

### 2.2 预期结果

0.8.0 完成后，应能够用数据回答以下问题：

- 冷启动耗时是多少？热会话是否真正复用了原有进程？
- 请求到第一个助手文本 Token 的时间（TTFT）是多少？
- 上下文组装花费多少时间、注入了多少内容？
- 工具调用占用了多少时间，哪些调用可以并行？
- 一项代表性编码任务从提交到完成用了多少时间？
- 性能优化是否增加了内存占用、错误率或 Token 消耗？

### 2.3 非目标（本迭代不做）

- 不重写 Codex Runtime，不自行实现完整 Agent 执行引擎。
- 不替换 Codex App Server 通信协议，不绕过官方 Runtime 的执行调度。
- 不在 0.8.0 默认开启原生多 Agent；多 Agent 独立作为后续专项评估。
- 不以更换中转站、模型或模型厂商作为本迭代的必要前提。
- 不新增未经验证的 Grok Runtime、Claude Runtime 或其他执行后端。
- 不为追求速度降低代码质量、测试覆盖、权限控制或项目数据隔离要求。
- 不默认引入向量数据库、外部缓存服务或新的云端基础设施。
- 不调整现有业务功能、JIRA 流程、MES/WMS 开发规范的业务定义。

## 3. 用户场景

| 场景 | 当前可能遇到的问题 | 0.8.0 期望行为 |
|---|---|---|
| 同一会话连续提问 | 每轮结束后进程释放，下一轮需要重新启动/初始化 | 在配置兼容且 TTL 有效时复用同一会话的 Runtime 进程 |
| 用户新建 Codex 会话 | 首次发送任务后才开始初始化，等待明显 | 可在会话准备阶段后台完成本地 App Server 就绪，不触发模型生成请求 |
| 分析 MES/WMS 任务 | 每轮可能重复塞入大量固定规范和数据字典 | 固定规则精简，项目上下文分层，具体字典按需检索 |
| 批量读取代码 | 多个独立只读任务逐个执行 | 在明确安全、独立的前提下限流并发执行 |
| 模型持续输出 | UI 频繁刷新，长输出时交互卡顿 | 传输层保持实时，界面层进行轻量批处理渲染 |
| 排查“为什么慢” | 缺少统一时间指标 | 能够看到启动、上下文、TTFT、工具和总耗时分解 |

## 4. 功能需求

优先级定义：P0 = 0.8.0 必须完成；P1 = 0.8.0 建议完成；P2 = 具备时间后完成或预留接口。

### 4.1 P0：Codex Runtime 生命周期优化与同会话复用

**需求编号：PERF-001**

#### 需求说明

优化 Codex Runtime 生命周期，减少同一个逻辑会话连续发送任务时的进程启动、App Server 初始化和协议握手开销。

#### 功能要求

1. 同一逻辑会话在一轮任务结束后进入 `IDLE` 状态，不立即销毁可复用的 Codex Runtime 进程。
2. 在空闲 TTL 内，且运行配置未变化时，下一轮请求优先复用现有 Runtime。
3. 默认空闲 TTL 建议为 **5 分钟**，允许配置；默认最多保留 **3 个空闲 Runtime 实例**，允许配置。
4. 超过 TTL、超过实例上限、应用退出或会话被明确关闭时，应可靠释放进程和关联资源。
5. 一个会话正在执行任务时，不得被空闲实例清理逻辑关闭。
6. 同一会话同时触发多个发送动作时，必须串行化或明确拒绝重复执行，不能让两个任务争用同一个 Runtime 会话状态。
7. 运行配置发生不兼容变化时，禁止复用旧实例；需要按既有逻辑安全重建。
8. Runtime 退出、进程崩溃或通信断开时，必须清理状态并允许下一次请求重新创建实例。
9. 记录本轮是冷启动还是热复用，并记录命中/未命中原因。
10. 本迭代先只对 `codex` Runtime 启用新策略。不得因为 Codex 复用改造而自动把 Jinggong Runtime 加入复用白名单。若底层实现适合抽象，可设计成可扩展接口，但需单独证明兼容性。

#### 配置要求

建议配置项（命名可按现有配置规范调整）：

```ts
interface RuntimeReuseConfig {
  enabled: boolean;
  idleTtlMs: number;       // 默认 5 * 60 * 1000
  maxIdleInstances: number; // 默认 3
}
```

#### 安全与隔离要求

- 默认只允许同一逻辑会话复用其进程，不允许将一个会话的活动线程、历史消息或工具状态直接借给另一个用户会话。
- 若未来需要跨会话共享 App Server 进程，必须先验证 App Server 是否支持多个独立 Thread 安全共存，并设计独立路由、状态隔离和回收策略；不属于本次默认实现。
- 复用 Key 不得记录 API Key、密码、访问令牌等明文凭据。需要使用不可逆摘要或仅比较内存中的安全指纹。
- 复用 Key 至少应能反映：Runtime 类型/版本、可执行文件身份、工作目录、模型服务端点、模型名称、推理等级、开发者指令、项目字典/上下文版本、插件快照、工具定义及关键环境配置。字段以当前 Runtime 实际配置为准。

#### 验收标准

- 同一会话在 TTL 内连续执行两轮任务，第二轮不重新 spawn Codex App Server，且任务结果与原有逻辑一致。
- 更改模型、服务端点、工作目录、开发者指令、字典版本或工具配置等关键参数后，不会错误复用旧实例。
- TTL 到期后进程能够释放；释放后再次发送请求可正常冷启动。
- 应用退出时所有空闲 Runtime 均被清理，不残留孤儿进程。
- 并发发送、取消任务、异常退出相关测试通过。

### 4.2 P0：App Server 后台预热

**需求编号：PERF-002**

#### 需求说明

将“本地组件完整性检查”与“Runtime 进程预热”区分。用户进入 Codex 会话或选择 Codex Runtime 后，可在后台启动本地 App Server 并完成必要的协议初始化，让用户发送第一条消息时减少本地启动等待。

#### 功能要求

1. 提供独立的 Runtime App Server 预热能力，不替代现有组件校验服务。
2. 可在用户进入/创建 Codex 会话后异步触发，不能阻塞 Electron 主窗口可交互。
3. 预热只允许完成本地进程启动、协议握手和必要的非生成式初始化。
4. 默认不得发送模型生成请求，不得因预热产生模型推理费用。
5. 同一配置只允许有一个预热任务；多个页面或重复事件不得重复启动进程。
6. 用户真正发送消息时，将已准备好的 Runtime 与会话安全绑定；绑定失败时回退为正常冷启动。
7. 用户取消、切换 Runtime、关闭会话或应用退出时，预热进程应按生命周期策略处理。
8. 支持禁用预热，且预热失败不能影响正常冷启动。
9. 预热过程应记录耗时、成功/失败及失败原因。

#### 验收标准

- 预热不会触发模型生成请求。
- 预热期间主界面仍可操作。
- 预热成功后第一次发送任务能够使用已初始化的本地进程。
- 预热失败不影响用户正常使用 Codex。
- 同一配置下重复触发不会产生多个无主进程。

### 4.3 P0：性能遥测与耗时分解

**需求编号：PERF-003**

#### 需求说明

建立统一性能埋点。所有耗时采用单调时钟计算，避免系统时间调整影响结果。

#### 必须采集的指标

| 指标 | 定义 |
|---|---|
| `runtime_cold_start_ms` | 从决定创建 Runtime 到 App Server 完成必要初始化的耗时 |
| `runtime_reuse_hit` | 本轮是否命中热复用 |
| `runtime_reuse_miss_reason` | 未命中原因，如过期、配置变化、进程退出、未启用 |
| `app_server_spawn_ms` | 创建子进程耗时 |
| `app_server_initialize_ms` | App Server 协议初始化耗时 |
| `thread_resume_ms` | 恢复已有 Thread/会话状态耗时 |
| `context_build_ms` | 本轮上下文收集与组装耗时 |
| `context_size_chars` | 注入上下文的字符数量；如可获得 Token 数，另行记录真实 Token 数 |
| `first_assistant_delta_ms` | 从用户发送任务到收到第一个助手文本增量的耗时（TTFT） |
| `first_ui_render_ms` | 第一个助手文本增量显示到界面的耗时 |
| `tool_call_count` | 本轮工具调用次数 |
| `tool_call_duration_ms` | 每次工具调用及汇总耗时 |
| `task_total_ms` | 从用户提交到任务结束的总耗时 |
| `input_tokens` / `output_tokens` | 仅当 Runtime/API 提供可信用量字段时采集；不可用时不伪造 |
| `runtime_exit_reason` | 正常退出、TTL 清理、应用退出、错误退出等 |

#### 要求

1. 每轮请求使用唯一 `traceId`，将主进程、Runtime 事件和渲染层日志关联起来。
2. 记录应结构化、可过滤、可导出；优先沿用项目现有日志基础设施。
3. 不记录 API Key、密码、完整客户数据、代码文件全文或敏感业务字段。
4. 指标采集对主执行链路的额外耗时应尽可能小；日志写入不得阻塞 Token 流。
5. 至少支持按会话、Runtime 类型、模型、冷/热启动和任务类型筛选。
6. 为无法取得的指标标记 `null` / `unavailable`，不能用估算值冒充真实数据。

#### 验收标准

- 一轮任务可以导出完整的时间分解记录。
- 能区分进程启动、上下文准备、首 Token、工具调用和任务总耗时。
- 日志中不存在明文 API Key 或用户凭据。
- 开启/关闭遥测后任务执行结果一致。

### 4.4 P0：上下文分层与按需加载

**需求编号：PERF-004**

#### 需求说明

优化 MES5、MES6、WMS 开发字典、开发规范、项目资料、JIRA 任务描述和历史对话等上下文的组织方式，减少每轮请求中重复注入和无关内容。

#### 上下文分层

| 层级 | 内容 | 加载方式 |
|---|---|---|
| L0 核心规则 | 必要的 Agent 行为约束、代码安全规则、基本开发原则 | 每轮固定注入，保持精简 |
| L1 项目概览 | 当前仓库、技术栈、模块边界、数据库类型、项目约定 | 会话启动或项目变化时加载，可缓存 |
| L2 当前任务 | 用户任务、JIRA 标题/描述、相关附件摘要、当前任务约束 | 每轮按任务更新 |
| L3 按需知识 | MES5/MES6/WMS 数据字典、字段说明、接口规范、业务规则、测试案例 | 根据任务检索后加载相关片段 |
| L4 历史上下文 | 较长对话的摘要、已确认方案、未完成事项 | 按需加载摘要；原始历史保留在会话中 |

#### 功能要求

1. 核心开发规范不得因性能优化而被删除；应通过去重、归类和压缩降低冗余。
2. 不再无差别地把所有 MES/WMS 字典全文注入每轮请求。
3. 优先复用仓库现有索引/搜索能力。若当前索引能力不足，先实现轻量关键词检索，不默认新建向量库。
4. 检索结果必须携带来源文件、章节/行号或其他可追溯信息，便于模型核对原文。
5. 只把与当前任务相关且达到置信阈值的片段加入上下文；无法确定相关性时，提示模型通过现有文件读取工具进一步核查。
6. 项目、工作目录、产品线、字典版本变化时，清理或重新构建对应上下文缓存。
7. 支持上下文大小统计，并记录每个模块贡献的字符数/Token 数（真实 Token 数可得时优先）。
8. 历史内容达到阈值时，可生成滚动摘要，但必须保留用户明确要求持续遵守的约束、当前任务目标、已做修改、待办事项和关键决策。
9. 摘要不能覆盖原始会话记录；用户仍可查阅历史。
10. 增加“上下文来源/加载摘要”的诊断信息，不能向用户暴露内部密钥或隐藏系统提示词。

#### 缓存要求

- 缓存键至少包含文件规范路径、修改时间、文件大小及项目/字典版本信息。
- 文件变更后应失效；由 Agent 本轮修改的文件应主动使相关缓存失效。
- 不允许跨项目混用项目专属上下文。
- 对含凭据、客户隐私或高敏感信息的内容不做持久化缓存，除非已有机制明确安全并经过评审。
- 字典检索结果必须能追溯至原始字典，不能只保存模型生成的二次解释。

#### 验收标准

- MES5、MES6、WMS 相关任务能够按产品线和业务主题加载知识，而不是每次注入全部字典。
- 相同任务重复运行时，重复上下文能够去重，缓存不会在文件更新后返回旧内容。
- 能查看本轮上下文各层级的大小和来源摘要。
- 代表性长上下文任务的注入内容较 0.7 基线明显减少；建议目标为中位数减少 30% 以上，同时任务正确率、测试通过率不得下降。
- 不相关知识不应被错误注入并影响任务结果。

### 4.5 P1：只读工具受控并发与结果缓存

**需求编号：PERF-005**

#### 需求说明

对平台自有工具调用进行安全分类。只有确认彼此独立、无副作用的只读调用才允许有限并发；写入、命令执行、部署、数据库变更及状态型工具不得被简单并发化。

#### 功能要求

1. 给平台自有工具增加执行元数据：`readOnly`、`idempotent`、`concurrencyGroup`、`cachePolicy`。
2. 默认最大并发数为 3，可配置；必须设置队列和取消机制。
3. 只有 `readOnly=true` 且 `idempotent=true`、并且无共享状态冲突的工具可进入并发执行队列。
4. 同一文件的读取、同一会话状态变更及相互依赖的工具调用必须保持正确顺序。
5. 写操作、Shell 命令、数据库写入、文件修改、Git 状态修改、部署类操作默认串行，不允许因本需求自动并发。
6. 对确定性只读查询可增加短时缓存，但必须具有项目/会话作用域与失效条件。
7. 工具并发失败时，应返回可识别的单项错误，不得吞掉错误或把部分结果伪装成完整结果。
8. 不改变 Codex App Server 内部工具调度逻辑；本需求只处理精工 Agent 自己管理的平台工具。

#### 验收标准

- 两个或更多独立、只读平台工具可以并发执行，最大并发数不会超过配置。
- 写工具和 Shell 操作仍保持安全顺序。
- 取消任务后，尚未开始的队列任务取消，正在运行的任务按工具能力安全中止。
- 缓存结果在文件、配置或项目发生变化后失效。

### 4.6 P1：流式事件与界面渲染优化

**需求编号：PERF-006**

#### 需求说明

保持 Runtime 到主进程的流式传输及时性，对 React 渲染层进行受控批处理，避免每个 Token 或每个微小事件都触发整块会话 UI 更新。

#### 功能要求

1. 不得在网络接收层、Runtime 事件层人为等待较长时间再转发 Token。
2. 可以在渲染层将高频文本增量合并到 UI 更新批次，建议刷新间隔 16～50ms，且最后一个增量必须及时 flush。
3. 消息列表应尽量局部更新，不因一个消息增量重新渲染整个会话列表。
4. 历史消息、工具事件和当前流式消息需要区分更新路径。
5. 切换会话、关闭窗口、取消生成时清理订阅和待刷新队列。
6. 流式内容必须保持顺序、完整，不允许丢字符、重复字符或错乱。
7. 用户仍能及时看到工具状态、取消状态和错误提示。

#### 验收标准

- 长文本流式输出时 UI 不明显卡顿。
- 流式内容最终与 Runtime 原始事件内容一致。
- 在性能测试中可分别测出首 Token 到首屏渲染的耗时。
- 高频事件不会造成持续的高 CPU 占用或不受控的 React 重渲染。

### 4.7 P1：性能诊断面板/导出

**需求编号：PERF-007**

#### 需求说明

提供面向开发和问题排查的轻量性能诊断能力。不得为了本功能重新设计主界面。

#### 功能要求

- 可在开发模式或明确开启的诊断模式下查看一轮任务的性能数据。
- 显示冷启动/热复用、上下文构建、TTFT、工具耗时和任务总耗时。
- 可导出脱敏 JSON 或 CSV。
- 生产环境默认不显示内部调试细节；用户数据必须脱敏。
- 如果现有日志查看页已支持扩展，优先在原有入口增加诊断信息。

### 4.8 P2：性能策略配置

**需求编号：PERF-008**

在现有设置架构允许的前提下，提供以下可配置项：

- Runtime 空闲复用开关。
- 空闲 TTL。
- 最大空闲实例数。
- App Server 预热开关。
- 上下文按需检索开关（如关闭，回退到现有兼容行为）。
- 平台只读工具最大并发数。
- 流式 UI 刷新间隔（仅内部高级配置，不建议普通用户频繁调整）。

配置必须有合理默认值、范围校验和恢复默认值能力。配置变化后应明确哪些项目需要在下一会话生效，不能静默改变正在执行的任务。

## 5. 非功能需求

### 5.1 稳定性

- 任一优化模块关闭或初始化失败，均能回退到现有 0.7 可用路径。
- Runtime 崩溃、进程断连、取消任务、应用退出时均不得残留无主子进程。
- 不能因缓存、复用或并发造成跨会话数据污染。

### 5.2 兼容性

- Windows 桌面环境优先，保持现有 Electron 打包、升级和本地数据兼容。
- 不改变现有 SQLite 数据结构，除非诊断数据确有持久化必要；如需迁移，必须提供向前兼容迁移脚本。
- 保持现有 Codex Runtime 和 Jinggong Runtime 的功能边界。
- 0.8.0 不升级 Codex 上游版本，不混合“Runtime 性能优化”和“上游版本升级”两个变量；确需升级时另行评估并单独提交。

### 5.3 安全

- 本次优化不得扩大现有 Runtime 权限。
- 现有 Codex Runtime 当前采用的 `danger-full-access` / `approval_policy = never` 属于高权限执行配置；本迭代不得将其描述成 OS 沙箱安全，也不得因性能优化进一步放宽权限。
- 日志、缓存、性能导出中不得出现明文 API Key、密码、用户令牌或完整客户敏感数据。
- 工具并发必须遵守只读白名单，禁止把 Shell、写文件、数据库写入和部署命令纳入默认并发。

### 5.4 性能

- 指标采集不得明显增加任务处理耗时。
- Runtime 复用要以准确性和资源可控为前提，不能无限常驻。
- 上下文优化要兼顾任务质量，不以减少 Token 为唯一目标。
- 所有性能结果必须标明测试环境、模型、中转站、任务集和运行次数。

## 6. 性能评测方案与目标

### 6.1 测试任务集

至少建立以下四类固定任务：

1. **轻量问答**：基于当前项目规范回答一个简单问题，不修改文件。
2. **代码定位**：定位某个业务功能的入口、调用链和关键文件。
3. **小型修改**：修改一个明确的小功能并运行相关测试。
4. **MES/WMS 知识任务**：根据指定字典/业务规则定位字段并分析代码影响。

每类任务使用固定仓库快照、任务描述和验收点。涉及真实模型的测试必须由用户主动执行，避免 CI 自动产生中转站费用。

### 6.2 测试维度

| 维度 | 测试方式 |
|---|---|
| 冷启动 | 清空对应 Runtime 进程后执行任务 |
| 热启动 | 同一会话连续执行第二轮及后续任务 |
| 上下文 | 对比完整注入与按需加载的内容大小、结果质量 |
| 工具 | 对比独立只读任务串行与受控并发的耗时 |
| UI | 使用长文本流和高频事件验证渲染表现 |
| 资源 | 记录主进程、Runtime 子进程内存及 CPU（可采集时） |

每个场景建议至少运行 5 次；报告 P50、P95 和失败次数，不只展示最好的一次。模型、中转站、模型参数、项目快照和任务描述必须保持一致。

### 6.3 目标原则

- 先记录 0.7 基线，再记录 0.8 结果。
- 热复用的硬性验收以“同会话第二轮不重新创建 App Server 进程”为准，不以单次毫秒数作为唯一标准。
- 对上下文按需加载，建议以代表性长上下文任务中位数注入内容减少 30% 作为初始目标，并要求任务质量不下降。
- 对工具并行，以并发行为正确、最大并发受控及总耗时有可重复改善为准。
- 不预设模型推理速度提升。模型服务端性能与本地 Runtime 优化分别报告。

## 7. 版本范围与交付物

### 7.1 必须交付

- Codex Runtime 生命周期复用优化。
- App Server 后台预热能力。
- 性能遥测与耗时分解。
- 上下文分层、按需加载和缓存失效机制。
- 自动化测试和固定性能任务集。
- 0.7 与 0.8 性能对比报告模板。

### 7.2 建议交付

- 平台只读工具受控并发。
- 流式 UI 局部更新优化。
- 性能诊断数据导出。

### 7.3 暂不交付

- 默认开启 Multi-Agent。
- Jinggong Runtime 的进程复用策略改造。
- 更换中转站/模型策略自动路由。
- 新的向量数据库或独立缓存服务。

## 8. 发布与回滚要求

1. 所有新增性能能力应有独立 Feature Flag 或配置开关。
2. 默认先启用低风险能力：性能指标、同会话复用、轻量预热。
3. 上下文按需加载、只读并发和 UI 批处理可以分项关闭。
4. 出现会话串线、上下文丢失、工具结果不完整或明显任务质量下降时，必须可以单项回滚。
5. 0.8.0 发布前必须完成 Windows 安装包验证、旧版本数据兼容验证及异常退出清理测试。

## 9. 给 Codex 的实施约束

1. 开始开发前，先读取仓库当前分支、`package.json`、锁文件、Runtime 管理器、Runtime Adapter、上下文组装、工具注册、流式事件处理和现有测试。
2. 先输出当前代码结构与本需求的映射表，指出哪些能力已存在、哪些缺失、哪些需要重构；不得重复开发已有能力。
3. 不得只修改文档或写伪代码；必须完成可运行代码、测试和必要的配置迁移。
4. 每个功能拆成小提交/小阶段，先实现 P0，再实现 P1。
5. 修改前后执行相关单元测试、集成测试、类型检查、Lint 和构建。
6. 所有新增配置必须带默认值、校验、异常处理和兼容行为。
7. 不得为了并发而并发，不得跨会话复用业务上下文。
8. 对无法验证的性能收益明确标注，不得编造提升百分比。
9. 不得在本迭代顺手升级 Codex Runtime 依赖版本或改变模型 API 协议；如发现必须升级，先单独说明原因和影响。
10. 完成后提供变更文件清单、关键设计说明、测试结果、性能基线与优化后对比，以及未完成事项。
